# Review an Agent Core App for resilience

Review the App's actual workflow, handlers, knowledge reader, and configured limits. Use available authorized traces or offline fixtures to walk a short request, a complex request, a long-history follow-up, and a failure near the limit. For each finding, identify the first limiting resource, the affected path, and what the App can still deliver. Use [review patterns](references/review-patterns.md) when you need implementation precedents or acceptance cases.

1. **Assess useful program-side data work.** Trace where raw data enters the model input. Look for parsing, schema checks, pagination, filtering, joins, deduplication, calculations, diffs, and coverage checks that a handler can perform. When worthwhile, pass the model compact, validated facts with source identity and coverage. Fully model-driven, program-driven and hybrid replies are all legitimate; lack of preprocessing alone is not a defect. Use the model for intent, ambiguity, interpretation, and synthesis as appropriate. Reuse same-scope reads and advance known dependencies through program routes.
2. **Inspect the first tool decision and its payload.** Identify the first model request that can choose a tool, even if context processing ran earlier. Inspect the tool IDs, descriptions, parameters, and choice mode actually sent by its transport. Check for missing tools needed by implicit requests, follow-ups, or multiple intents. Reuse the executable catalog to expose capabilities relevant to the current stage, available facts, and user scope. Check that direct replies or clarification remain possible and that later-stage tools become available when their prerequisites hold. Keep execution authorization in the App.
3. **Remove redundant model-facing tool information.** Compare definitions with adjacent instructions and repeated call stages. Look for equivalent aliases, repeated purpose or field descriptions, long examples, and internal metadata. Keep the differentiators the model needs to choose correctly and preserve required fields, scope, and confirmation rules. Use the prepared request's `measure` to compare effective input size, counting schemas embedded in instructions as part of the same input. Check routing and parameter accuracy as well as size.
4. **Size the quota to the task.** For Apps with materially different workloads, check that the App chooses an effective allocation from validated work and registered capability requirements. Keep separate model and tool ledgers, hard caps, the original deadline, and a completion reserve. Charge actual attempts across retries, fallback, compression, and children. Increase an allocation only when validated new work justifies it within the original caps and without resetting consumption. Reassess necessary work before reaching the completion reserve; expand an underestimated allocation within host authority when justified. Replan repeated work that makes no progress, and consider safe context reduction before partial delivery. A fixed allocation can suit uniform paths.
5. **Check knowledge sections and retrieval.** For text corpora, look for paired section anchors or a structured equivalent with stable document and section IDs. Locate the executed search path and verify whether it uses MiniSearch, for example through `TextSearch` from `@jangts/agent-core/kits/search`, or a suitable existing index. Confirm that bounded hits resolve to authorized sections at the expected revision and that the reader loads the cited content. Test representative queries with the App's actual languages and data. Structured records should use the App's query handlers.
6. **Check context reduction before overflow.** Measure the assembled request with its actual instructions, tool schemas, and output reserve. Prefer targeted section reads, projection, and complete-group trimming. For long conversations that need continuity, check for a compression trigger and a lower target, protected recent turns and current constraints, and an incremental summary with a coverage cursor and original-source lookup. Count compression against the run and retain a valid fallback if it fails or cannot fit. App policy controls these choices. Core enforces the final bound.
7. **Exercise completion and failure boundaries.** Check the transitions for completed, partial, missing evidence, budget exhaustion, dependency failure, and cancellation. Confirm that the App can report verified progress at zero model calls left. Bound retries to recoverable work, preserve completed effects, and reconcile an uncertain write against its receipt before any repeat. Make denied, cancelled, and incomplete work distinguishable in output and diagnostics.

Deliver findings ordered by impact. For each, give the path and its evidence, the actual versus allowed usage or coverage when known, a fix that fits the App's contracts, and the smallest test that would demonstrate it. Use the installed SDK's workflow inspector and offline scenarios when they fit. Use the budget optimization Skill for a deeper per-call cost ledger or before-and-after measurement.

Use [request recovery](../../docs/api/reliability.en.md) and [reliable recovery article](../../articles/reliable-request-recovery.en.md) to review whether faults preserve useful work and produce a truthful account. Optional modules must not veto the principal task. Distinguish execution, delivery, persistence and transport outcomes; never conceal cancellation or replay an uncertain write.

Assess node boundaries by contract and net benefit, not business versus technical labels. Complete-use-case nodes and bounded exploration loops can both be sound. Observation alone does not justify splitting. No inspection warnings is not design approval; offline wiring is not semantic evidence. Apply intern-assistant rules only when they belong to the App product contract.

Use [the organization comparison](../../docs/examples/organization-comparison.en.md) as a runnable end-to-end starting point. Trace the principal answer and receipt through read, generation, optional-check and uncertain-write faults in the current implementation. Then substitute actual App ports for authority, persistence and delivery. Do not count the example as testing Completion Kit or request-recovery helpers unless those helpers are actually invoked.

For durable work, start from each step's side effects. Choose `safe` only when replay is safe; use `reconcile` when a prior attempt may have taken effect. Require explicit `completed` plus state, `not-executed`, or `unknown` results, never an untagged State. Confirmation must not repeat the write, call a model or compensate. A missing receipt is not stable negative evidence while an old call could still complete. Check that `unknown` preserves position and reservations and stops automatic execution.

Review `authorize` by its `operation` (`execute`, `reconcile`, `read`). Read-only confirmation receives zero model allowance and can confirm old work after execution time or allowance is exhausted; any new attempt must still pass the original gates. Completed-result reads use current authorization, request timeout and App retention, not the expired execution deadline. Keep task/step operation identity stable across retries. Check commitId read-back on lost save acknowledgements and do not confuse it with atomicity or exclusion. Persisted cancellation belongs to the App; an aborted wait cannot prove an external effect was rolled back. Use the [Durable contract](../../docs/api/kits.en.md#durable) and the smallest applicable fault case; do not add a separate recovery protocol.

For a stage/tool matrix, read the [executable matrix reference](../../docs/examples/lifecycle-matrix.en.md). Preserve combined intent/next decisions when suitable; derive stage, hook, handler, all/selected mode and intent scope from actual registration. Export optional `lifecycleMatrix` for inspector/diff; associate authorized `toTrace` subflow records through stable binding IDs. Missing records remain unobserved, not proof of non-execution. Review pairing rejection, visibility and live authorization, retained results, budgets and cancellation; do not replace a valid matrix with use-case nodes merely to match another App's graph.

Use [reply development](../agent-core-reply-development/SKILL.md) for answer style, reference use and processing choices; it reuses these recovery guarantees without making program-side rendering mandatory.
