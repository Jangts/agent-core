# Resilience review patterns

Use the patterns that match an observed failure or a representative App path. Consult the installed SDK's `development/docs/api/core.en.md`, `development/docs/api/context-processing.en.md`, `development/docs/knowledge.en.md`, and `development/docs/api/kits.en.md` for the relevant contracts.

| Observed pattern | Program and model responsibilities | Check |
| --- | --- | --- |
| The model receives full lists or makes repeated reads to count, compare, or find exceptions | Query the needed projection, aggregate in a handler, and return scoped counts, exceptions, and source references. Track whether the scan and returned detail are complete separately. Cache equivalent successful reads and share in-flight reads within the authorized request. | Use multiple pages with an incomplete page or an explicit refresh. Check that counts describe the scanned scope, equivalent reads run once, and incomplete results stay marked partial. |
| The first tool decision exposes the entire catalog, forces a tool call, or omits a required capability | Inspect the actual prepared tool set and choice mode. Derive stage-specific candidates from the registered catalog and trusted request context. Keep a path for replies or clarification and expose dependent tools when evidence or user confirmation is available. | Capture the first decision for a direct question, an implicit action, a short follow-up, and a multi-intent request. Assert which tools are offered and exercise the expected path. Verify authorization at execution. Use real-model cases to evaluate whether the shortlist still supports semantic selection. |
| Tool definitions repeat descriptions, schema details, or prompts across stages | Keep one definition of each responsibility. Keep critical distinctions such as read versus write, required identifiers, effects, and outputs where the model needs them. Send only stage-relevant definitions and keep local metadata in the App. Measure the actual model input for the same representative request before and after. | Compare tool IDs and effective request size, including XML, JSON, or other schema text embedded in instructions. Verify tool choice, arguments, and authorization on cases that distinguish similar tools. |
| Short replies and multi-stage requests share a single quota | Evaluate an appropriate initial allocation from workload and registered requirements; revise it when necessary work changes. Resolve intent and propose work in the same model call where possible. Clamp against hard limits. Give known dependencies direct routes and stop repeated cycles without new evidence or state progress. | Check a direct request, legitimate multi-stage work, a higher model-proposed tier above the cap, and repeated calls with equivalent parameters. Assert actual attempts and the final state. |
| A child, retry, or optional generation consumes the final answer call | Share request accounting across branches. Keep a parent reserve and cap child and recovery work. Before the reserve boundary, reassess work, context reduction and justified allocation changes; switch to finalization only for actual blockers or exhausted feasible alternatives. At zero remaining calls, use program-generated receipts, partial results, or a clear insufficient-evidence result. | Assert that an underestimated allocation can expand without resetting consumption, repeated work replans, zero remaining calls can still explain actual progress, and cancellation prevents late success. |
| The model repeatedly receives entire documents or answers from snippets | Use stable chapter or section identities, bounded retrieval, then an authorized read of selected sections. For MiniSearch, verify the executed index, searchable and stored fields, tokenizer, candidate limit, and revision or refresh policy. Keep snippet, read receipt, and complete section coverage distinct. Report no candidates, source unavailable, and access denied as separate outcomes. | Test an input with common aliases or Chinese terms where applicable, a miss, a stale section reference, an unauthorized section, and an oversized section. Check that a hit alone produces no read receipt. |
| Old history consumes the request and gets summarized every turn | Keep recent full turns and protected material. Apply thresholds to measured input, then summarize newly covered old history into a versioned checkpoint with its cursor. Preserve source references, decisions, constraints, and unresolved work. Recheck live facts and permissions at use. | Test below and above the trigger, the same history on the following turn, an edited or stale checkpoint, failed compression, and too little remaining quota. Check the final request against its real transport. |
| Tool or provider failures cause repeated work or ambiguous completion | Distinguish exhausted calls, input/schema/output limits, timeout, cancellation, access denial, invalid data, and transient failure. Bound repair and retry. Preserve committed results and confirm uncertain effects by authoritative receipt. | Simulate an invalid proposal, repeated no-progress work, transport failure, and a timed-out write with a recorded commit. Check that there is no duplicate write or false success. |

With static evidence, report the suspected boundary and the trace or fixture needed to confirm it. Offline cases can prove branching, accounting, and observable outcomes. Evaluate semantic quality, retrieval recall, and compression fidelity with representative inputs. Compare by request class and retain failure and partial-completion rates alongside calls, tokens, and elapsed time.
