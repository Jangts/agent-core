# Design an Agent Core workflow

Use the App's installed SDK and read its workflow and workflow view contracts at `development/docs/api/workflow.en.md` and `development/docs/api/workflow-views.en.md`. For an existing App, start from the actual workflow and tool registration. Use the workflow inspector if you need the graph or an authorized recorded execution.

1. **Start with representative requests.** Cover a direct reply, an implicit or follow-up request, dependent work, a missing prerequisite, and a failed or denied operation where applicable. Describe the required result, the source of its facts, and what must be checked before an external effect or final delivery.
2. **Compare boundary benefits and costs.** Describe inputs, prerequisites, consumable outputs, effects, completion evidence, progress and failure ownership first. Independent routing, commits or recovery are reasons to consider splitting, not sufficient conditions. Compare independent recovery and reuse benefits with state handoff, invalidation, calls and recovery complexity. A complete use case can be one node; a bounded exploration loop can be appropriate when new evidence drives the next decision and no-progress work exits or replans. Business names do not establish good boundaries; technical names do not establish bad ones. Use internal subflow/invocation records for observation-only details. Avoid nodes for local parsing, counting or logging without independent outcomes. A tool may serve several nodes and a node may use several tools.
3. **Specify the state and routes.** Record each proposed node's input and prerequisites, committed output and evidence, route priority, failure target or terminal status, and whether a model is optional or required. Derive route and inspector metadata from the executable declarations where practical. A downstream node can take a validated upstream result directly. An incomplete, stale, or out-of-scope result must use the declared partial, recovery, or clarification path. Re-entry must have a progress condition and a bound.
4. **Call the model when the outcome requires judgment.** One call can understand the goal, select a capability, and propose known arguments using the conversation in scope. Let program logic advance known dependencies, enforce permissions, validate contracts, and deliver prepared results. Call the model again when new evidence requires interpretation or synthesis. Keep execution and delivery receipts distinct from model proposals.
5. **Review representative paths.** Walk the candidate route, expected effects and call count for each request. Check that recovery keeps valid results and avoids replaying completed effects. For an implemented change, reuse the SDK's workflow diff and offline scenarios where appropriate. Inspect actual node visits and invocation records separately. Use real-model evidence for claims about semantic quality.

Deliver a compact node and route design with the reason for each split or merge, the happy and failure paths, and the cases that would verify them. For example, a comparison can export a validated result set to a check for the same version. If the result set is partial, the check waits for the missing scope or reports what can be verified.

Core guarantees its execution, budget, cancellation and handler contracts; Support offers recommended compositions; App policy owns role behavior, business evidence and delivery. Do not require business-node topology or intern-assistant behavior for every App. Inspection without warnings only establishes that inspected declarations triggered no checks. Require actual contracts and behavioral evidence to assess the design. See [node boundary decisions and counterexamples](../../articles/nodes-and-tools.en.md).

Work through [the same task in two organizations](../../docs/examples/organization-comparison.en.md) before choosing a boundary. Run its installed-package entry, read the shared business handlers and both registrations, and compare which results can be independently consumed or recovered. Select boundaries from the App’s required handoffs and lifecycle rather than matching example node names. Follow the example’s current regression entry for concrete routing and effect assertions.

When a task must survive restart, identify the actual side-effect boundary before choosing a durable step. `safe` permits replay only when the operation tolerates it; `reconcile` confirms an uncertain prior operation using a stable operationId. Its explicit results are `completed` with state, `not-executed`, and `unknown`; an uncertain receipt must not trigger blind repetition. Confirmation is read-only with zero model allowance, separate from a new execution attempt and its authorization, deadline and reservation. Preserve completed effects and use current read authorization for saved results after the execution deadline.

A Durable step may contain a Workflow or Agent, but its recovery position is the step boundary, not an arbitrary inner graph node. Keep one owner of the durable position and commit; use ordinary mappings instead of another scheduling protocol. Save acknowledgement read-back uses commitId under the host's real exclusion, not inferred success from matching output. Cancellation stops acceptance and may leave remote effects unknown. See [Durable](../../docs/api/kits.en.md#durable); select a targeted failure case before changing interfaces.

For a stage/tool matrix, read the [executable matrix reference](../../docs/examples/lifecycle-matrix.en.md). Preserve combined intent/next decisions when suitable; derive stage, hook, handler, all/selected mode and intent scope from actual registration. Export optional `lifecycleMatrix` for inspector/diff; associate authorized `toTrace` subflow records through stable binding IDs. Missing records remain unobserved, not proof of non-execution. Review pairing rejection, visibility and live authorization, retained results, budgets and cancellation; do not replace a valid matrix with use-case nodes merely to match another App's graph.

For reply wording, input/output formats, style or reference design even when the graph is unchanged, use [reply development](../agent-core-reply-development/SKILL.md). Keep fully model-driven, program-driven and hybrid choices valid.

For prompt ownership, stage-specific context and explicit history processing, read [prompts and context](../../articles/prompts-and-context.en.md). Apps choose content and policy, Support executes the configured processing flow, and Core enforces assembly and invocation boundaries. Direct message calls do not acquire fragment-level provenance or mutation auditing.
