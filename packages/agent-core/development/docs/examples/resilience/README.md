# 保存已确认的成果，限制恢复范围

保存报告后，生成详情失败。用户能否收到准确的说明，取决于 App 保存的是业务回执、未确认操作，还是一次尚未交付的文案。用这个离线案例核对这三者的边界，再把断言接到自己的业务端口。

## 运行并核对结果

在已安装 Agent Core 的项目中使用 Node.js 22.12 或更新版本。

```sh
node node_modules/@jangts/agent-core/development/docs/examples/resilience/request-recovery.mjs
```

[示例源码](request-recovery.mjs)使用内存端口和断言，五个场景均验证实际结果。写入计数记录模拟端收到的操作，回执描述 App 能确认的成果。

| 注入故障 | 应看到的处理 | 必须保持的事实 |
| --- | --- | --- |
| 保存成功后详情格式错误 | `source: 'recovery'`，基于原回执修复 | 写入一次，修复一次 |
| 修复也失败 | `source: 'fallback'`，说明已保存、详情不可用 | 同一回执仍可用，保留两次失败原因 |
| 模拟写入后丢失确认 | 返回 `status: 'unconfirmed'` | 无可用回执、不生成成功内容，写入一次 |
| 附属审核报错 | 正常交付已确认成果 | 审核错误保留在检查记录 |
| 保存后请求取消 | 以取消结束 | 已确认回执保留，修复与 fallback 都未调用 |

## 把恢复限制在已确认的工作上

主执行一拿到回执就把它写入 App 工作记录。用 `defineCompletionChecks` 区分必需交付格式和附属审核。格式失败时，`createRequestRecovery` 的恢复函数只能读取已有回执并替换详情。同步 fallback 根据回执输出当前可确认状态，错误留给运行诊断。

业务写入无法确认时，先用稳定操作身份查询权威回执。核对明确未执行后，才按原期限、额度和当前授权决定是否重试。内存案例保留未知状态。跨进程保存、互斥、回执读取和重新交付要由真实端口验证。用户取消能终止仍在进行的工作，已经发生的写入继续以业务回执核实。

用一次执行专用超时验证恢复仍能在外层请求期限内运行，并单独测试用户取消。二者都应保留诊断中的失败阶段。最终消息是否到达客户端，由宿主的交付协议和消息记录确定。
