# 用故障验证任务如何收尾

审批通过后服务端确认写入，最后一条消息却未送达。验收应分别断言业务写入一次、回执可读、重连可查询，以及取消以后不会接受迟到的交付。只有“捕获了异常”的断言发现不了这些差异。

## 在交接最脆弱的地方注入故障

| 注入点 | 必须成立 |
| --- | --- |
| 工具参数合规但授权拒绝 | 业务端口调用为零，错误与权限相符 |
| 外部效果完成后，保存或回包中断 | 稳定身份可核对，未知时不重复写入 |
| 流程已得结果，答复格式校验失败 | 只修复当前交付，保留已有成果 |
| 子任务取消但结果稍后到达 | 不进入父任务提交，已确认的效果仍可查 |
| 总额度接近上限或输入过长 | 硬上限有效，交付仍能给出真实状态 |

把状态和业务调用次数都写入断言，保留路由与错误分类作为定位证据。持久化失败需要实际存储端口的故障测试。用模拟端口时，结果仅涵盖该模拟条件。

## 按可验证的问题选择环境

纯逻辑用例检查计算与 schema。离线组合验证授权、路由、预算和回执。真实模型样本验证语义选择与表述。进程重建、远端操作与连接恢复则用目标运行环境验证。案例的固定回复用于控制条件，可以对同一输入反复检查。

以下命令运行随包的分层测试 fixture。

```sh
sdk=./node_modules/@jangts/agent-core
node "$sdk/development/skills/agent-core-app-testing/scripts/test-agent.mjs" \
  --fixture "$sdk/development/skills/agent-core-app-testing/examples/agent-tests.mjs"
```
