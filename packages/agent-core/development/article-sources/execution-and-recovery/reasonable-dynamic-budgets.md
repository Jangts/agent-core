# 按剩余工作调整调用预算

一个月度对账任务已经完成资料读取，还需两次模型调用解释差异、一次检查和一次必要的交付修复。初始分配只有两次时，可以用剩余工作重新评估。是否继续取决于任务是否可完成、上限是否允许以及刚才有没有取得进展。

## 把初始分配、上限和消耗分开

`maxCalls` 是初始分配，`maxTotalCalls` 是宿主设置的上限，默认等于初始分配。请求绑定的 Runner 通过 `callBudget` 提供当前已用、有效余量与调配记录。子任务还受上游容量和保留额度约束。一次已经消耗的调用在失败或重规划后仍计入账本。

将执行、复核、交付、恢复的必要次数交给 `Support.assessModelBudget`。用观察到的成果和阻塞来更新估计。它返回建议，不调用模型。App 采纳 `expand` 时，用 `adjustCallBudget` 传入上限内的新分配和清晰的程序原因。在使用已绑定 Runner 时，同一请求可以稳定地查看前后两次分配。

假设账本已用一次、分配为二、上限为八。解释两次、核对一次和最多一次交付修复共需四次余量，因此调整的目标总分配为五。已用的一次仍在其中。若祖先只留下三次可用容量，将本地分配设为五也无法拿到第四次调用。此时应重新决定哪些工作可以确定性完成，或依据仍缺的条件请求澄清。

## 扩额要有明确的产出

缺少用户授权时先澄清。重复读取没有增加证据时要换路径或收束。若阻塞来自输入体积，可以投影或压缩后再评估。跨重试保留已读证据和成功回执，并在任务阶段为交付预留调用机会。对额外模型调用评估的同时，App 仍应适用自己的截止时间和费用策略。
