# 普通 handler 与工作流组合对照

[English](harness-handler-comparison.en.md) · [源码](harness-handler-comparison.mjs)

两种写法完成同一确定性任务：准备输入、子模型决定保存、授权工具保存一次、保留回执、草稿格式失败后仅修复交付。使用 Node 22.12+、已有 SDK 产物，在工程根运行：

```sh
node development/examples/harness-handler-comparison.mjs
```

普通 handler 使用现有 ModelRunner、真实父子账本和工具目录，直接书写顺序与解析错误的恢复。推荐写法复用有界 Agent 工作流。对照断言两种交付和实际 Provider 序列相同；均消费四次，额外调用在 Provider 前拒绝；授权拒绝均无保存和修复。没有另造执行引擎、访问网络或使用密钥。

| 决定或保证 | 普通 handler | 工作流组合 |
| --- | --- | --- |
| 父子预算、工具参数和授权 | 复用 Core／Support，不应自行实现 | 同样复用 Core／Support |
| 固定依赖 | 函数装配一次，通过闭包使用 | 工作流与 runtime 绑定一次 |
| 接下来做什么 | 顺序代码与显式错误捕获 | 节点、声明路由、onErrorNodeId |
| 何时接纳子成果 | handler 自己保留回执，确保修复不回写工具 | 子节点返回补丁，由 Engine 接纳，修复路由明确 |
| 执行定位 | 模型与工具事件存在；App 需组织处理阶段 | Engine 提供节点进入、转移、失败和结束事实 |
| 新增负担 | 最短固定任务无需图概念 | 要理解节点、补丁和路由；收益随分支与独立恢复需求体现 |

这个例程不能证明工作流总是更简单，也不证明普通 handler 不可靠。对于短小固定任务，普通函数可以更直接；需要查看执行路径、独立恢复和复用节点时，声明式组织减少 App 自行维护阶段状态的负担。共同预算和授权的收益来自实际 Core／Support，不能把它们全归功于图。

行为对照仅覆盖此处的正常、拒绝与额度路径。取消竞态、诊断去重、持久恢复和并行分别由专门回归验证，不宣称本例已证明两种写法在所有故障下等价。
