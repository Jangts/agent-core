# 延伸阅读导览

前面的指南解决“怎么搭起来”，这个板块解决“搭起来之后怎么判断、怎么维护”。这里的文章不是 API 说明，也不新增合同；它们把已有接口放进真实业务的取舍里，给出可以验证、可以调整的做法。

## 硬约束与软约定

| 类型 | 例子 | 位置 |
| --- | --- | --- |
| 合同 | 预算超限拒绝、未授权不执行、取消传播、来源不可伪造、校验失败抛错 | [API 手册](/manual/api/)与各 Kit 页面 |
| 建议 | 预算取值、切块粒度、候选数量、日志字段、降级顺序、上线检查项 | 本板块 |

软约定不改变权限、预算、取消和输入输出合同。它们不是 SDK 的强制校验，也不应被写成“只要照做就一定正确”。采用前先确认它解决的是你当前真实存在的问题。

## 阅读路径

| 文章 | 解决什么 | 什么时候读 |
| --- | --- | --- |
| [稳健性与恢复](./resilience.md) | 按实际故障和已确认成果决定修复、核对或结束 | 定义第一条业务路径和验收条件时 |
| [MockGPT 离线验证](./mockgpt.md) | 不接真实模型验证协议、工具选择、流式与失败 | 写测试、调工具循环、复现故障 |
| [RAG 资料搭建](./rag.md) | 判断整篇、章节还是切块，并搭出可核验的检索链 | 资料变大、整篇装不下 |
| [检索质量评估](./retrieval-evaluation.md) | 用真实问题判断检索是否真的更好 | 准备引入或调整检索 |
| [配置与软约定](./configuration.md) | 管住不受类型保护的配置、默认值与启动自检 | 项目开始、准备上线 |

| [上线前的软性检查](./production-checklist.md) | 发布前逐项确认证据，而不是凭感觉 | 每次发布前 |

## 一条共同原则

先用真实数据和真实调用判断，再增加机制。每项建议都应能回答三个问题：它解决什么问题、怎么观察它有效、失效时退到哪里。回答不了时，先不要加。

用 [API 手册](/manual/api/)查精确签名、参数和异常。用[示例与参考](/recipes/)按需要守住的行为选择可运行案例。
