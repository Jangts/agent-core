# 按故障和已有成果选择处置

一次请求可能读到了资料、完成了写入，却没发出最终消息。先记下哪一步失败、哪些成果已经确认、请求是否仍有效。把业务结果、解释文案和消息送达分别记录，才能判断恢复还能做什么。[运行请求恢复与取消案例](/manual/examples/resilience/)

## 从失败现场决定下一步

| 已知事实 | 处理 | 要断言的结果 |
| --- | --- | --- |
| 工具拒绝当前授权 | 结束或澄清当前请求。保留权限错误和作用域 | 受限端口调用为零，交付没有受保护字段 |
| 读操作超时，目标和权限仍有效 | 对瞬时故障按原预算和期限有界重试 | 尝试被记账，达到截止时间后停止 |
| 检索不可用，已有部分可核验证据 | 根据可用的授权来源缩小结论。关键词或整篇读取仍须符合权限和输入预算 | 已核对和未核对范围可区分，检索故障保留原分类 |
| 输入过长或模型额度紧张 | 先投影或读取必要章节。按剩余工作决定扩额、澄清或部分交付 | 已用额度与上游预留保留，必要事实可回查 |
| 已确认写入，解释或格式失败 | 使用原回执定向修复。修复不可用时使用程序化收尾 | 业务写入次数保持一，确认结果仍可查 |
| 写入回包丢失 | 按稳定操作身份查询真实回执。保持未知，直到确认已执行或明确未执行 | 核对只读。未知状态下没有再次写入 |
| 用户取消 | 传播取消信号，停止接纳迟到结果 | 取消不会变成成功，已确认回执继续按权限可读 |

只有确定可重放的操作才适用通用重试。网络拒绝、协议错误、期限到达、授权失败和模型输出不合规都应留下各自的诊断原因。模型限流可纳入有界重试，配置或授权错误应进入明确处理。索引未就绪和检索无命中也需要不同结果。[模型协议与生命周期](/manual/api/model-protocols) · [请求恢复合同](/manual/api/reliability)

## 让回执、预算和终态穿过恢复边界

让读取、统计和可验证的计算在程序中完成。确认阶段只接纳实际执行返回的资料与回执，随后把必要字段给模型组织。有新的结果或证据时才增加工作。检查工具和上下文声明是否重复，分别测量输入体积和调用消耗。[预算与上下文案例](/manual/examples) · [检查稳健性](/manual/workflow-development#检查-agent-稳健性)

模型或节点的执行超时应留在其执行范围。外层请求仍有效时，恢复才有机会读取并交付已确认成果。显式取消传播到同一执行链。若连接中断，重新送达通过受授权的请求或消息身份查已有成果。App 负责持久化、跨进程排他和重连处理。取消和网络断开都无法证明外部写入已经回滚。[回执核对](/articles/evidence-and-operation-receipts) · [跨进程审批与恢复](/articles/approval-and-durable-recovery)

## 用不同的证据回答不同的问题

- 用注册图和声明差异核对可能路径与引用。用实际运行记录说明本次为什么走到降级，记录失败阶段、分类、次数、结果状态和耗时。
- 用离线场景注入一次失败，断言结果、路径和读写次数。用分层测试定位节点、工具和业务组合的责任。
- 用模拟供应商验证 HTTP 失败、流中断和终态解析。用真实模型和业务端口分别验证语义、权限、持久写入和重新连接。
