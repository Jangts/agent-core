# 0.3.0 迭代计划复审（草案 v2.1）

现行计划已改名为 [0.2.5 与 0.3.0 迭代计划（草案 v2.3）](agent-core-iteration-plan.md)。本文评审结论及章节引用保留为 v2.1 时点记录，当前范围与取舍以现行计划为准。

日期：2026-11-08。对象：[配置与装配迭代计划（草案 v2.1）](agent-core-iteration-plan.md)。性质：维护评审记录，不是 API 依据，也不表示已进入实施。上一轮结论见 [v1 评估记录](0.3.0-iteration-plan-review.md)，按草案第 10 节保留为历史证据。

## 复审结论

- v1 的主要阻断项已在计划层面得到处理：范围收窄、对象装配先行、实例作用域写入合同、编译条件前置、元数据机制不提前固定、试点以净收益为继续条件。
- 复审结论由“不建议按现稿实施”调整为：**P0 与 P1（对象归一化与聚合装配）可以批准；P2（工具装饰器）可作为受控适配试点；装饰器的公开导出应单独把关；P3（节点、资料）维持后置。**
- 仍存在 6 个需要在 P0 关闭的具体问题，其中 2 个属于设计阻断：`defineAgentCatalog` 命名冲突、`AgentHandle.create` 的请求预算合同。
- 其余问题集中在清单元素类型统一、ModelProfile 与既有 `createModelStrategy` 的关系、节点类式形态的冗余、装饰器公开面缺少真实消费者。

## 2. 仍待解决的问题

### 2.1 `defineAgentCatalog` 命名冲突（P0 阻断）

计划第 3 节已注意到与 Intents Kit 的 `defineAgentCatalog` 重名，但示例仍使用该名称。实际冲突范围比计划描述更大：

- `packages/agent-core/src/kits/intents/catalog.ts` 已导出 `defineAgentCatalog`，语义是“按意图、范围与工具注册投影出任务目录”。
- `packages/agent-core/src/kits/intents/index.ts` 同时以命名导出和 `Intents.defineAgentCatalog` 暴露该函数。
- 再增加一个 `Support.defineAgentCatalog`，同一包内会出现三个同名符号，其中两个语义不同。搜索、补全、文档锚点与错误堆栈都会产生歧义。

建议：在 P0 首项确定新名称，例如 `defineAgentComposition`、`defineAgentAssembly` 或 `defineAgents`；同时核对 `AgentDefinition`、`AgentHandle`、`AgentCatalogPorts` 等既有类型是否还有近名冲突。名称未定之前，不应把示例写进公开文档或生成参考。

### 2.2 `AgentHandle.create` 与请求预算合同（P0 阻断）

第 2 节把句柄定义为“可跨请求复用”，把运行实例定义为“由 create 按请求创建”。这个方向正确，但第 2 节同时要求“不能用反复 create 重置同一请求的预算”，而当前设计没有机制阻止调用方在同一请求内多次 `create`：

- 每次 `create` 都会新建 Engine 与 Runner，各自持有 `maxCalls`、调用计数与 journal。
- 现有 [engine.ts](../../../packages/agent-core/src/execution/engine.ts) 在绑定请求级模型运行时拒绝并发 `run`，但不会识别“同一请求的第二次 create”。
- Banker 当前的 `createBankerRuntime` 每次请求只建一次 Runner，预算共享依赖这一约定；句柄化之后，约定从“装配函数内部”变成“调用方纪律”。

建议在 P0 明确并实现其中一种：

1. `create` 接受请求级 `execution`、既有 `AgentModelRuntime` 或预算端口；同一请求复用同一预算来源。
2. `create` 只允许每请求一次，并由宿主在请求边界持有句柄创建的运行时；SDK 文档明确重复 create 会得到独立预算。
3. 增加轻量运行时守卫：同一 signal 与同一模型运行时下重复创建直接报错。

同时明确：一个 create 结果允许顺序多次 `run` 时，预算是累计还是每次重置；这与现有 Runner 计数语义必须一致。若句柄还提供 `run` 快捷入口，每次调用都会隐式 create，预算重置风险更高；P0 应说明该入口是否允许用于多轮或委派调用。该问题不解决，“不能重置预算”只是描述性承诺。

### 2.3 清单元素类型不统一（中高）

对象写法传入 `{ id, workflow }`，装饰器写法传入类构造器：

```ts
Support.defineAgentCatalog([{ id: 'query', workflow: queryWorkflow }]);
Support.defineAgentCatalog([QueryAgent]);
```

这要求清单在运行时区分“普通对象”和“类构造器”，并在内部走两条归一化分支。它与仓库现有的显式合同风格不一致，也让类型签名变成联合类型。工具侧同样会出现“对象定义 / 类实例 / 工厂函数”的联合。

建议统一为一种描述符：

- 装饰器在类上暴露静态描述符（例如 `QueryAgent.definition`），清单只接收描述符；
- 或提供 `agentOf(QueryAgent)` 之类的小函数，在编译期完成转换，清单元素类型保持单一；
- 工具类同理，清单项统一为 `{ definition, dependencyFactory? }`，避免在装配器内部做 `typeof entry === 'function'` 判断。

计划第 3 节“模块导出单句柄可以作为清单的特例”可以保留，但单句柄与清单应返回同一 `AgentHandle` 类型。

### 2.4 ModelProfile 与 `createModelStrategy` 重叠（中）

`Support.createModelStrategy` 已从模型声明、推理档位、预算档位与显式覆盖生成完整的 `ModelRunnerOptions`（见 [strategies.ts](../../../packages/agent-core/src/support/model/strategies.ts)）。第 5 节的 ModelProfile 目前只写“组织现有配置及显式引用”，没有说明它比 `createModelStrategy` 多解决了什么。

如果 ModelProfile 只是给一组 options 起名字，它属于接口规范中“原样接收字段再换一个对象返回”的壳，应优先复用现有入口。建议二选一：

- 让 `defineModelProfile` 直接返回 `ModelRunnerOptions`，作为 `createModelStrategy` 的命名别名，不新增运行时类型；
- 或删除 ModelProfile，由 Agent 清单直接引用 `createModelStrategy` 的产物。

若确有“按 ID 代指模型配置”的需求，应说明它与现有模型 ID、阶段传输 ID 的关系，避免出现第三套模型引用体系。

### 2.5 节点类式形态与实例共享（中）

两个具体问题：

1. **完整类实例形态冗余。** 第 4.1 节要求类实例完整满足 `WorkflowNode`（含 `id`、`description`、`routes`）。既然实例已经具备全部字段，现有 Core 已经接受类实例，`defineWorkflow({ nodes: [instance] })` 可直接工作；此处的类装饰器只起“标记可适配”的作用，没有减少字段或决定。建议删除该形态，只保留真正需要元数据的 run 方法装饰器形态。
2. **实例共享的并发语义。** 第 2.1 节规定“同一清单内只实例化一次，多个 Agent 复用该实例”。在并发服务中，这意味着多个请求共享同一个 `this`。计划用“只保存稳定依赖、不保存请求状态”约束，但装配器无法验证；同时“稳定依赖”可能是带连接状态的客户端，计划也承认不证明线程安全。
   - 建议默认按运行实例创建节点对象，共享实例作为显式选项；
   - 或要求类节点声明为无状态，并在类型／文档中固定该合同；
   - 明确“同一清单复用”只在依赖与 App 无关时成立；携带 App 专属依赖的清单不应跨 Agent 共享。

### 2.6 装饰器公开导出缺少真实消费者（中高，规范问题）

仓库现有标准要求 Support 的每个保留入口说明场景、生成物、推荐依据与真实消费者（见 `docs/maintenance/plans/plan-b.md` 的 B3 导出复核）。v2.1 第 6 节已确认两个 NestJS 应用不能在同一编译单元使用标准装饰器，P2 又只要求“受控样例”验证装饰器语法。这意味着：

- 装饰器子路径可能以公开 API 的形式发布，但没有任何生产消费者；
- 唯一真实受益者变成“使用标准装饰器编译的第三方”，而当前没有这样的仓库内证据。

建议：

- 对象装配与 Agent 句柄作为公开能力交付；
- 装饰器子路径先以实验性入口存在，不进入根导出、不写入入门文档，待至少一个真实消费者采用后再提升为正式公开面；
- 若决定直接公开，应在 API 手册明确“不支持 NestJS 旧版装饰器编译单元”，并把这一限制写成使用条件，而不是维护计划里的说明。

### 2.7 试点基线混入版本升级（中）

`apps/banker-api` 当前解析到 agent-core `0.1.0`，`apps/server` 为 `0.2.0`。若试点直接把 Banker 升级到包含本次改动的新版本，升级本身会带入 `0.2.0` 的工具调用协议变化（completionPolicy、collector、ProviderMessage 等），净收益测量会把“版本升级影响”和“装配写法影响”混在一起。

建议把 P2 的对照固定在同一版本内：

- 基线：同一版本下 Banker 现有的对象装配；
- 对照一：静态 `definitions` 字段；
- 对照二：类式工具装饰器；
- 版本升级另做一次兼容验证，不计入装配收益。

计划的“不做全端批量版本对齐”可以保留，但试点至少要保证三条对照使用同一 SDK 产物。

### 2.8 生命周期清理缺少具体资源（低）

第 2 节写“结束时清除本次资源引用并执行实际需要的清理”。当前 Engine 与 Runner 不持有外部资源，Provider、客户端与 signal 均由 App 拥有。若没有真实资源需要释放，这句话会诱导新增一个没有实际职责的 dispose 合同。

建议改为：句柄与运行实例不提供额外生命周期；外部资源仍由 App 在创建边界管理。若确有资源所有权，再单列说明所有者、触发时机、异常与取消路径。

### 2.9 空类 Agent 写法（低）

`@agent({...}) class QueryAgent {}` 明确“不创建实例”，仅作元数据载体。空类容易让读者以为会被实例化，也让“类装饰器”与“对象定义”的差别只剩语法。

建议改用对象描述符 `defineAgent({...})`，或在保留装饰器时使用能表达“仅声明”的名称（如 `@agentDefinition`），并在示例中直接说明不会创建实例。

## 3. 修订后的实施建议

### 3.1 阶段闸门

| 阶段 | 建议范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 | 解决命名冲突；确定 create／预算合同；统一清单描述符；明确 ModelProfile 与 createModelStrategy 的关系；确认装饰器公开面策略 | 上述四项有书面结论，示例可编译但暂不进入正式手册 |
| P1 | 对象归一化、Agent 组合清单、AgentHandle、请求级 create | 可独立交付；普通路径比现状更少接线；不改变 Engine／Runner 行为 |
| P2 | Banker 工具链试点：对象、静态 definitions、类式工具三态对照 | 同一版本对照；记录减少的决定与字段；无净收益则停止装饰器扩展 |
| P3 | 节点 run 方法装饰器（仅在该试点有收益时）；资料适配 | 节点图仍集中可读；实例并发语义明确；资料装饰器默认不做 |
| P4 | 兼容、文档、示例、Skill、站点 | 只对已验证范围作结论；装饰器是否公开单独决定 |

### 3.2 P0 检查清单

1. 新名称与 Intents Kit、现有 Agent 类型无冲突。
2. `create` 与请求预算、signal、模型运行时的关系有可执行规则，不是描述性承诺。
3. 清单元素只有一种描述符类型；类与对象的差异在转换边界消失。
4. ModelProfile 能指出比 `createModelStrategy` 多减少的决定；否则删除。
5. 节点类式形态只保留真正需要元数据的一种。
6. 装饰器子路径是否公开、是否要求真实消费者，有明确决定。
7. 元数据收集路径说明“不扫描成员、不提前创建请求实例”如何同时成立。
8. 继承与重复装饰的拒绝规则写入合同。

### 3.3 验收调整

- 保留第 8 节的转换边界测试策略，不再要求五类 × 两种写法的端到端等价。
- 增加“同一请求重复 create 不重置预算”的专项验证；这是新增风险点，现有回归不会覆盖。
- 增加“清单元素类型单一”的类型测试，避免联合类型在装配器内部扩散。
- 试点报告分开记录：字段减少、决定减少、阅读跳转、维护成本；四项中至少两项有正收益才继续。
- 装饰器语法验证与 Nest 对象装配验证分别留证，不互相替代（计划已写入，复审确认保留）。

## 4. 结构化结论

### 4.1 可行性

| 交付 | 可行性 | 说明 |
| --- | --- | --- |
| 对象归一化与 Agent 聚合装配（P1） | 高 | 复用现有定义与注册路径，独立有价值，风险可控 |
| AgentHandle | 中高 | 方向正确，但 create／预算合同必须先闭合 |
| 工具类式装饰器（P2） | 中 | 仅作受控试点；公开导出需真实消费者 |
| 节点 run 方法装饰器 | 中低 | 取决于试点；完整类形态建议删除 |
| 资料装饰器 | 低 | 维持后置，不建议本轮实施 |
| ModelProfile | 低 | 与 `createModelStrategy` 重叠，需证明增量价值或删除 |

### 4.2 风险

| 风险 | 可能性 | 影响 | 处理 |
| --- | --- | --- | --- |
| 同一请求多次 create 重置预算 | 中 | 高 | P0 定义规则并加专项回归 |
| 清单联合类型导致装配器分叉 | 高 | 中 | 统一描述符，转换在装饰器／工厂处完成 |
| 装饰器公开但无真实消费者 | 中 | 中 | 先实验性导出，或明确放宽标准的理由 |
| 节点实例跨请求共享状态 | 中 | 高 | 默认按运行实例创建；共享需显式声明并限无状态 |
| 试点收益被版本升级噪声掩盖 | 高 | 中 | 同版本三态对照 |
| ModelProfile 成为第二套模型配置入口 | 中 | 中 | 复用 `createModelStrategy` 或删除 |
| 空类／标记式装饰器造成理解负担 | 中 | 低 | 改用对象描述符或明确命名 |

### 4.3 建议汇总

1. 批准 P0 与 P1，先交付对象归一化、Agent 组合清单与句柄；不把装饰器作为首批公开能力。
2. 在 P0 首项解决 `defineAgentCatalog` 命名与 `create` 预算合同，两项未闭合不进入 P1 实现。
3. 清单只接收统一描述符；类、对象、工厂的差异在转换层消除。
4. ModelProfile 要么成为 `createModelStrategy` 的命名别名并直接返回 `ModelRunnerOptions`，要么删除。
5. 节点只保留 run 方法装饰器形态；完整类实例形态删除；节点实例默认按运行创建。
6. 装饰器子路径在出现真实消费者前保持实验性；公开面与 Nest 编译限制写入使用文档。
7. P2 试点使用同一 SDK 版本做三态对照，版本升级单独验证，不计入装配收益。

### 4.4 需要决策的事项

1. Agent 组合清单的正式名称，以及是否接受 `defineAgentComposition` 一类的新名称。
2. `create` 是“每请求一次、由宿主持有预算”，还是“接受既有预算端口”；是否允许同一运行实例顺序多次 run。
3. 装饰器子路径是否随本次公开发布，还是等真实消费者出现后再公开。
4. ModelProfile 保留（作为 `createModelStrategy` 别名）还是删除。
5. 节点类式适配是否只保留 run 方法形态；节点实例默认共享还是默认按运行创建。
