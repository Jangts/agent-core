# 0.3.0 迭代计划评估：装饰器定义与装配

现行计划为 [0.2.5 与 0.3.0 迭代计划（草案 v2.3）](agent-core-iteration-plan.md)，意见取舍见其第 5 节。本文保留针对 v1 的评估及其后 v2 时点说明；下文版本与章节引用为当时记录，不构成当前 npm 发布决定或当前章节导航。

日期：2026-11-08。对象：0.3.0 迭代计划 v1 草案（同一文件现已更新为 v2）。性质：维护评审记录，不是 API 使用依据，也不表示已进入实施。

本记录评审的是 v1 草案。v2 已采纳“装饰器 + 显式清单 → Agent 句柄 → 请求级运行时”的方案，并确定标准／旧版装饰器的处理方式及装饰类实例按 `create` 创建；节点装饰器只注册，支持实现 `Node` 接口的类与 `run` 方法，由 Workflow 显式挂载，普通对象和数组仍走显式定义入口。下文“需要决策的事项”保留为当时评审记录，现行计划以 [v2](agent-core-iteration-plan.md) 为准。

## 结论摘要

- 计划边界写得克制：Core 不识别装饰器、不引入自动扫描、不建立 DI 容器，方向本身没有破坏 Core／Support／Kit 分层。
- 但五个模块的收益高度不均：工具与 Agent 组合有可感知价值，节点有限，资料与 ModelRunner 基本只是写法替换。
- 客户端四端没有直接收益：`banker-web`、`web-admin`、`ai-admin` 不依赖 `@jangts/agent-core`；`cafe` 只使用 `/kits/interaction` 与 `/sse`，不属于本次五类定义。
- 两个真实服务端消费者都使用 NestJS 的旧版装饰器编译条件，而 SDK 自身按新版语义编译。计划把“是否支持旧版装饰器”留作待定项，但它实际是前置否决项。
- 按现稿直接实施不建议。建议改写为“定义归一化优先、类式书写后置、工具与 Agent 先试点”的分阶段方案。

## 1. 功能模块的分端受益清单

### 1.1 受益程度口径

| 程度 | 判定标准 |
| --- | --- |
| 高 | 该端可直接使用，并实质减少需要作出的决定或重复配置 |
| 中 | 有可感知收益，但需要额外装配、实例生命周期或仅覆盖部分场景 |
| 低 | 主要是写法变化，配置项和决定基本不变 |
| 无 | 该端不消费该定义，或本次范围不覆盖其真实入口 |

### 1.2 节点

计划覆盖节点方法、状态前置／产出、路由、轮次边界及错误出口，但明确“节点顺序、入口和路由优先级通过显式配置表达，不依赖方法扫描”。因此顺序、入口和路由仍要写在集中清单里。

| 端 | 受益 | 说明 |
| --- | --- | --- |
| 客户端 | 无 | 四个前端都不定义 Workflow；`cafe` 的交互契约属于 Interaction Kit，不是节点定义 |
| 服务端 | 低 | 小可乐的 `run/catalog.ts` 目前把整张图、路由优先级与 handler 入口集中在一屏内；装饰器会把 `run` 移入类方法，清单只剩 id 与路由，读者需要往返跳转，和该文件“执行顺序与分支优先级集中在此”的目标相反。Banker 的委派与问候流程也以普通对象为主 |
| SDK | 中低 | 对第三方可以“节点即方法”，但 id、description、requires、provides、routes、错误出口仍要写，减少的主要是元数据与实现的物理距离 |

判断：收益集中在“就近书写”，不减少图结构本身需要的决定。对已经用单一 catalog 表达流程的两个服务端，净收益可能为负。

### 1.3 工具

工具是五类中字段最多、同源关系最强的一类：模型说明、输入 schema、授权、执行、输出检查需要保持一致。

| 端 | 受益 | 说明 |
| --- | --- | --- |
| 客户端 | 无 | `cafe` 的 `action-contracts.ts` 使用 `defineInteractionProtocol` 声明聊天操作契约，归 Interaction Kit；本次计划不覆盖 |
| 服务端 | 中 | Banker 工具数量最多，`defineToolCatalog` 已集中声明并生成模型能力；但当前 handler 是 `(input, context)` 纯函数，请求级 `bind({ app })` 注入上下文。改成类方法后要回答实例作用域问题，见 2.6 |
| SDK | 中高 | 同源声明收益最大，第三方最容易感知；但 `defineTool` 已经完成 schema 快照、handler 绑定和授权结果检查，装饰器只改变书写位置，不改变合同 |

判断：五类中最值得做的一类，但前提是解决“类实例 vs 请求级 app”的关系，否则会把纯函数装配改成需要工厂的实例装配。

### 1.4 资料

| 端 | 受益 | 说明 |
| --- | --- | --- |
| 客户端 | 无 | 前端不声明上下文片段 |
| 服务端 | 低 | `defineContextFragments` 已经是自描述声明：`id`、`sourceId`、`trust`、`lifetime`、`maxChars`、`format` 均在定义内。装饰器无法再省字段；动态加载与检索本来就在 Kit |
| SDK | 低 | 只会把“配置对象”换成“装饰器 + 配置”，概念数增加而字段数不变。计划已设边界防止把资料全部静态 prompt 化，这是必要的，但也说明该模块的装饰器收益最低 |

判断：不做，或推迟到归一化层证明有公共收益之后再考虑。

### 1.5 Agent

| 端 | 受益 | 说明 |
| --- | --- | --- |
| 客户端 | 无 | 四端不装配 Agent |
| 服务端 | 低到中 | 真正的装配发生在每请求的 `createBankerRuntime`：`signal`、`provider`、额度、诊断都来自本次请求。装饰器只能描述静态组合，无法替代这段装配。可读性上可以把“这个 Agent 由哪些定义组成”写成一个类，但集中清单同样能做到 |
| SDK | 中 | “组合声明”比“组合实现”更清晰，对第三方是真实的可读性收益；但仍需显式清单，且必须保留既有 Engine 身份与运行入口 |

判断：作为“聚合清单 + 装配入口”的对象式 API 更有价值；类装饰器只是它的可选外壳。

### 1.6 ModelRunner

| 端 | 受益 | 说明 |
| --- | --- | --- |
| 客户端 | 无 | 前端不创建 Runner |
| 服务端 | 低 | Banker 的 `maxCalls`、超时、`signal`、`provider`、传输集合都由配置与请求决定；小可乐的阶段 Runner 同理。把这类值写成类级元数据，容易把请求级配置冻结成模块级常量 |
| SDK | 低且风险偏高 | 计划自己写明“可复用模型定义不等于共享 Runner 实例”。这说明装饰器描述的是模板，与现有 options 工厂／`createModelStrategy` 的差别很小，却新增了作用域与继承语义 |

判断：建议不做装饰器形式，改为“命名的模型配置档”（返回普通 `ModelRunnerOptions`）即可满足复用诉求。

### 1.7 汇总

| 模块 | 客户端 | 服务端 | SDK | 建议 |
| --- | --- | --- | --- | --- |
| 节点 | 无 | 低 | 中低 | 试点后再定 |
| 工具 | 无 | 中 | 中高 | 优先 |
| 资料 | 无 | 低 | 低 | 不做或后置 |
| Agent | 无 | 低到中 | 中 | 次优先，用对象式清单 |
| ModelRunner | 无 | 低 | 低且风险高 | 不做装饰器 |

一句话：这是 SDK 书写层的 DX 优化，不是跨端能力建设。客户端不会因此受益，服务端只在工具与 Agent 组合上有限受益。

## 2. 对现有开发路径的影响

### 2.1 正向影响

1. **定义与实现就近。** 对工具最明显：schema、授权、执行、输出检查可以和方法放在同一处，减少跨文件查找。
2. **有可能收敛内部重复。** 五类 `define*` 目前各自做 id 非空、重复检查、handler 绑定等相近校验。若先提取内部归一化，可减少 Support 内部重复；这是真实收益，但不依赖装饰器语法。
3. **保留显式清单。** 不依赖方法扫描或导入顺序，节点顺序、路由优先级仍可审计，符合现有 Workflow 的可检查性。
4. **降低第三方上手门槛。** 对熟悉 NestJS／TypeORM 的开发者，类与装饰器是熟悉的组织方式，可能提升 SDK 采用率。

### 2.2 业务逻辑清晰度

- 正向：单个工具或节点的“定义 + 实现”更紧凑，减少“这个 schema 属于哪个 handler”的查找成本。
- 负向：同一业务出现两套写法。仓库的接口规范要求“同一入口由简入繁”，并明确反对“先用一套极简 DSL，遇到真实业务再要求使用者重新学习另一套编排方式”。装饰器不是现有对象写法的渐进扩展，而是平行入口；手册、示例、Skill、站点都必须同时教两种写法，长期会分散“首选写法”的共识。
- 负向：流程图被拆成“清单里的顺序与路由 + 类里的处理逻辑”。小可乐当前的单文件图是可整体阅读的；拆分后，评审者需要同时打开清单和类，理解成本上升。
- 负向：验收要求“同一业务两种写法行为等价”。这会把 5 类定义 × 2 种形态的回归面翻倍，而现有 SDK 回归已是 464 项量级，新增等价性测试的维护成本高于收益。

### 2.3 模块边界划分

- 计划坚持 Core 不反向依赖 Support、Kit 保留局部语义，这条边界是对的。
- 但“元数据收集 + 显式清单 + 归一化 + 装配检查”本身是一套新的子层，实质上接近一个轻量定义容器。计划禁止自动扫描与通用 DI，能压住扩张；一旦为了支持类方法而引入实例工厂、生命周期钩子或依赖解析，就会继续向 DI 容器漂移。
- Kit 完全不在本次范围内。而 Banker 与小可乐真正的业务复杂度集中在 Knowledge、Answering、Presentation、Intents、Tools 等 Kit 链路。也就是说，本次优化的是最薄的一层（静态定义声明），不是最复杂的一层。
- 资料装饰器虽然被限定为“不自动取得读取权限”，但它仍会把“资料来源、信任、生命周期”与“实现方法”放在同一个类里。对隐私与权限边界敏感的模块，元数据集中反而增加了误读风险：读者容易把“声明了来源”理解为“已经获得读取授权”。

### 2.4 协作效率

- 短期：同一版本要同时改 SDK、两个后端、文档、示例、Skill、站点与公开参考，且两个后端的依赖版本当前分别锁在 0.1.0 与 0.2.0，0.3.0 需要一次跨端升级与重新验证。`cafe` 只消费 Kit 与 SSE，升级无功能收益，却会增加验证面。
- 中期：如果“不强制迁移”，两种写法会长期并存。代码评审需要判断“这段为什么用装饰器、那段为什么用对象”，但两者没有语义差异，评审无法从合同上区分，只能接受风格差异。
- 长期：继承、重复装饰、成员覆盖、配置合并、元数据收集时机都会成为公开兼容面。计划把这些列为待定项是诚实的，但它们不是实现细节，而是使用者可见的语义。

### 2.5 后续迭代扩展性

- 正向：一个稳定的 `DefinitionDescriptor` 归一化层，可以被未来的定义类型复用，也能让文档生成、引用检查、模型投影共享同一来源。
- 负向：装饰器语法一旦公开，后续任何“在装饰器里顺手做点事”的诉求都会有压力，例如包装方法、注入依赖、根据类名推导 id。这些都会削弱 Core 现有的“执行顺序与保证只由 Core 拥有”的清晰性，需要在规范里明确禁止。
- 负向：TypeScript 新旧装饰器两套语义会成为长期测试矩阵。即便首期只支持新版，也必须长期声明“不支持旧版”，并承担第三方在 NestJS 项目中无法直接使用的解释成本。

### 2.6 两个硬约束

#### 2.6.1 TypeScript 装饰器语义与消费者编译条件

- `packages/agent-core/tsconfig.json` 未开启 `experimentalDecorators`，即按 TypeScript 新版（Stage 3）装饰器语义编译。
- `apps/server/tsconfig.json` 与 `apps/banker-api/tsconfig.json` 均开启 `experimentalDecorators: true` 与 `emitDecoratorMetadata: true`，这是 NestJS 的旧版语义。
- 同一个装饰器函数在两种语义下接收的参数不同：旧版是 `(target, propertyKey, descriptor)`，新版是 `(value, context)`。因此“SDK 导出一个装饰器，两个后端直接在源码里使用”默认不成立，除非实现双参数兼容并在两端分别验证。
- 计划把“是否支持旧版装饰器另行决定”放在第 5 节待定项，但它不是普通的待定项：它决定 P4 能否用 Banker 与小可乐做真实接入验证。如果只支持新版，P4 只能退化为独立示例或非 Nest 模块，验证价值明显下降。
- 计划明确不依赖参数装饰器、`emitDecoratorMetadata` 和自动类型反射，这是正确的保守选择；但也意味着 schema、id、description 仍需手写，“减少重复配置”的收益主要来自就近书写，而不是字段数量。

#### 2.6.2 实例作用域与请求级依赖

- 装饰器落在方法上，装配时必须有一个实例。当前 Banker 工具是纯函数 + 请求级 `bind({ app })`；小可乐节点通过 `context.app` 调用运行时方法。两者都不需要“定义类实例”。
- 引入类方法后必须回答：实例是模块级单例、每请求工厂，还是只允许无状态单例？
  - 模块级单例与计划自身“不隐式把 App handler 变成全局单例”冲突。
  - 每请求工厂会新增一个生命周期概念，并需要定义并发、取消与私有状态的边界，已经超出“装饰器只记录元数据”的轻量定位。
- 这个问题必须在 P0 解决，否则 P1 的归一化结果无法可靠映射到现有注册器和构造器。计划把它放在第 4 节“实例复用与并发安全责任须明确”，位置正确，但需要提升为前置决策，而不是实施期再定。

### 2.7 小结

正向收益集中在书写体验与内部校验收敛；负向影响集中在概念数量、文档与回归成本、图的可读性、以及 TS 语义和实例生命周期的长期约束。对当前已经完成 A／B／C／D 的 SDK 来说，这更像一次“可选的开发者体验升级”，而不是能力缺口修复。

## 3. 优化调整提议

### 3.1 重新定位交付物：归一化优先，装饰器后置

把原计划拆成两个独立交付：

| 交付 | 内容 | 是否新增公开语法 |
| --- | --- | --- |
| 0.3.0 定义归一化与显式装配 | 内部 `DefinitionDescriptor`、`normalize`、`validateReferences`、`assemble`；五类 `define*` 复用同一校验；提供一个对象式聚合入口（例如 `defineAgentAssembly({ nodes, tools, fragments, model })`），输出仍交给现有 Engine／Runner／注册器 | 否 |
| 0.4.0 类式书写适配（可选） | 装饰器作为归一化层的薄语法糖，放在独立子路径，先只覆盖工具，再评估 Agent | 是 |

这样做的好处：

- 归一化层独立有价值，即使装饰器最终被否决，也不会浪费。
- 装饰器的前置决策（旧版语义、实例作用域）可以在不阻塞主版本的情况下单独验证。
- 公开面先不增加，文档不必同时教两种写法。

### 3.2 优先级重排

| 新顺序 | 内容 | 理由 | 停止条件 |
| --- | --- | --- | --- |
| 1 | 工具定义归一化 + 引用检查 | 字段最多、同源关系最强、两端都有真实消费者 | 若无法在 Banker 工具链上减少实际决定或重复，停止 |
| 2 | Agent 组合清单（对象式） | 提升“由哪些定义组成”的可读性，不引入类实例问题 | 若清单只是把现有装配换个位置，停止 |
| 3 | 节点（试点后再定） | 顺序与路由仍需清单，收益不确定 | 若小可乐图的可读性下降或无实质减配，停止 |
| 4 | 资料 | 现有 `defineContextFragments` 已声明式 | 不建议进入实施 |
| 5 | ModelRunner | 请求级配置不应写成类级常量 | 不做装饰器；如需复用，提供返回普通 options 的配置档 |

相对于原计划的 P2／P3（节点与工具同批、资料与模型同批），建议把工具与 Agent 提前，把资料与 ModelRunner 移出本轮。

### 3.3 模块拆分与合并建议

- **新增内部目录** `src/support/definition/`，只做归一化、引用校验和装配错误，不新增执行机制；五类公开 `define*` 改为调用同一内部实现。
- **装饰器独立子路径**（例如 `support/decorators`），不进入根导出，避免 Core-only 用户承担加载成本，也避免与既有 `ModelRunner`、`AgentCoreEngine` 构造器混淆。
- **每类一个装饰器，不做通用 `@Definition`。** 通用装饰器会迫使五类共享一个 options 袋，最终变成需要解释的 DSL。
- **不合并公开入口。** `defineTool`、`defineWorkflow`、`defineContextFragments` 仍是唯一公开合同；装饰器只产出相同的普通定义，不产出第二种运行格式。
- **Core 零改动。** 不在 Core 增加装饰器识别、元数据读取或新的装配钩子。

### 3.4 依赖与构建优化

- 不引入 `reflect-metadata`，不依赖 `emitDecoratorMetadata`，不新增运行时依赖。
- 元数据存储使用以构造函数为键的 `WeakMap` 或新版装饰器的 `context.metadata`，不使用模块级全局注册表。
- 必须验证双格式单实例：应用可能通过 `require` 加载 CJS 入口、通过 `import` 加载 ESM 入口；如果两套模块实例各自持有 WeakMap，会出现“装饰器写了、清单读不到”的问题。这是双包危害，必须在验收中单列。
- 保持 `sideEffects: false`。装饰器在类定义时写元数据属于模块求值副作用，需要验证打包器不会因为只看副作用而丢弃仅被清单引用的类。
- 不把维护计划、评审记录或站点源码加入 SDK 分发白名单。

### 3.5 兼容与发布路径

- 先明确结论：两个 NestJS 应用能否在源码内直接使用。如果不能，就不要在计划里承诺“用 Banker 与小可乐验证”。
- 若坚持新版语义，则把适用范围写清楚：“仅适用于新版装饰器编译的消费者”，并提供等价的普通对象／静态字段写法；不要把 NestJS 场景写成已支持。
- 若要覆盖两个后端，需实现双参数兼容装饰器，并分别在两套 tsconfig 下做编译与运行验证；这会显著增加维护面，应作为独立决策。
- 发布协调：当前 `apps/banker-api` 与 `apps/cafe` 锁定 `0.1.0`，`apps/server` 锁定 `0.2.0`，SDK 为 `0.2.1`。任何 0.3.0 试点都要先完成版本对齐；`cafe` 无直接收益，建议排除在试点外。

### 3.6 验收指标调整

- 用“减少的决定与字段”衡量，而不是代码行数。每条真实调用链至少列出一项被删掉的决定，并说明由哪个既有合同接管。
- 等价性测试放在归一化描述层做一次，不要为五类 × 两种写法重复端到端用例。
- 只选一条真实链路试点：建议 Banker 工具目录（数量最多、同源字段最多），通过后再评估小可乐工作流。
- 文档只保留一条主路径。装饰器若保留，作为进阶可选项，并明确限制（实例作用域、编译条件、继承规则）；不新增“两种写法对照”的入门章节。
- 增加三条专项验证：旧版／新版装饰器编译、ESM／CJS 元数据单实例、请求级依赖不被冻结到类级元数据。

### 3.7 可优先考虑的替代写法

如果目标是“定义与实现就近”，不引入装饰器也能做到：

```ts
export class ServiceTools {
  static readonly definitions = [
    defineTool({
      id: 'lookup_service',
      kind: 'query',
      description: '查询服务状态',
      inputSchema,
      authorize(input, context) {
        /* ... */
      },
      execute(input, context) {
        /* ... */
      },
      parseOutput(value) {
        /* ... */
      },
    }),
  ] as const;
}
```

- 静态字段在两种装饰器配置下都能工作，不改变 TS 语义。
- 不引入实例生命周期问题，仍然可以按请求 `bind({ app })`。
- IDE 跳转、类型推导和现有 `defineToolCatalog` 完全兼容。

如果目标是“一个 Agent 由哪些定义组成”，对象式聚合入口比类装饰器更直接，也更符合“同一入口由简入繁”的规范。

## 4. 结构化评估结论

### 4.1 可行性判断

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 归一化与显式装配 | 可行性高 | 复用现有定义与注册路径，不改变执行机制，内部收益明确 |
| 装饰器语法 | 可行性中低 | 受 TS 新旧语义、实例作用域、双包元数据和文档成本约束 |
| 客户端价值 | 无直接价值 | 四端不消费五类定义；`cafe` 仅使用 Kit／SSE |
| 服务端价值 | 有限 | 工具与 Agent 组合有可感知收益；节点、资料、Runner 收益低 |
| 需求必要性 | 低到中 | 不解决任何已记录的能力缺口，属于 DX 优化 |
| 总体 | 有条件可行 | 建议调整范围与顺序后再实施，不建议按现稿直接推进 |

### 4.2 风险清单

| 风险 | 可能性 | 影响 | 缓解建议 |
| --- | --- | --- | --- |
| SDK 新版装饰器与 NestJS 旧版语义不兼容 | 高 | 高 | 决策前置；要么双参数兼容并双端验证，要么明确不支持并调整 P4 |
| 两套写法长期并存，评审与文档分裂 | 高 | 高 | 不新增公开语法；若保留，只作为进阶可选项并限定范围 |
| 类实例作用域未定义，状态跨请求泄漏 | 中 | 高 | P0 明确单例／工厂／无状态三种模式，并写入合同 |
| ESM／CJS 双模块实例导致元数据丢失 | 中 | 高 | 单实例验证；元数据键与加载入口解耦 |
| 请求级配置被写成类级常量 | 中 | 高 | ModelRunner 与 Provider 不做装饰器；运行资源仍从创建边界传入 |
| 继承、重复装饰、成员覆盖语义成为长期兼容面 | 中 | 中 | 首期禁止继承合并，重复装饰直接报错 |
| 公开 API、文档、测试矩阵膨胀 | 高 | 中 | 只覆盖工具与 Agent；等价性测试放在归一化层 |
| 小可乐工作流可读性下降 | 中 | 中 | 节点不进首批；图与 handler 的集中阅读方式保持不变 |
| 与 R1 图形、过程事件缺口争夺资源 | 中 | 中 | 0.3.0 只做归一化；装饰器作为独立可选版本 |
| 消费者版本落后导致试点失真 | 高 | 中 | 先对齐版本；`cafe` 排除；只选 Banker 一条链路 |

### 4.3 建议汇总

1. 把 0.3.0 的目标从“提供装饰器写法”改为“统一五类定义的归一化与显式装配”；装饰器降级为可选适配层。
2. 优先级改为：工具 → Agent 组合 → 节点（试点后定）→ 资料／ModelRunner（本轮不做）。
3. 装饰器如保留，放入独立子路径，不进入根导出；每类一个装饰器，不做通用容器，不做自动扫描。
4. 先回答两个前置问题：两个 NestJS 应用是否必须支持；类实例采用何种作用域。两者未定之前不进入 P1。
5. 用 Banker 工具链做唯一试点，以“减少的决定与字段”验收；没有可量化减配就停止，不扩展到五类。
6. 保持 Core 零改动、Kit 不参与、无新增运行时依赖，并单列双格式单实例验证。

### 4.4 需要决策的事项

1. 0.3.0 的首要目标是“减少重复配置”，还是“提供类式写法”？两者取舍不同。
2. 两个 NestJS 应用是否必须能在自身源码中直接使用装饰器？这决定新版／旧版语义路线。
3. 是否接受 0.3.0 不交付装饰器语法，仅交付归一化与聚合装配？
4. 类实例采用模块级单例、每请求工厂，还是只允许无状态单例？
5. 试点只做 Banker 工具，还是同时改小可乐工作流？
