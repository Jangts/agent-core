# Agent Core 0.6.0 迭代计划

日期：2026-11-12。状态：已实施核心改动，应用基线失败已关闭，发布前检查尚待执行；详见实施验收记录。目标版本基于本地包版本 0.5.1，暂定 0.6.0；最终是否需要次版本升级，取决于 Runner 扩展合同和兼容性评估。

具体任务、依赖和完成条件见[执行清单](0.6.0-execution-checklist.md)。

## 目标与依据

下一版本以可靠性、执行归属和接入简化为主线。Core、Support、Kit 的现有责任关系继续保留：Core 维护通用执行保证，Support 下沉接线与生成规则，Kit 提供 App 自选能力。没有证据支持更换整套执行框架。

本计划依据当前工作区源码、两端接入方式和本轮全范围审查。审查盘点 225 个 TypeScript 文件；确认公共授权组合、共享 Runner 子类状态、异步 token 计数器拒绝及检索键碰撞四类缺陷。上一轮 889 项回归通过，没有覆盖这些新增复现场景。一次性原始证据保留于根 `.tmp/agent-core-review/`；正式回归应独立表达触发条件，不依赖该临时目录。

期望交付效果：

- 授权、取消、预算和同步解析在全部入口保持相同保证。
- 定义、实例内存与请求执行的归属明确；不依靠隐式“当前请求”。
- 普通对象、真实子类、装饰器及池读取最终消费同一运行合同。
- 新增工具、模型传输或上下文策略主要通过现有参数和清单完成，不复制候选选择、会话接线或生命周期分发。

## 必须先确定的 Runner 合同

现实现为每次 execution 创建基础 Runner，再将覆写方法转发回共享子类。这样保留了私有字段的真实接收者，却让覆写方法中的 `this.callCount`、journal 和 signal 读取共享宿主状态，与真正执行调用的绑定对象分离。

这不是简单替换一段转发代码能解决的问题。一个共享对象在两个并发 execution 中，裸 `this.callCount` 没有执行参数，无法唯一确定应读取哪次调用。用一个可变字段保存“当前 execution”会串请求；复制原型不能复制 JavaScript 私有字段；重新构造子类又会改变单次初始化和共享内存的合同。

**推荐评估方向：继续使用已有 execution 明确执行归属。** 共享子类保存固定依赖及有意共享的内存；覆写方法通过已有请求参数取得 execution，并从该 execution 对应的绑定读取统计、journal 和取消状态。Engine 与 Support 负责补齐 execution，应用不逐层手动接线。不得把共享实例的裸统计属性描述为本次请求统计。

这仍是待验证方案，不直接宣布为最终 API。先实现最小设计样例，验证以下情形，再选择实现和版本范围：

1. 两个并发 execution 使用同一子类、私有字段和 Provider，执行统计及取消各自正确。
2. 覆写 invoke／prepare／createChild 调用 super 后，能通过同一既有 execution 读取真正执行的状态。
3. 请求绑定对象与原始输入 execution 的关系稳定，不靠再次绑定重置预算。
4. 原请求级构造保持累计次数、祖先预留和并发保护；共享工具内存不被误当成请求状态。
5. ESM／CJS、浏览器可用入口及真实子类均成立，不依赖 Node 专属异步上下文存储。

如果必须保留“覆写方法内无参数读取 this 的请求属性”，则应明确改变实例生命周期，并重新评估初始化、副作用和私有内存共享；不能同时承诺共享同一实例、任意并发以及无参数属性自动隔离。该选择在进入正式实现前必须闭合。

## 迭代范围与优先级

| 编号 | 优先级 | 工作项 | 解决的问题 | 交付与验收 |
| --- | --- | --- | --- | --- |
| R1 | 必须 | 修复 toolbox 公共授权组合 | 公共 false／非 void 结果被丢弃，工具继续执行 | 公共和单项检查分别复用 assertion 合同；顺序、取消及同步／异步工具行为均有回归 |
| R2 | 必须 | 收敛 Runner 执行归属 | 方法在共享宿主、状态在基础绑定对象，继承行为不一致 | 完成上述设计验证；公开统计、signal、journal、预备调用及子调用都具有明确 execution 归属 |
| R3 | 必须 | 统一 token 计数同步边界 | 异步计数器的拒绝未消费，产生 unhandledRejection | countModelInput 复用 synchronous；prepare.measure 和 invoke 都拒绝异步结果且无未处理拒绝 |
| R4 | 必须 | 明确并修复检索键值域 | Date、嵌套 undefined／函数、非有限数产生碰撞 | 按声明的值域逐层处理；无法稳定表示的值明确拒绝，不误判成另一个查询 |
| O1 | 应做 | 统一组合入口的边界检查 | 多个包装层容易丢弃结果、接收者或取消检查 | 盘点 Core／Support／装饰器／Kit 的共同处理路径，仅抽取真实重复机制，保留原错误优先级 |
| O2 | 应做 | 补齐声明到执行的类型关系 | toolbox 当前输入输出大量通过 any 和池读取泛型表达 | 先补严格正反类型用例；尽量从已有编译器、parser和同名方法推断，不增加第二份类型／schema清单 |
| O3 | 应做 | 简化调用方接线 | 模型选择、阶段准备和上下文处理有重复接入风险 | 对照 Banker／Microcola 的同类代码，固定关系交给现有绑定端口推导；只下沉可复用机制 |
| O4 | 条件纳入 | 复用稳定 schema 与准备结果 | 编译已复用，但快照、冻结、计量可能仍有重复工作 | 先区分静态定义和动态输入；以工作量断言确认重复，再决定是否修改；不默认缓存动态 transport |

“必须”指本版本退出条件；“应做”需通过具体代码和收益评估，不要求为凑齐清单新增抽象。“条件纳入”没有证据时保留现实现，不制造性能承诺。

### R1：授权和取消的复用

重点位置：`src/support/decorators/toolbox.ts`、`src/capabilities/tool-runtime.ts`、`src/utils/synchronous.ts`、`src/utils/cancellation.ts`。

- 公共授权成功后再执行单项授权，任何非 void 结果都拒绝，包括异步解析出的 false、true、null。
- 公共授权抛错后，不执行单项授权和工具；公共授权等待期间取消后，即使其稍后完成，也不再进入单项检查。
- 不把原可同步工具强制改成异步，不新增独立授权链协议。
- 普通定义、装饰器定义及 toolbox 使用相同正反样例验证。

### R3／R4：异常与查询身份

计数器覆盖同步非负安全整数、负数、小数、非有限数、同步抛错、已拒绝 Promise 和普通 thenable。验证拒绝被消费，以及预算和 Provider I/O 没有被错误推进。

查询键建议默认限定为可稳定表达的 JSON 数据；Date 若要支持，应作为明确规则处理，否则直接拒绝。嵌套 undefined 的选择须与应用可选字段用法核对，不能静默更改去重意义。对象键顺序不影响身份，数组顺序影响身份；循环、稀疏数组、函数、symbol、非有限数及自定义对象均纳入边界验证。两个不同查询不得仅因序列化丢值而共用 seen 记录。

### O1／O2：可优化的组织与类型

较大的 Engine、Runner、Tools 和 context processing 文件是检查入口，不以行数直接作为拆分理由。优先拆清生命周期、配置快照、执行状态、校验与交付的真实归属；不把同一大函数原样搬家，不以大量小函数掩盖顺序。

toolbox 继续保持：options 声明元信息，inputSchemas 只含 JSON Schema，ParseInput／ParseOutput 挂方法，Authorize 复用组内检查。类型增强必须服从这套写法；不能为获得类型推断要求再写一套 schema、ID或handler映射。若JSON Schema与类方法签名无法静态证明一致，应明确运行时校验边界，不能用类型断言伪装保证。

### O3／O4：复杂度下沉与性能

对照两端至少核对模型接入、上下文准备和工具会话三个场景。App 继续拥有资源权限、业务事实、提示词和副作用；Core 不按 Banker／Microcola 的业务名称分支。

优化只围绕可确认的重复编译、快照、序列化和全量扫描。共享的是稳定定义及其准备快照；用户输入、权限结果、动态候选、收集器和运行统计保持 execution 归属。输出 collectors 继续逐调用创建。不得以跳过 schema 快照、输入审计或解析换取速度。

## 可拓展方向

以下是已有合同能承接的增长方向，不全部承诺在 0.6.0 新增 API：

| 方向 | 沿用的扩展点 | 允许扩展的内容 | 纳入条件 |
| --- | --- | --- | --- |
| 更多工具组 | toolbox、toolPool、ToolDefinition | 共用服务依赖和有意共享的内存；不同输入解析及授权检查 | R1、R2闭合后，用一个真实应用工具组验证接入收益 |
| 更多模型／供应方 | ChatProvider、ModelTransportDefinition、现有options及completion policy | 新wire适配、采样配置和响应合同 | 有明确供应方需求；不按模型名称在Core猜行为 |
| 更多上下文策略 | fragment、ContextPlan、普通节点和既有处理端口 | 更合适的历史分组、裁切和压缩策略 | 有两端实际场景；继续保留信任、字符／token预算与原问题保护 |
| 更强的会话工具组合 | 现有session response与工具runtime.invoke | 多个提案的逐项校验、执行和回执关联 | App明确副作用顺序和失败策略；不把模型提出并行等同于执行并行 |
| 更完整的故障诊断 | 既有CoreEvent、invocation、execution.observe | 授权／解析／计量／执行阶段的错误归属和可核对回执 | 现有字段不足的具体证据；不另建日志或trace协议 |
| 长任务和资料能力 | 既有Durable、Family、Knowledge及存储端口 | 更完整的恢复与对账场景 | App提供真实排他、CAS和幂等保证；不能由Core伪造事务或授权 |

优先扩展使用场景和测试矩阵，再考虑新增入口。没有真实消费者时，不预建插件发现、自动 DI、通用工作流装饰器、全局会话总线或自动重试框架。

## 执行顺序与阶段门槛

1. **固定失败回归与设计验证。** 将四项临时复现转换为正式失败回归；先确定Runner可实现的执行读取合同，评估兼容性。此阶段不承诺设计已经解决。
2. **修复共同边界。** 完成R1、R3、R4；确认同类组合入口没有相同遗漏。Runner按验证结论完成R2，避免补丁式逐方法转发。
3. **两端接入收敛。** 核对并按需调整Banker与Microcola实际调用；完成O1—O3中有证据的部分。两端保留原请求预算、取消、鉴权及最终返回合同。
4. **可证明的复用优化。** 评估O4，不满足收益条件则不改。扩展方向最多选取有真实需求的一项作为接入样例，不同时铺开多个新能力。
5. **同步与验收。** 同步公开类型、英文／中文手册、README、示例、App Skill与网站来源；由源码生成API参考。过程和兼容迁移说明独立留在维护记录。

R1、R3、R4在逻辑上可独立修复；R2是本次结构调整的关键依赖。若R2需要较长设计周期，可另行评估先发布0.5.2安全修复包，但不通过把Runner限制写进文档就宣称F2已修复，也不复用已发布版本号。

## 验证与发布退出条件

| 验证层次 | 必须证据 |
| --- | --- |
| 缺陷关闭 | 四项失败回归在修复前成立、修复后通过；有同入口和相邻入口的负例 |
| 生命周期 | 两请求并发、同请求累计、单次取消、失败后复用、预备句柄归属／单次消费、子调用祖先预留均正确 |
| 扩展方式 | 普通对象、真实子类、标准装饰器、池读取、直接调用和Engine接入结果一致；私有字段和方法接收者有真实样例 |
| 类型与公开面 | 严格正反类型测试、ESM／CJS公开入口及实例接入通过；不靠any扩大合同 |
| 应用验证 | 按受影响范围执行Banker与Microcola离线回归；发生接入修改时检查两端类型，明确真实模型未验证的边界 |
| 资源与性能 | 没有未处理Promise拒绝；有必要的取消清理和工作量断言。无专用环境时不做吞吐、延迟或容量结论 |
| 文档与包体 | 正式文档只描述最终合同；示例可执行；npm发布前按公开包规范检查README、元数据及最终tarball |
| 构建协调 | 使用根build:packages；在稳定产物下运行回归，协调构建锁，受并行重建干扰的结果作废 |

不预设新的测试数量或覆盖率数字作为成功标准。完整Core回归在关键实现和接入稳定后执行一次；只有新修改、失败或未决疑问才扩大或重复检查。修复后更新独立验收记录，不把检查结果写进正式API正文。

当前任务只拟定计划。修改生产实现、调整版本号、npm发布、文档站部署和应用部署均未执行；发布时按当次授权与对应Skill执行。
