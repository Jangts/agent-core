# Agent Core 开发范式与应用整改计划

本文是实施计划与交接入口，不是公开 API 合同。任务状态以各工作流的实施记录和实际修改为准，不将计划中的能力写成已实现能力。

## 目标与边界

让开发者使用现有 Core 自由选择架构，同时能够解释职责划分、执行推进、资源决策和失败交代，并用实际证据验收应用质量。稳健性第一；预算追求与必要工作匹配的合理消耗。不得为了预算、格式或附属功能丢失主回答，不用未经证实的内容冒充完成。

Core 保有通用执行、调用、取消、预算和协议保证；Support 提供可组合的应用辅助；Kit 可选。业务角色、工具权限、完成条件和表达方式由 App 决定。不新增强制业务图、平行调度器、统一工作项 DSL 或仅为分类完整而增加的 API。

保留当前所有已暂存和未暂存修改，不重置、清理或擅自提交。当前授权覆盖本地整改与必要的针对性验证；不包含 npm 发布、生产部署、数据库改写和 UI 预览。正式正文描述最终合同，过程材料保留在维护记录。生成副本从唯一来源同步。

## 统一评审依据

每项设计须能回答：输入及前置条件是什么；产生什么可消费成果；是否有副作用；完成由什么证据证明；下一步为何发生；失败归谁处理；是否需要独立生命周期；模型在哪里提供不可替代的判断。

独立路由、提交或恢复是拆分节点的依据，但不是见到其中一个条件就必须拆分。比较拆分收益与状态交接、模型调用、恢复复杂度；只需观察的细节优先考虑节点内执行记录。通用探索循环与业务用例图都可以合理，不按图的形状评分。

明确的下一步由程序推进，尚不确定的选择才交给模型。必要复核和恢复保留资源；重试有进展依据和边界。不得重放已确认副作用；未知写入结果先核实，不将未知当作失败。

## 阶段与依赖

1. 建立基线：各线程先读取项目 AGENTS 和相关 Skill，审视实际源码与既有脏改动。记录具体缺陷、已有正确机制和需要保留的边界；不能只根据截图决定大改。
2. 并行落地：A/B/C 先使用现有公开 API；D/E 按本文统一依据实施已经有证据支持的调整，不等待新增 SDK API，不杜撰计划中的接口。发现公共能力缺口，留下具体调用与失败场景，交由总线程判断归属。
3. 汇总同步：总线程核对文章、Skill、案例、工具输出和两 App 的术语与合同；必要时修复真正缺失的公共能力，同步消费者。生成 articles npm 副本和文档站来源，核对链接及打包白名单，不手改生成内容。
4. 交叉验收：用两种参考架构以及两个实际 App 反向检查指导能否解释取舍、工具能否暴露风险。记录证据层次和剩余限制；发现矛盾必须修正文档或实现，不能靠减少断言通过。
5. 交付：交付修改清单、设计依据、证据与剩余风险。版本按实际兼容性再确定，不自动变更 0.9.0 身份或发布；部署单独按明确请求执行。

## 代表场景与断言

至少覆盖：直接回答、已有证据的追问、需要有序依赖的任务、缺少前置条件、工具失败、模型失败、初始预算估计不足、上下文过长、硬边界无法继续、可选检查失败、格式修复失败、写入结果未知，以及交付后的持久化/连接故障。按实际应用能力选取，不为覆盖名目制造业务。

关键断言：正常路径不被强制额外模型分类；成果有证据且不会被附属失败抹掉；已完成操作不会被重放；无进展循环会重规划或收束；必要工作可在宿主上限内合理扩额；长上下文先判断投影/复用/压缩是否保留关键事实；只有缺口、阻碍或硬边界确实存在时才局部交付；最终有与真实原因一致、自然可理解的交代。显式取消及时生效，不以稳健性为由继续执行。

压缩针对信息承载问题，不能凭空补足缺失事实；提前局部交付针对无法继续完成的问题，不能只因初始配额见底。压缩要保留最新纠正、授权、关键数值、来源、未完成项和回执，必要时可回读。

## 证据等级与完成条件

- 静态结构：注册、引用、可达性、声明一致性；不声称证明运行完成或动态授权。
- 离线行为：实际工作流配脚本化响应，断言执行路径、交接和副作用次数；不声称证明语义质量。
- 真实模型：仅在已有安全配置与明确样本范围内检验语义、路由和表达；不可用则明确未验证，不临时申请密钥或访问生产用户数据。
- 生产：本计划不包含生产发布和线上效果证明。

每个工作包需完成实际文件修改及对应的最小有效验证；文章案例应能由公开入口复现。源码可推理的简单改动不自动全量测试/构建；存在具体执行疑问时先写明疑问，再运行针对性检查。不得用测试数量、无警告、节点数量或开发机耗时替代质量结论。

整体验收要求两种不同组织方式都能保持 Core 自由，并让读者沿目标、成果、推进和恢复读懂执行。所有剩余缺口明确归属；未完成项不能被其他工作包的通过掩盖。
