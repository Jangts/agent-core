# Agent Core 1.0.0 戊方案：答复组织与开发检查

日期：2026-11-25。状态：设计已审计；W0—W5及可选调用级答复指导已实施，有限本地与仓外验证见[实施记录](1.0.0-wu-implementation.md)。性质：消费者提案审计后的方案与实施依据，不是整体正式发行或真实模型语义验收。依据用户完整要求：评估程序处理确定数据、强逻辑和响应结构的收益，但不强制程序化，允许全模型；回答风格与回答参考同样纳入；SDK 提供组织工具、范式和辅助开发且带设计/检查能力的 Skill，业务由 App 拥有。“带”表示引导开发者设计、比较方案和检查；这里没有“辅助开发带”新概念，也不由 Skill 代替业务设计者决策。

## 1. 可行性与明确选择

可行。现有 Presentation、Knowledge、Answering 和开发测试入口已经具备组合基础；当前没有证据要求新增 Core 调度层、统一答复协议、通用比较 API 或新的必选阶段。新增工作的重点是可采用的组织范式、端到端例子、答复设计与检查 Skill、可选开发检查器。

全模型、程序、混合处理是三个正常候选，不是“默认合格、特批例外”的等级。设计检查优先提出两类问题：哪些数据整理/判断可由程序可靠承担，哪些响应字段/结构可由程序生成或绑定；然后比较实际收益与成本。没有预处理、没有模板、没有采用 SDK 的某个 Kit，均不能单独成为失败条件；全模型方案不需提交程序化豁免证明。准确性、已声明接口、安全和真实业务授权等既有合同仍适用于所有方案。

| 正常候选 | 常见适用条件 | 需要检查的取舍 |
| --- | --- | --- |
| 全模型处理 | 规模小、语义变化多、非结构材料理解/改写、没有值得单独实现的确定算法，或整体模型处理更合适 | 所需资料是否在场，事实/逻辑/表达是否正确，成本是否可接受；不能仅因模型做计数或结构生成判失败 |
| 程序处理 | 已知请求与参数、可靠数据及明确业务规则、固定说明、确定结果/界面反馈 | 程序投影、算法、单位、完整范围与当前身份是否正确；不能以“代码算的”推导结论一定正确 |
| 混合处理 | 程序准备事实、统计或结论，模型解释/选择受控语义/概括，程序再组合确定字段及交付结构 | 不同部分来自哪里，模型是否扩大事实，绑定是否正确，额外协调成本是否值得 |

这不是硬路由表，不由关键词触发，也不要求每个 App 实现三种模式或每轮运行选择器。语义与历史仍可由模型理解；已知依赖可程序推进。一个答复也可按字段、段落或结果块混合，而不是整条消息只能二选一。

## 3. 可采用的组织范式

以下是可组合的参考，不是 Core 状态、必选节点或固定答复栏目。

1. **自然答复与全模型处理。** 直接理解已提供资料或当前问题，按任务生成完整答案；需要数据或动作时遵守既有调用合同。没有必要的工具、模板和复审不额外加入。
2. **程序结果与直接交付。** App 按明确规则生成已知结果或可信文案，直接呈现；纯界面复制、选择或取消也可没有助手正文。若选用零模型的答复路径，其零新增调用是该路径的验收要求，不是所有回答的要求。
3. **程序事实或结论，加模型解释。** App 提供原始事实的适当投影、可推出的结论及未确认范围，模型负责概括、说明和新的语义判断；不从样例手数全量，不把结论扩大到未比较维度。
4. **模型正文，加程序结构或确定字段。** App 可仅绑定数量、标题、清单、顺序、真实入口或固定段落，让模型组织其余文字；也可由模型生成结构化结果后做已有结构检查。选择哪种以适用性和成本决定；稳定模板也可按任务不用。
5. **资料答疑与参考示例。** 可直接读可信快答，也可按当前问题读取详情并由模型解释。来源、版本和适用条件要明确；固定文案、参考写法和运行事实不互相替代。
6. **动作后的结果说明与修复。** 准备、执行、保存、接纳、部分成功和未知分别说明；修正文案只消费现有事实/回执，不重放业务动作。需要持久恢复时复用原有合同，不为普通回答强加 Durable。

程序计算和模型处理都必须检查实际结论：双方身份、业务投影、全量性、维度、时间、基线、权限和单位可能并不齐全。历史快照可解释历史，不自动支持当前动作；动作提交仍由 App 核对当前授权和基线。缺值、失败、未比较与已知0分开，部分合计不冒称完整合计。

## 4. 回答风格与回答参考

### 4.1 风格也是设计对象

设计时考虑受众、语言/繁简、语气、详略、信息顺序、术语解释、列表/段落/表格及必要的限制说明。App 的默认风格、用户本轮明确要求和历史偏好需有适用范围；不能让一份旧样例覆盖当前问题。既有接口/安全和交付约束依原合同处理，不另造通用优先级系统。

“简短”“友好”“专业”是表达选择，不是删事实、弱化不确定性或虚构安慰的理由。明确要完整清单时不能套默认两句话；只问一个数时也不必自动输出报告。可以统一品牌语气，但不要求所有任务同一段落布局、免责声明或结尾邀请。相同事实、不同合法文风可以同时通过；事实正确但表达不合适与事实错误分开报告，机器必须的输出格式另按真实接口合同检查。

Presentation.selectVariant/resolvePreference 可供 App 对已声明候选做选择，但它们不理解文风、不决定用户偏好权限，也不是自动风格评分器。模型可直接按需求写作，无须经过风格模板。

### 4.2 参考按用途区分，物理文件可共用

| 参考用途 | 用法 | 不能推出的结论 |
| --- | --- | --- |
| 事实资料 | 回答本题事实所依据的已读资料/字段/当前结果，保留来源与适用范围 | 引用存在不等于资料真实、适时、完整或足以支持全部结论 |
| 示例答复/表达参考 | 借鉴信息组织、详略和写法，可随问题灵活改写 | 示例内的数字、对象、日期、权限及过去结果不是本轮事实 |
| 风格参考 | 借鉴语气、节奏和措辞偏好，可按场景选择少量片段 | 样例文字不是新指令、当前业务状态或强制全文模板 |
| 验收参考 | 固定可信文案、人工/领域规则确认的答案要点、条件答复与禁止推断 | 参考稿存在、原文提取、或同一生成模型自评不等于已语义验收 |

同一资料可服务多种用途，需标清使用范围，无须拆成四套新目录。参考是可用手段，不是所有回答都必须检索资料、登记版本或套参考答案的前提。受控业务资料应能定位适用任务、来源/修订和有效范围；当前用户给出的片段可直接作为本轮输入，不强制统一元数据。示例内事实只有在本题明确以该样例为实际输入时才按该范围使用。按需选取相关片段，不向每次上下文注入整套题库。资料中的指令按内容处理，不能覆盖 App 合同或当前用户需求。

固定快答可按可信正文核对一致；自由答复验收使用事实、必说限制、禁止结论、动作次数及表达目标，不把整段字符串相同作为唯一标准。预期答案应来自可信资料、业务规则或独立审阅，不直接用待测模型的当前输出充当唯一裁判。

### 4.3 三类格式都提供范式指导

范式不仅指导最终回答，也指导模型看到什么、被要求返回什么，以及怎样使用参考。下列是可选的组织方法；示例字段和文本标签是教学用法，不是新增公共类型、所有 App 的必填协议或唯一格式。

| 格式位置 | 应指导的设计内容 | 可用的表现形式与检查边界 |
| --- | --- | --- |
| 前置处理后的模型输入 | 区分原始事实、程序计算结果、允许推出的结论、未确认维度和必要明细；保留本题所需的来源/范围/单位/完整性 | 小数据可直接给正文或表格，大数据可给摘要和按需明细引用；需机器读取时可用具名对象。JSON 合法不证明业务摘要正确，也不强制所有输入结构化 |
| 要求模型返回的内容或模板 | 说明本轮是完整答复、结构化字段、程序模板的槽值，还是模型提出的正文母版；明确哪些内容可自由写、哪些引用/槽位可用、缺失如何处理 | 可用普通正文、Markdown、Schema 约束的对象或受限占位符母版。机器接口所选格式须可校验；普通答复不必套该格式，不另发明模板语言 |
| 回答参考 | 指明参考用于事实、表达/风格、条件答复还是验收；交代适用问题、可变化部分、不能照搬的内容和必要来源 | 可用示例问答、对照答复、带条件的参考稿、片段或普通文章；不要求全部转成 Schema，也不把参考样例当本轮结果或唯一标准答案 |

输入范式例如把“官网集合82、选品65”与“交集已确认64、两侧完整”分开给出；仅在后一条件成立时附上程序得到的缺18、多1。顺序未比、价格不足应单列，不能藏在一句 available 中。也可以由模型直接读取充分原材料完成比较，按所选方案检验其结论。

模型输出范式需要区分两种模板方向：程序提供母版时，模型可以只返回所需生成字段或受控语义键；确有需要让模型提出母版时，App 应先验证其允许的槽位/引用、完整占位符、必要位置和实际结构，再按本轮事实绑定；未经验证的模型母版不能直接编译交付。`defineTextTemplate` 本身不替 App 限定模型可以提出哪些槽；插槽白名单、来源授权及最终载体安全须由相应声明和 App 校验承担。模板是受限文本，不接受可执行表达式，插入值不递归执行；母版的标签、单位及结论是否与绑定值语义相符仍需相应业务断言或审阅，槽位白名单本身不能证明。全模型直接给完整正文仍是正常方案。

参考范式可以用同一组事实给出简答与解释版，并标注共同的必要事实、可变化的表达和禁止扩大；也可以展示一个错误答复及其缺少的证据。Skill 应引导开发者比较这些写法的适用性，而不是要求复制示例句式或每次填写全部栏目。

### 4.4 工具、文章和 Skill 的分工

适合稳定执行和复用的解析、字段归属、槽位/引用及已声明断言检查，优先复用现有工具；有实际通用缺口才补工具。格式怎么选、数据怎样组织、何时全模型更合适、参考怎样写、风格怎样变化等判断，可以通过文章、完整示例和反例指导，不要求为了每一种范式新增 API 或 CLI。

本案明确交付一份答复组织专题文章或既有文章的完整专题章节，覆盖上述三类格式、处理方式选择、风格和参考使用。文章逐项给出适用条件、完整输入/期望输出、取舍、失败与反例；涉及程序接线的部分链接真实公开 API 及可运行示例，其余可用完整文字对照，不要求每一种格式都有可执行程序。不能只罗列原则或提示词。Skill 负责引导发现需求、选择范式、落到 App 接入和检查，按需读文章；工具负责能可靠机械检查的部分。

文章沿已有单一源稿、随包稿与文档站的生成链维护，不另建一套相互竞争的规范，也不手工改生成副本。文章是范式指导的正式交付方式；它不能替代已明确声称实现的工具或运行行为验证。

## 5. 已有能力与缺口判断

| 现有入口 | 能直接复用什么 | 不保证什么/本案补什么 |
| --- | --- | --- |
| Presentation.defineTextTemplate | 缺槽检查、单次替换，值中的模板文字不再执行 | 不保证事实、授权、新鲜度或 HTML/Markdown 安全；补完整使用及负例 |
| defineSemanticSlots | 允许 key、命名空间、次数和残缺格式检查 | 不证明 key 选择业务正确或来源授权；补真实引用与语义边界示例 |
| defineOutputCatalog / toModelSchema / compose | generated/bound/constant/semantic 字段所有权；程序指定 group 成员；只向模型暴露其字段 | provider 必须同步：异步读取先在 App 准备；需 OperationContext；绑定正确不证明自由正文忠实 |
| defineReplyFormats / replyFormatChecks | App when 条件决定适用格式、检查已声明约束，未匹配可返回 undefined | 不替 App 选语义/判断准确性；多个格式按声明顺序，不能假定全合并 |
| Knowledge | 文档/章节选择、revision 和有界读取 | 不获取/授权/判断文案是否符合当前业务；补参考按需使用与失效例 |
| Answering | 显式题项、有界生成/检查/审阅/修复，允许不同 review 策略 | accepted 是配置策略下接纳，不是模型/界面实测通过；修复 handler 的副作用归 App |
| 既有 workflow-design、app-testing、inspection、change-review、regression、resilience | 图与合同、真实绑定、离线用例、变更/恢复及证据分级 | 不自动完成答复风格/参考选取/逐题答案审阅；补答复专项工作流和检查输出 |

前置数据、输出结构和参考组织本身没有已证实的公共运行时 API 缺口；新增的调用级指导需求及其最小入口见下节。不得把官网 SKU 比较、App 页面/草稿、quick-reply 文件语法、所有题库状态或风格规则加入 Core 必填合同。普通函数和现有 App handler 足以实现领域预处理；需要可枚举登记时从实际执行清单取投影，动态语义不能可靠枚举时不强行建词表。

后续只有出现现有公开合同无法合理表达的必要需求及最小反例，才另提 helper：说明输入/输出、所有者、失败合同、通用性、现有组合成本及兼容面，结合选定示例核对复用边界后定向复审；不以调用方数量代替必要性判断，也不要求先凑两个业务消费者。不得因本案列了范式就反推必须有同名类或方法。

### 5.1 调用级短指导增量

用户新增问题是长摘要反而更长，且文档/提示词可能未进入当前模型输入。该需求收敛为可选 `ReplyGuidance.defaultDetail`：brief / normal / detailed。它是受信任的答复默认值，不是完整风格协议或领域判断器；全模型仍合法。

Core 在 `ModelPrepareRequest` / `ModelCallRequest` 接受 `replyGuidance`，准备时由固定词表生成短指导、冻结值及指令，并沿同一交互计量/发送路径使用。Engine 的节点 prepare/invoke 两处透传。prepared 调用不得再附指导；modelOptions 的准备不会重复注入。未配置保持原路径，不增加模型调用。

Support 提供 `resolveReplyGuidance({defaults,node,tools,call})`；App 从既有注册选择相关配置，优先级依次升高。适用工具默认值冲突必须显式 call 决定，不靠顺序胜出。Core 不自动扫描任意工具/节点字段，不把描述、用户原文和工具结果升级成 system 指令，也不自动启用到内部推理调用。

短指导要求简答先给结论及必要支撑、摘要压缩原文；用户明确要求详情、全量、语言、风格和格式时仍遵从，同时保留影响判断的限制及交互协议。它不强制字符/段落数、不截断、不做关键词分类、不加隐藏复审、不授权行动。更丰富的语气/受众/参考仍由可信任务上下文提供。指令增加输入开销，沿既有交互/schema 字符额度及总输入/token 计量；真实更短更合用尚无模型效果证据。

本增量由R3源码/协议和R6体验定向回查，修正Engine漏透传及枚举强制转换反例后闭合；运行证据见实施记录，不把该确认扩大成全案八方重新验收。

## 6. 开发 Skill 与可选检查工具

### 6.1 单个专题入口，设计/检查两种工作方式

拟新增 `development/skills/agent-core-reply-development/SKILL.md`，名称表示答复开发，不是运行时任务方法。它以引导设计和检查为职责：帮助开发者识别问题、比较候选、选择输入/输出/参考格式并落实到当前 App，而不是自动替开发者作业务决定。它处理既有图不变的答复方案、事实/表达/参考问题，复用已有 workflow-design、app-testing 等通用步骤；既有入口只加定向发现链接，不复制另一套图设计、测试 runner 或恢复流程。它不进入 `skills/` 运行时 task catalog，也不把整套开发规范注入用户对话。

选择专题入口的理由是：答复风格和参考设计可不涉及节点/路由改变，既有 workflow-design 的触发边界较窄；app-testing 又从已有测试接线开始。专题入口负责这段任务衔接和交付检查，通用能力仍由原入口拥有。两个近似的设计/审计 Skill 会重复维护同一参考与反例，因此本案不拆成两个。

设计方式交付：具体用例与真实入口、适用的处理方式（有选择疑问时再比较替代，不要求每题展开三套方案）、事实/语义/结构/风格责任、参考用途和版本、选定的完整或条件化答复、接入点、失败/取消/纠错路径及最小验收集合。不要求全模型方案额外写一份豁免书。

检查方式交付：实际触发题和预期范围、所用资料/参考、观察到的缺陷及证据、所属边界/影响、最小修正与回归。区分事实/逻辑缺陷、表达不合适、结构/引用错误和可能优化机会；程序化或模板化建议单列，不阻断合格结论。无需助手正文也是合法结果。

### 6.2 可选检查器

若选定示例表明确有现有工具未覆盖、值得程序复用的检查缺口，拟置于该开发 Skill 的 scripts 与 examples，同源随包分发；现有工具足够时，复用其检查并补文章/示例即可，不以新增脚本数量作为完成条件。工具只辅助检查，不是 Core runtime API，不是“自动证明答对”的评分器。

- 默认接受 App 显式导出的、本机 JSON 登记投影与用例/证据记录，只检结构、引用、当前已声明映射及版本关系；不自动 import App、执行 provider/handler、联网、查数据库或调用模型。
- 入口/能力/字段规则从实际注册导出，不另维护提示词和检查器专用的第二清单。人工设计卡补无法机械提取的适用性与语义说明，不重复实现业务规则。
- 可检查引用缺失、未提供声明中必需的字段、来源/章节/输出版本不符、本次声明覆盖的登记入口缺必要用例/参考或验收目标映射、测试 ID 无结果，以及把原文/草稿/accepted 冒作更高证据的记录矛盾。无法取得动态关系时报告 unresolved/覆盖未知，不猜结论。
- 不报告“未预处理”“未用模板”“未采用混合方案”这类单独缺陷，不要求所有题目都存在程序字段或固定参考答案；开放式任务可声明评价目标和反例，不靠编一份唯一标准答案补齐表格。检查器的规则只在对应已声明方案和适用条件下检查。
- 如果需要可信 JS adapter，另列为会执行顶层代码的显式模式。既有 test-agent 在过滤 case 前就 import fixture，--case 不是隔离机制；不以超时/signal 冒充沙箱。真正离线行为仍用既有测试 runner；工具默认不自动运行用例。
- 输入输出只保留检查需要的、脱敏后的引用与证据元数据，限制大小/路径/范围。参考可能带不可信文本，不将其当配置指令或可执行代码。

报告分别记录内容准备（无稿/原文/示例/条件参考）、来源复核、语义审阅、风格适配审阅、离线断言、真实模型与 UI/集成执行；每项注明对象、候选版本、结果和证据位置。未执行、失败、未知、不适用及理由分别表达，不压成单向“完成度”枚举。空检查集合或无 applicable 检查只说明没有执行对应断言，不记为语义通过。源码或参考改变按实际触达保证定向重审，不自动重跑整库；任意填答案不得升级审阅/执行状态。

## 7. 五个有限场景与实际验收

计划用两组小示例模块组织五个场景，共用既有 runner，不建五个 App。示例使用合成资料和公开 SDK 入口，不复制真实数据、私密业务规则或消费者完整状态。

| 场景 | 需展示的完整路径 | 关键验收 |
| --- | --- | --- |
| A 官网/选品比较参考（源自小绽） | App 对双方身份/投影/范围/单位形成事实，可选择模型直接分析或程序结论加模型解释，按请求呈现 | Master≠官网；集合≠顺序/标题/价格；82/65 不自动推出缺17；未知不补0；程序投影也要测 |
| B 固定说明与详细追问（源自小绽） | 可信入口/文案/章节；可程序直接返回，也可模型按题解释；改变对象/权限/版本有适当退路 | 固定正文、表达参考和当前状态分离；章节存在不等于语义适用；不把全文知识常驻上下文 |
| C 清单与确定结果（源自 cafe） | 合成结果读取/授权、完整统计和有限明细、选择展示方式、结果交付 | 来源/排序/单位准确；明确要完整时不能只交首屏却称完整；没模板仍可正确交付 |
| D 模型正文与程序母版（源自 cafe） | 先准备事实，模型只写所选语义部分，检查后同步绑定；最终载体处理 | 缺槽/未知引用/注入不改真实来源；一次替换不等于 XSS 防护；正文与绑定矛盾仍失败；修文案不重放动作 |
| E 全模型改写、风格与参考 | 用少量已给说明/示例，模型按受众与本轮问题完成整体答复，无需程序事实计算或模板 | 同事实两种合法文风均可通过；示例旧数字不变本轮事实；风格良好但内容错误不能通过；完整要求不被默认简短截断 |

A 的合成条件参考：官网完整唯一集合82项，选品完整唯一集合65项，交集64项，标题已比有2处不同，顺序未比，价格资料不足。可接受简答为：“按本次SKU集合核对，选品缺官网18款，多1款；共同项有2处标题差异。顺序未核对，价格不能确认。”解释式答复可说明两侧总数差17不等于缺17。无需逐字相同；不得加入同款规格关系或整体一致。若交集/完整性未知，18与1也不能照抄。该数据只用于示例，不是实际业务结论。

E 的参考：同一份虚构服务说明可生成“面向新手的两段解释”和“面向熟悉业务者的一句概括”；核心事实及适用条件一致，表达不同均合法。风格参考内的旧日期/数量不参与当前事实；若源资料不足，允许有依据地保留未知。这里没有必须程序化的答案部分。

各场景需具体参考答复或条件分支、机器可判定断言与语义/风格审阅项。对原提案14类反例逐项关联适用场景，不把“14项列出”写成已执行。至少保留：不匹配来源、部分覆盖、缺值/单位、合法引用但结论错误、过期参考、同路径换对象、用户纠错、准备≠执行≠保存、部分成功/未知、模型预算耗尽、修复不重放、全模型正确且无模板、无需聊天正文。

确定性路径可离线断言；自由语言和风格不能只做全文字符串相等。固定文案按可信源核对，逻辑用领域断言与负例，语义/风格按场景选择有依据的独立审阅或有实际结果的模型样本，不默认再调用一个裁判模型。真实模型、UI或厂商证据只能说明已测配置/输入，未执行保持未执行；不默认付费调用或打开页面。

## 8. 交付顺序与完成条件

| 工作包 | 拟交付 | 退出条件 |
| --- | --- | --- |
| W0 设计与范围 | 本提案、来源审计、处理方式/风格/参考及边界选择 | 全模型合法；已有/需补/不采纳明确；原意见回查闭合，不把设计当实现 |
| W1 端到端示例 | 两组小示例、上述五场景、参考与负例 | 真实公开 API 接线完整，可按场景单独读/运行；合成事实与源消费者做法区分；不默认迁移小绽0.8 |
| W2 开发 Skill | 一个引导设计/检查的专题双方式入口、设计卡/检查记录、文章与已有入口发现链接 | 能引导选择前置输入、模型返回与参考格式，交具体答案、风格方案及接入点；不是只给原则、问题列表或提示词 |
| W3 可选检查工具 | 先给现有检查能力与缺口取舍；必要时补纯数据入口、输入投影和分层证据报告 | 有可靠通用检查才工具化；现有能力足够可通过复用和文章/示例交付闭合。新增工具时须能发现相应断引用/证据冒领等，且不误报全模型/无模板方案，默认无运行副作用 |
| W4 定向回归与语义证据 | 复用 app-testing/场景 runner；机械负例、语义与风格样本分别记录 | 用例有真实断言，动作/模型次数按选定合同检查；不能用生成数量、引用有效或 accepted 冒作全通过 |
| W5 文章、分发与资料 | 三类格式的专题文章或完整专题章节、SDK 两语参考、Skill/examples/scripts 同源、候选包边界与消费入口 | 文章有完整输入/输出、适用取舍和反例，不只是提示词；与真实接口及示例互链。维护记录不混进使用手册；包外安装按实际变动检查；不把文章或站点静态通过等同运行或语义通过 |

设计阶段的交付是经过审计的可行方案和有限实施标准；实施阶段才可声称 Skill、检查器、样例与实际回归已完成。当前版本保持1.0.0。W0—W5的实际交付及调用级增量以实施记录为准，不自动计入先前其他方案的候选验收。既有发行/分库评审缺口另行跟踪，不在本案顺带修复。

本案预期收益是减少不必要的模型搬运、计算和结构拼接，提高可核验性；全模型方案也可能更省实现成本或更适合语义任务。没有运行对照前不承诺省钱百分比、更低延迟或准确率提升。后续若需量化，优先复用正常有限用例的已有调用/用量记录，不因此开启压测、反复基准或全量模型评估。
