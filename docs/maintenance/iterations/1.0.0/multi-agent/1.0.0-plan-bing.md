# Agent Core 1.0.0 丙方案：多 Agent 分歧发现与处置

日期：2026-11-25。设计修订：第三版，吸收七方独立审计与额外语义专项，原提出方原意见已逐项对齐，无待投票取舍。用户后续明确授权按子 Agent 实施；支持范围、实际接线、交叉复查和验收证据见[丙案实施记录](1.0.0-bing-execution.md)。不表示设计全文重新获七方验收、整个 1.0.0 完成或已发布。范围仍为职责归属、分歧与冲突发现、复用甲案等待与恢复；发布、部署不在本轮授权内。审计依据见[丙案审计记录](1.0.0-plan-bing-review.md)。

## 1. 可行性与现有基线

以图文分析与图像生成为使用场景的通用多执行者协作机制见[丙案协作机制增补案](1.0.0-bing-multimodal-supplement.md)。App 提供实际执行者，本增补不提供或评估模型能力；提案不计入主案已交付和已验证机制。

方向可行，但“发现并解决所有分歧”不能成为保证。确定性冲突、语义疑点、未覆盖和已核实分歧须分开；一致结论不等于正确。丙案交付可组合的检测与处置能力，不建设第二套执行调度器。

## 2. 问题一：职责归属

| 所有者 | 责任 |
| --- | --- |
| Core | 维护既有执行隔离、预算、取消、结果接纳保证；只有真实示例证明无法由现有合同安全表达时，才提出最小执行合同变更 |
| 可选 Kit | 按 App 声明组织结果对照、检测器、复核与处置策略，返回结构化结果；复用 Waiting、Durable、Aggregation，不依赖 Core 识别 Kit 状态 |
| Support | 必要的注册校验、装配和关联接线；不另建委派或调度协议 |
| App | 业务目标、资源身份和版本、证据权威性、真实授权与原子存储、最终裁决权、持久化范围及呈现 |

不内置多数票、自报置信度排序或主 Agent 必然正确。App 可显式选择有界评审或投票策略，但不能用其覆盖用户要求、权限、确定事实和提交条件。模型及检索结果是待检验数据，不能赋予工具权限或改写策略。

上表 Kit 表示可选能力归属，不预先决定新增公开入口。P0 用同任务、同故障、同授权和预算比较普通 handler 组合与推荐接线：核对重复规则、关联元数据、存储窗口处理和定位负担。有可复用收益才抽取公开 Kit／Support；没有独立收益则交付复用既有机制的接线与示例，但通用安全关联不能留给每个 App 重写。

渐进接入按同一结果读取语义连续扩展：普通单 Agent 无需丙能力；请求内多 Agent 可仅检测并返回；再增加有界复核；最后按需增加跨请求等待与继续。仅检测不要求争议持久库、等待门或持久总账；没有语义调用的确定性检测不新增模型调用。P0 定义并探路，P4 用实际示例验证，不为此预设万能入口或总协调类。

P0 参数所有权分为：检测器、策略、稳定存储及授权端口一次绑定；当前身份、signal、Runner 和本次预算按运行注入；可信关联从持久记录派生并由推荐接线校验，不手工复制同一关系。保留普通对象、原型方法、自定义实现及其接收者，不复制带私有状态的宿主服务实例。

## 3. 问题二：发现分歧与冲突

### 3.1 检测输入与可比性

仅参与共同决策的任务使用可选结果合同，不强迫普通回答结构化。结果至少关联问题／目标、执行与分支来源、材料版本、结论、证据引用、关键假设、未确认事项及建议动作。真实执行来源由可信宿主绑定，不能相信模型自报的 Agent 身份。证据引用必须能解析或标记不可核验；不能由引用存在推导内容真实。

检测投影不替代业务结果：保留 SpecialistReport 等原结果的精确类型、业务扩展字段或稳定引用，避免降成 unknown 后要求调用方重建；新发现／覆盖字段不改变所有 Core 输出。P4 的仓外类型验证须包含带业务扩展字段的消费示例。

宿主分派时固定共同决策范围、规范化资源身份、输入版本和必须核对的约束。模型可提出新假设，但不能通过改写问题名、适用条件或材料版本缩小检测范围；无法映射的结果进入待核查／未覆盖。同一问题不同措辞、伪造条件和版本逃避筛选列入 P2 验收。

先建立可比较的问题与范围，再做候选筛选和语义复核。不同时间、适用条件、目标权重或材料版本的结论不直接算作同一命题的矛盾；必要时先补齐输入。相同结论但依据不可靠，属于验证问题，不冒充已发现分歧。

输入／条件不一致本身是一类发现：合理场景分叉保留各自范围；影响共同决策的陈旧或缺失输入必须登记为需补齐输入的疑点，不能因不可比而静默筛掉。无法对齐时保留未完成覆盖。复核确认只表示指定问题、证据和条件下存在可复核的不一致，不表示某一方已被证明正确；第三个模型赞同不替代独立事实验证。

### 3.2 检测清单

使用一份类型化声明清单驱动检测器装配、适用条件、输入输出校验、严重性与阻塞策略和诊断关联。规则不只写在提示词中。不为追求统一而重写现有 Aggregation。

| 检测种类 | 方法 | 承诺 |
| --- | --- | --- |
| 已有补丁重叠 | 复用 aggregateBranchResults | 仅其现有顶层字段冲突合同 |
| 资源版本、读写集合与前置条件 | App 提供可信资源映射、版本和检查端口 | 宿主真实存储中执行原子校验／提交；预检不替代提交检查 |
| 显式约束与任务依赖 | App 登记可判定规则 | 仅已声明、实际执行的规则范围 |
| 事实、推理及方案分歧 | 对齐命题后语义检测，再针对具体疑点复核或补证据 | 输出疑似或经复核分歧；不承诺完备性，不将模型结果当确定事实 |
| 目标与偏好差异 | 对照 App 声明目标与用户取舍 | 保留选项，按裁决权限处理 |

结果至少区分：发现疑点、确认分歧、在声明覆盖范围内未发现、检测未完成。超时、缺结果、畸形输出、预算不足不能转成无分歧。失败与取消沿现有执行合同传播或由 App 显式转成未完成结果。

以上不是互斥的单一状态枚举。结果分为发现集合与覆盖情况两个维度：每个发现独立标记疑似／复核确认，覆盖情况独立记录完整／部分／未执行、声明范围、跳过项和停止原因。可以同时存在已确认分歧与未检查候选；空发现集合不证明覆盖完整。首期检测限定显式共同问题／资源的汇合结果，不承诺跨任务隐藏依赖的全局发现。

### 3.3 检测时机与成本

分派时检查任务重叠与输入版本；汇合时检查可比结论；动作提交前检查最新版本和前置条件。三者按场景启用，不要求每次调用全跑。

避免全量两两辩论：按问题、资源和条件筛选候选，设置候选数、复核轮数、证据读取和模型额度上限。筛选可能漏检，必须暴露实际覆盖范围、跳过项和停止原因。语义调用沿当前 Runner／受控子执行共享预算，预留父级收尾；不得新建无限额度 Runner。日志与诊断复用现有链路，不默认永久保存内部推理或所有材料正文。

## 4. 分歧项与处置

分歧项是 Kit 局部数据：标识与修订、争议问题、参与结果引用、材料版本、具体矛盾与条件、证据、检测／复核状态、是否阻塞及其依据。保留判断依据与简要理由，不要求模型内部思维链。未完成检测和未解决分歧分别表示。

App 显式选择策略：补证据、定向复核、指定评审者、保留多方案、等待用户或停止。每次处置返回明确状态与理由；达上限保留未解决项，不强制共识。策略的适用条件、裁决权限和实施入口从集中清单读取。

App 对每类动作显式登记必需检测范围、可选检查及阻塞规则。必需检测未执行／覆盖不全、版本失效或相关阻塞项未解决时禁止放行；其他动作仅按显式策略带未解决项继续。最终原子提交须核验当前策略修订、覆盖依据和争议状态，空发现集合、模型“已解决”或界面状态不能替代准入。首个闭环使用两个只读分析 Agent 提交提案、一个串行提交者执行；受控并行 commit 不被当作存储事务。

分歧生命周期与等待生命周期分别管理。pending/resolved/cancelled 只描述等待门；收到答案不等于事实正确、争议关闭或动作已获授权。裁决只作用于指定分歧修订和材料版本；旧结果不得覆盖新争议。

影响裁决有效性的内容／材料修订与通用记录 CAS 版本分别表达。只改变生命周期状态不导致内容修订变化或重建等待；内容或材料变化必须使旧裁决失效。处置还需无新证据／无进展出口，不能只靠耗尽总额度结束重复争论。

## 5. 复用等待与恢复

请求内评审使用现有子执行等待。跨请求等待使用 defineWaitGate；App／可复用接线绑定争议修订、材料版本、裁决者及执行代次，等待数据本身不增加授权。

现有 Waiting 按 gate.id 与 taskId 存储单槽，waitId 只是代次。默认由宿主为每个争议修订分配并持久保存独立等待 taskId，关联父任务；不同并行争议使用不同槽。同一争议修订串行等待，新代次使用不复用的 waitId 和 previousWaitId。pending 即使过期也不能直接替换，须先显式取消；resolved 后输入变化在争议记录中使裁决失效，再为新修订创建新槽，不能通过 gate.cancel 撤销已确认答复。

流程：保存待裁决事项及必要成果引用 → 建立等待 → 正常返回、释放请求资源 → 当前授权下接纳答复 → 重新核验争议和材料版本 → 显式继续后续有界任务。

等待门和争议记录可能不在同一存储事务中。P0 必须定义操作身份、可重入顺序和失败读回／对账方案：建立等待失败不能丢失待处理事项，答复成功但后续保存失败不能重复执行动作。不得假定两个 Kit 自动形成原子事务。优先以宿主事实为依据，通过稳定操作身份和 Durable 对账恢复；必要的新接线必须可复用，不能只留示例约定。

裁决接纳使用预期争议修订、材料版本、submissionId 和稳定动作 ID，由 App 原子条件提交端口比较并接纳；并发恢复者只能成功接纳同一次状态转移。提交业务动作时再次校验这些条件，不能依赖先检查后写入。等待锁与 Durable 任务锁不自动保护业务资源；跨存储动作使用幂等或只读对账，不承诺 exactly-once。

等待到期、任务取消、主体权限变化、材料更新、重复与冲突答复须各有结果。暂停期间累计额度、执行期限不重置；已答复但无法继续执行时允许当前授权下查询，不能借恢复绕过期限。无自动轮询或后台常驻调度承诺；App 提供显式重新进入入口。

现有 Durable 额度和期限仅属于单个 checkpoint，不自动覆盖等待前后两个任务。P0 必须明确父级持久总账及原始截止时间的所有者，前后子任务只取得受限分配，重建不重置总消费或延长父期限；先核查现有宿主接线，缺失时设计最小可复用接线。只有另一项明确授权的工作才可使用独立总额度，不能用新 taskId 隐式续额。

P0 另交付资源与退出所有权表：请求 Runner、子执行、流／订阅、借用服务、存储锁及在途保存的创建者、所有者与结束顺序。等待返回释放本请求资源，不销毁宿主共享服务；已开始保存及确认读回 settle 后才释放排他作用域。恢复只重建当前资源，凭据与连接不序列化。清理使用乙案公开的独立有界 lifetime，不复用已 aborted 的 signal，不新增丙案清理调度器；P3 验证等待、取消、失败、恢复的退出。

App 提供当前授权下的只读争议／成果查询，推荐接线负责可信身份关联和状态投影。查询不隐式继续、不分配新执行额度、不重新复核或触发动作；Durable.run 对非终态可推进，不能充当通用只读入口。答复已确认但争议尚未接纳等跨存储窗口，返回待接纳／待确认及可核验引用，不能按 resolved 猜测已解决。只有显式继续入口负责原子接纳、重验和有界推进，P3 覆盖答复成功但接纳保存失败后的纯查询行为。

## 6. 实施阶段与验收门槛

| 阶段 | 产物 | 关闭条件 |
| --- | --- | --- |
| P0 合同与最小探路 | 可比结果、检测器／策略清单、等待关联及两种接线对照；真实参考场景的确定性薄切片 | 实际贯通一个争议的产生、等待、答复和有界后续动作，父级额度／期限与原子接纳有效；至少注入保存确认丢失或并发恢复竞争之一。明确其余中断窗口留 P3、与甲乙丁边界及新增 API 必要性，不先冻结候选字段 |
| P1 确定性检测 | 复用补丁冲突；资源及约束检查接线 | 同值字段冲突、版本变化、提交竞争、缺失结果和不同完成顺序有明确行为 |
| P2 语义检测与处置 | 有界候选筛选、疑点复核、证据补查和未解决结果 | 条件不同不误算矛盾；隐含矛盾、同源错误、不可核验证据和恶意材料有样例；共享预算与取消有效 |
| P3 等待与继续 | 复用现有 Kit 的可复用接线和持久示例 | 重启、旧裁决、重复／冲突答复、等待与争议保存的各中断窗口、权限变化、不重做已完成动作 |
| P4 消费者与资料 | 实际受影响消费者适配及必要回归、公开入口与双语资料、Skills、包体和相邻来源同步 | Banker／小可乐按实际影响适配，不受影响者有依据；pages 和 MockGPT 的实际受影响来源同步。最终候选 tarball 在仓外干净消费目录安装，验证声明的导入、类型、依赖和必要示例，ESM／CJS 按公开承诺验证；运行控制、真实语义效果和未验证范围分别陈述 |

离线测试验证控制行为，不能证明语义检测质量。真实模型评估使用标注样例，分别记录误报、漏报、未完成比例与成本；不在开发机压测。正式实施前由审计确认样例范围和质量门槛，未确定门槛不宣称语义能力验收。按仓库规范只运行必要验证，不修改或重置已有工作区改动。

P0 参考场景明确为：Banker 专业报告的版本差异与认知分歧（包含补齐输入后复核，以及同条件互斥建议无法收敛后等待裁决），另以两端现有 Family 三方字段合并验证状态冲突；保留 partial 的缺覆盖语义，不将材料冲突、字段冲突、认知分歧直接合成一个字段。优先投影已有结果，只补缺失信息。

最小闭环主动对照成员意见，不依赖 Agent 自报冲突；语义比较返回双方原意见和依据定位。验收同结论不同措辞不误报、相反结论能定位、不同字段但同资源的冲突阻止动作、分支失败不冒充一致。先以首个消费者证明，再抽取稳定公共接线并同步第二消费者，阶段表按交付合同展开而非要求先造新框架。

P3 必测：多争议同时等待及独立取消、过期待轮换、resolved 后材料更新、核验后提交前争议更新、两个恢复者竞争、跨等待总消费不清零和超过父期限后的答复查询。P2 必测恶意证据不能改变检测器注册、跳过阻塞条件、修改等待身份或增加工具权限。

语义评估分别统计候选筛选漏检、命题对齐／复核误判和从原始结果到最终发现的端到端表现；不能只测人工挑选的冲突对。标注至少覆盖直接与隐含矛盾、条件分叉、版本差异、多方联合约束冲突、共同错误但无分歧、缺证据与恶意材料。P0 冻结样例与验收阈值后再进入语义实现。

## 7. 本轮审计要求

沿用甲乙七方方式：范围审计、无原方案输入的独立规划、源码可行性、可推翻前提的反方、故障语义、API 体验、职责分层；另保留语义专项意见。每条意见给出具体段落、风险、源码依据及最小替代，区分阻断、建议和已满足。主审逐项记录采纳／改写／拒绝理由，再交每名原提出方核对自己的原意见，不以摘要认可代替逐项回查。不能对齐的具体 A/B 取舍交其余六名正式评审投票，原提出方与主审不投，每票有理由，3:3 交用户。未答复和附条件认可不算通过；未解决阻断保持打开，不在设计审计后直接开始编码。
