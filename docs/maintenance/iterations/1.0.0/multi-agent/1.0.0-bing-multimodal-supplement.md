# 丙方案增补案：图文任务的多执行者协作机制

日期：2026-11-25。修订：第二版，八角色首轮审议及原提出方逐项回查完成，设计表达缺口已回应，M0 实际证据仍待取得。状态：设计提案，尚未实施，不代表修订全文重新八方独立审计或实现验收。定位是提供协作机制，模型能力本身不在本案内。主案见[丙方案](1.0.0-plan-bing.md)，已有交付见[实施记录](1.0.0-bing-execution.md)，本次审议见[八角色记录](1.0.0-bing-supplement-review.md)。本轮仅调整方案，不改运行代码。

## 1. 目标与职责

App 提供实际执行者，Agent Core 包提供原生、可复用的协作组织机制。执行者可以是另一个 Agent、模型调用、工具或 App handler；Core 不需要判断具体模型能否识图、生图，也不承担这些能力的实现、选型、效果评估或服务接入。

图文理解与生图只是检验协作机制的两个使用场景。机制应允许主 Agent 将有边界的任务交给 App 登记的其他执行者，等待其结果，按依赖继续工作或交付成果。不能要求主 Agent 本身具备全部能力，也不能让每个 App 重写委派、等待、关联、取消与结果接纳。

| 所有者 | 职责 |
| --- | --- |
| Core 内核 | 保持已有调用、预算、取消及状态提交保证；跨执行者的最小基础缺口仅由 M0 原型证明后确定，不预授整组协作职责 |
| Support／可选 Kit | 在现有 Core 保证上提供可替换的装配、安全关联和局部组合；已有 runChildren、Waiting／Durable 的职责不因增补移入内核 |
| App | 提供实际 handler／Provider／工具及输入输出合同，登记可调用项和本次允许范围，提供真实身份、资料访问、授权、存储和业务验收 |
| 模型或外部服务 | 实际执行识图、推理、生图等工作；其能力事实与服务协议由接入方负责 |

Core 不内置“先识图再推理”的必经流程，不根据模型品牌或图片关键词选择服务。不新增模型能力目录、厂商支持矩阵、专用识图／生图 Provider、模型推荐或图像质量评测作为本案交付。

### 1.1 主审价值判断与可证伪条件

主审判断值得保留本增补，价值在不同执行者之间可复用的父执行关联与安全接线，而非再提供一套泛化任务引擎。现有 Workflow 已能表达依赖，工具／ModelCalls 已能登记调用，Waiting／Durable 已能组织有界等待；这些能力本身不算本增补新增收益。当前 createChild 固定继承父 Provider，ModelCalls 的尝试预算也不自动证明内部调用共享父 Runner 账本，跨这些入口的组合保证需要明确验证。

增补成立须在同一任务、相同权限／预算／取消／接纳要求下，对照普通 App 组合与推荐接线，指出真正减少的重复规则和容易错配的关联：父子身份、共享资源边界、等待与结果对应、迟到隔离、错误归属和显式接纳。不能以少几行包装代码或多一层注册表证明价值。

若现有公开合同已经足够，则交付其可复用接线、连续用例与确切保证，优先扩充已有入口，不预定新“参与者”实体、目录或调度器；仅有原型可复核地证明现有合同无法安全表达时，才补最小执行合同。若连重复安全接线和可操作收益都无法证明，则不新增公开机制，保留已有组合及范围明确的使用说明。图文与生图示例必须能替换成普通自定义执行者而保持这些保证，避免以具体能力掩盖机制价值。

M0 对照须逐条列授权、计量、取消、身份／代次、迟到隔离及接纳规则的执行者、宿主前提和重复维护点。候选仍要求 App 手工同步相同规则、仅搬移回调、需要第二份登记，或现有组合已满足全部要求且没有安全接线收益时，不通过新增机制门槛。行数与接口数量不单独构成收益。

M0 必须分别论证父子模型调用的跨绑定缺口与任意 handler 的组合缺口；前者不能为后者提供抽象必要性证明。公开合同尚未必要，不等于用户所需的协作组合没有价值。

## 2. 两个协作示例

### 2.1 主 Agent 委派图像分析

App 登记图像分析执行者并提供调用实现。主 Agent 接到一个图文任务后，可以通过协作入口提交相关问题与材料引用；执行者返回有来源的结果，主 Agent 据此继续推理，也可以针对指定材料发起有界补查。

框架负责让请求、材料引用、子执行和返回结果准确关联，保留输入的图文顺序以及引用关系；分析内容是否充分、模型如何收到图片、使用什么接口由 App 的执行者实现。Core 不把返回的文字当成已核实事实，不替 App 判断视觉转文字是否满足业务要求。

### 2.2 主 Agent 委派图像生成

App 登记图像生成执行者并提供调用实现。主 Agent 可将生成任务交给它，即使主 Agent 自身不能生成图片。框架等待执行结果，将产物引用交回父流程，或者按 App 声明的交付方式输出。

框架不生成图片、不规定生图服务或参数，也不因主 Agent 名称变化而切换逻辑。产物可以是图片、文件或其他 App 结果，协作机制保持同形。请求被接纳、等待中、执行失败、状态未知与成果已接纳必须分清，不能把任务提交当成果完成。

以上两例可以串联、并行或单独执行，其依赖由 App 声明或主 Agent 在已登记且获准调用的范围内选择。业务编排可以变化，执行保证不变化。

## 3. 参与者登记与通用合同

“参与者”仅为文档中的执行者统称，不预定新的公共实体、ID 空间或目录。集中声明是单一事实来源要求：优先直接消费或引用已有工具、ModelCalls 绑定、handler／Workflow 定义，沿用稳定标识、职责说明、输入输出校验和执行入口。仅有实际安全合同缺口时才补必要描述，不重抄既有清单，不登记模型品牌能力表。

模型可见的说明、本次可调用投影与真实分派来自同一份定义。共享定义不保存账号、当前授权或运行中状态；投影按本次主体生成。启动、恢复、结果接纳和真实提交时分别按当前条件复核，不能把旧投影当持续授权，也不能靠隐藏模型说明代替执行检查。资料解析、授权事实与诊断脱敏由 App 端口提供。

同一合同支持普通对象、原型方法和自定义 handler，保留真实接收者。执行定义与本次运行分开；服务实例不作为任务数据随意序列化或克隆。参与者内部可以调用任意合法实现，Core 不据其名称假设内部工具权限、成本或完成语义。

一次委派明确父任务、目标参与者、输入／材料引用、依赖、局部限制和结果合同。图文内容或产物引用复用既有有序内容／资源合同；实际资源解析和访问许可仍通过 App 端口。执行之间只传递声明的数据与引用，不默认复制完整对话、凭据或可变父状态。

子结果先由声明的校验／接纳端口检查，再进入父状态或后继步骤。部分完成、失败、取消、超时、未执行、等待及未知状态不得伪装成功；分歧需要评审时复用丙案 ResultReview，不能由框架凭多数或到达顺序决定业务正确性。

定义标识与定义／输入合同版本、一次委派逻辑身份、每次执行尝试及接纳位置分别可辨。跨重试稳定的副作用幂等身份不能变成每次新的尝试 ID；接纳必须原子比较当前有效尝试或等价代际条件，隔离父任务仍存活时的旧尝试迟到。恢复核对已保存定义版本、输入版本和成果身份；定义缺失、绑定含义或输入合同不兼容时，在新副作用前明确拒绝或按已声明迁移，不静默交给新实现。没有新增保存合同的组合不为填表制造格式版本。

## 4. 原生协作需要承接的保证

协作保证由 Agent Core 包提供可复用的实现，不等于都由内核持有。逐项登记执行者、宿主前提、失败表现及证据；只有 Support／Kit 在既有保证上无法安全实现的最小基础缺口才进入 Core。不能将公共安全接线全留 App，也不能让内核识别所有局部协作状态。

### 4.1 唯一推进者与持久边界

| 操作 | 请求内组合 | 显式启用跨请求组合 |
| --- | --- | --- |
| 查询 | 只读取已有状态／结果，不启动工作 | 当前授权下读取记录，不 resume、不分配新额度 |
| 子结果登记 | 子调用返回对应结果，暂不推进父流程 | 回调／答复仅登记对应成果或回执，不独立启动后继 |
| 校验与接纳 | 父调用中的唯一接纳入口核对身份、代次和结果合同 | 同一个显式推进入口通过 App 原子条件端口比较有效尝试、输入／定义版本、已接纳状态及回执 |
| 父状态提交 | 沿用 Workflow 提交／选路或明确普通 handler 的顺序 | 由选定的有界 Durable 步骤及宿主记录确认状态、接纳事实与下一位置，不把不同存储键的锁当同一事务 |
| 下一步启动 | 已声明路由／编排依据已接纳结果推进 | 只有上述推进入口在持久事实确认后继续；重复恢复读取同一结果，不能再推进一次 |

M0 选择一个明确恢复单位并映射现有记录：父任务、稳定子操作、当前尝试／代次、定义与输入版本、子成果引用、接纳／提交回执及后继位置由谁保存、何时确认。子成功但父保存确认丢失时先读回／对账，不能只凭等待门 resolved 重做子动作或跳到下一步。恢复仅在明确启用时增加这些前提，不承诺任意子图或持续远端任务自动恢复。

### 4.2 计量、取消与资源边界

受控模型／工具调用使用真实共享执行端口，明确同一次实际尝试由哪一层扣额、何时扣额，外层何时仅关联诊断。ModelCalls、runOperation 与子 Runner 包装不能对同一单位重复扣减，也不能以外层一次调用掩盖内部独立满额调用。不同单位可有独立限制，不伪装成已合并的全局账本。

App 内部调用须遵守约定端口；不透明 handler 只可承诺框架可观察的委派准入、等待期限与结果隔离，内部消费和远端运行不自动受 Core 强制控制。App 的执行政策须明确是否接受该独立有界资源域；要求全域强限制却无法提供对应端口时，在派发前拒绝这一受限路径，而非虚报受控。这里描述执行前提，不新增模型能力目录，也不改变旧普通 handler 入口。

取消分清停止新分派、停止本地等待、发出取消请求、远端确认停止与停止状态未知。框架不能强制终止任意 JavaScript 或外部任务；忽略 signal 的旧尝试仍可能完成，但失效结果不得接纳。外部额度／并发何时释放依据真实确认，不因本地等待结束自动返还或重发工作。

外部动作无法在有限时间确认时保留未知并转入已声明查询／对账，不伪造失败或安全重试。已发出的本地原子保存及确认读回仍按既有合同 settle 后释放排他；不能仅超时抛错就假设保存不会迟到落盘。不具备有界确认前提的端口不承诺有界退出。借用服务不擅自销毁，迟到成果的释放／保留由明确所有者处理。

并发上限、待派发数量、输入／结果体积及引用集合须有有界政策；不隐式改变现有入口的默认并发和失败语义。诊断关联父任务、子执行、调用和产物引用，保留真实停止原因，不默认记录媒体正文、可访问私有 URL、凭据或内部推理。

### 4.3 失败、部分结果与提交

默认沿用既有 runChildren 的首错停止、取消兄弟、失败抛出及全部接纳后按声明顺序提交的合同；不暗中将旧入口改成 all-settled 或部分成功继续。框架对取消的隔离不证明外部工作已停止。

| 情况 | 调用方可观察行为与推进边界 |
| --- | --- |
| 全部成功 | 依既有结果合同返回，校验接纳后才推进 |
| 单分支失败 | 默认按既有入口抛错并停止组；可观测成功事实不自动成为可推进成果 |
| 取消／超时 | 按当前执行合同结束等待与接纳；已开始动作的外部事实仍需确认 |
| 等待 | 仅在启用相应 Kit 时返回其局部等待／句柄，不算调用已完成，也不新增所有结果必处理的全局 union |
| 外部结果未知 | 保留关联并先查询／对账，不自动重新派发 |
| 一项已提交、后项失败 | 不承诺组事务或回滚；按已保存逐项回执恢复，已确认项不重交、未知项先对账 |

执行完成、结果接纳和业务提交分别记录。若场景需要部分成功推进，必须显式选择策略并定义哪些依赖可用、哪些结果仅供观察；复用现有分支结果合同或必要的局部扩展，不覆盖默认失败合同。普通 handler、请求内错误与启用持久后的恢复分别给出连续读取方式，不强制新的统一状态机。

## 5. 现有机制复用与待验证缺口

| 当前基础 | 可复用内容 | 增补案需要核对 |
| --- | --- | --- |
| createChild／runChildren | 父子预算、取消、隔离与受控汇合 | 当前 createChildBound 继承父 Provider；跨不同执行者的安全接线须用原型证明，不能宣称已自动支持 |
| ModelCalls 与已注册工具／handler | 多绑定登记、输入输出断言、尝试预算及统一调用入口 | 与父执行的账本、取消和诊断关联是否完整，避免平行执行循环或重复计账 |
| Waiting／Durable | 等待答复、持久步骤、重建和未知副作用对账 | 等待的是子执行还是人工答复、结果与下一位置如何接纳，必须沿各自现行合同表达 |
| ResultReview／ReviewDecision | 分歧记录、独立覆盖与裁决关联 | 子结果有分歧时可选接入，不变成所有委派的必经评审流程 |
| 乙的有序内容、资源引用和生命周期 | 携带图文数据与结果、请求或异步操作的既有合同 | 只复用合同；实际模型／服务接入不列入本案的新增能力交付 |

本案新增的是协作组织与跨执行者的通用接线，不以框架具备图片理解或图片生成为验收条件。

## 6. 与甲乙丁的边界和阶段

甲提供可靠执行、等待和恢复基础；乙负责其已有模型协议、内容及调用生命周期合同；丙增补负责在这些执行入口之间组织协作。丁负责长期术语、公共入口、执行身份、保存格式与兼容收口。参与者的真实实现归 App 或它接入的其他库。

公开名称按长期职责定稿，不以单一模型、图片、OCR 或生图命名通用执行合同；不把一次工具调用强称为完整 Agent。定义、调用目标与运行主体的身份不能因统称“参与者”而合并。模型能力与协作机制分别维护，不因更换执行者而重写框架编排。

| 阶段 | 交付 | 验收依据 |
| --- | --- | --- |
| M0 合同与探路 | 既有入口→实际缺口→同安全对照→增量归属记录；计量表、操作权责表、有限恢复单位及默认失败合同；渐进公共入口草图 | 两份同任务接线证明逐条保证及前提，覆盖受控调用与不合作黑盒；普通对象／实例 handler→异构委派→串并行→可选跨请求时，标明新增配置与保持的执行／结果读取合同。必须按下列 A/B/C 出口裁定，不以原型存在就自动建设新机制 |
| M1 所选分支的协作交付 | 按 M0 裁定复用既有定义和调用入口、抽取确有收益的接线，或仅补被证明必要的最小基础合同 | 不增加重复登记；不同自定义实现能替换且公共安全关联由包复用，不依赖具体模型能力。A 分支无新增运行代码任务 |
| M2 显式恢复与接纳 | 需要跨请求时复用有界等待、继续、查询和提交端口；请求内路径独立可用 | 旧尝试迟到、新旧定义、重复回执、双恢复竞争、子成功父保存确认丢失、局部提交、取消后未知及忽略 signal 有确定性证据；不将本阶段配置强加请求内路径 |
| M3 使用与稳定交付 | 将 M0 草图落为确定性公共入口示例，图文／生成委派场景可替换为普通执行者；按实际改动同步消费者与资料 | 至少一条登记→本次可用投影→确定性提议／选择→真实分派→等待／汇合→校验接纳→后继／产物交付纵切面；未知／未授权目标在副作用前拒绝。按分支交付独立可运行例子，不要求模型服务接入 |

M0 的三个合法出口：A，既有组合足够且无额外接线收益，只交明确的说明和参考用例，结束新增运行机制工作；B，既有 Core 合同足够但有重复安全接线，补 Support／可选 Kit 或既有入口的最小接线；C，存在原型可复核的不可替代缺口，才增加最小基础合同。M1—M3 按所选出口及实际启用的持久能力执行，不以阶段标题倒逼新实体或新 API。

M0 明列沿用字段、可从既有定义机械绑定的字段及真正新增信息，不增加第二份 ID／输入输出合同。M2 至少覆盖子成功后父保存确认丢失、同回执重复、两个恢复者竞争、旧进程在新尝试后返回，以及先提交一项后另一项失败的有限组合；这些是后续确定性验证，不是本轮已通过的测试。
