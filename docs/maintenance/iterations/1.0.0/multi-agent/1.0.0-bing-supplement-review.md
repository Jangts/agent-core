# 丙案协作机制增补：八角色审议与取舍记录

日期：2026-11-25。阶段：设计审议完成，八方首轮及八名原提出方回查均已收齐；没有待九席表决的具体分歧。使用宿主 `eight-role-review` Skill，按八名独立子 Agent 与主进程 M 的九席规则处理必要分歧。本轮不编码、测试、调用模型、迁移或发布。提案见[协作机制增补](1.0.0-bing-multimodal-supplement.md)。

## 1. 不可变范围与主审价值判断

用户要求提供协作机制，实际执行者由 App 接入；模型能力、模型选型、视觉／生图实现和效果评测不在范围。图文与生图只作为替换执行者的协作例子。

主审在派发前独立判断：值得保留的目标是跨不同执行者的父执行关联与安全接线。Workflow 依赖、工具／ModelCalls 注册和 Waiting／Durable 本身已经存在，不算新增收益。增补需要同任务、同授权／资源／取消／接纳要求下证明减少公共安全关联的重复维护；普通包装减少行数或新增目录不足以证明价值。已有合同足够则复用接线与示例，有可复核缺口才增加最小执行合同；无实质收益则不新增公开机制。这一判断写入首轮提案 §1.1，允许 R4 推翻。

## 5. 影响面与替代路径摘要

R8 的八项均为静态条件风险，未编造事故或概率：C03/C07 涉及已经发生后无法靠代码回退的费用与副作用；C04/C08/C11 涉及错误接纳与历史身份；C12 涉及不可撤回的资料披露；C13—C15 涉及默认行为、依赖和资料传播。缓解设计不等于已实测风险消失。

- 不改：公开面和格式变化最少，但已存在跨入口组合的重复责任继续由 App 承担，当前 child 路径不能直接证明异构调用保证。
- 最小改：先明确现有合同组合及可复用安全接线，风险较小；黑盒内部消费、远端终止和跨进程原子性仍依赖真实端口。
- 必要基础扩展：仅 M0 的具体反例能够触发，扩大公开面、执行身份和格式责任须承担长期维护与定向升级验证，不以“原生协作”口号直接选择。

R8 原意见的覆盖限制保留：未检查具体模型、服务收费／取消、设备、视觉质量或部署运行指标，均不列本案验收。相邻仓只按实际契约追踪，不新增仓库迁移或部署授权。

## 8. 最终判断与决策边界

主审最终价值判断：值得推进受限 M0，目标是形成可复用、可解释且不误报保证的跨执行者组合。现有 API 的充分性与新增公开机制的必要性均尚未被本轮静态审议证明；这不妨碍按明确产物完成探路，但不允许提前确定新实体、通用调度器或整组内核扩张。
