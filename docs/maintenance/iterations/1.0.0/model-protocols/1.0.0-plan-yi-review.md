# Agent Core 1.0.0 乙计划：七方设计审计与重设计记录

日期：2026-11-25。范围：乙计划的独立规划、设计审计、源码复核、反方审查、第二版整合及第三版分歧对齐。当前第三版方案见[乙计划](1.0.0-plan-yi.md)。本记录不表示代码已实施、测试已通过或 1.0.0 已验收。

## 1. 方法与检查基准

沿用[甲计划评审](../execution/1.0.0-plan-jia-review.md)的七方方式，分批只读评审，主审统一修改文档。独立规划方只收到用户目标、架构原则与源码入口，没有阅读乙计划；反方明确可以推翻全部前提。其余角色按主题审阅乙计划和相关源码，不是七种模型投票。

按仓库检查标准选择 L0 范围与授权、L1 接入一致性、L2 分层与复用、L3 协议和类型、L4 恢复及并发、L5 身份与信任、L6 预算和资源、L7 验收证据。检查对象是设计，现有代码用于验证基础与缺口，不能将未实现的目标当成运行缺陷。

主审读取当前项目 AGENTS.md、设计分层、公开模型契约及消费者，保留既有和未提交修改。七名评审不并发修改方案或运行源码；第二版整合期间仍在评审的角色被告知文档已更新，结论按实际所读版本处理。首轮意见不冒充修订全文已获七方再次验收。

## 3. 主审源码复核

路径相对包根，行号以本轮静态工作区为依据。

- src/structs/model/messages.ts、chat-provider.ts：当前 Provider 只有 stream，消息以字符串、图片、工具调用为主，输出 part 只有文本或函数片段。可扩展抽象存在，但完整多模态、终态和特殊生命周期尚无公共合同。
- src/model/runner.ts:1073–1130：消费 Provider 迭代后同步 finish，发布 parsed、写 journal、生成成功回执。新增任务接纳／连接打开不能直接复用为生成完成。
- src/support/model/completion/default.ts、session.ts：现有兼容 Provider 已校验 finish_reason 与流结束，不得把“Core 中性合同缺显式终态”写成“现有内置 Provider 会把断流当成功”的已证缺陷。
- src/model/preparation.ts:140–163、options.ts：显式读取并冻结既有字段；只扩 TypeScript 类型不足以保留新内容、签名和参数，必须同步快照与准备路径。
- src/model/token-budget.ts:72–88、structs/model/runtime.ts：计量器输入是 messages／functions／json，无法自然证明远端历史、媒体和厂商最终 wire 的精确计量。请求内额度也不自动成为跨进程账本。
- src/context/journal.ts:54–63、model/message-diagnostics.ts：业务结果深克隆，当前脱敏只特判图片和工具参数；新增 continuation、媒体和资源必须独立处理，不能直接塞入普通结果或日志。
- src/model/transports.ts、support/model/session.ts、structs/model/runtime.ts：已有文本 string、单选择与 session 结果投影。新增事件须在 Runner 路由，不能强迫上层 collector 理解所有厂商事件。
- src/kits/durable.ts:268–329：已有 completed／not-executed／unknown 对账与持久预留；可复用保证，但不会替上游创造幂等或查询能力，也不是现成的 Batch 逐项账本。
- 仓内消费者 apps/server/src/microcola/ai/providers/compatible-chat.provider.ts、apps/banker-api/src/infrastructure/models/provider.ts 继承 CompatibleModelProvider；Banker 的 transport.ts 通过预设选择 interaction。乙计划须吸收普通接线负担，保留宿主业务政策，不能只交付一个新工厂便宣称迁移完成。

补充核对 src/model/settings.ts:115–116 仅绑定 stream，src/model/binding.ts 固定该 Provider 合同；新能力必须同步穿过准备、绑定和子 Runner，不能只扩类型。

以上均为静态事实和设计风险，没有运行故障复现。

## 4. 官方资料核对及边界

主审核对以下官方资料，仅用于确认设计必须保留的语义，不据此宣称整个协议矩阵已固定：

- [Gemini Interactions](https://ai.google.dev/gemini-api/docs/interactions)：区分服务端会话续接和无状态路径，并提供后台执行；支持目标须按具体模型／端点核定。
- [Gemini thought signatures](https://ai.google.dev/gemini-api/docs/thought-signatures)：有状态与无状态签名保留方式不同，不能只以一段普通文本代替。
- [Gemini Live](https://ai.google.dev/gemini-api/docs/live)：持续媒体、打断和工具交互要求实时会话合同，不能只映射普通有限输出流。
- [OpenAI background](https://developers.openai.com/api/docs/guides/background)：任务查询、远端取消、恢复事件位置与数据临时保留有独立语义；store:false 不等于后台任务完全没有远端临时保留。
- [Claude thinking 文档入口](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)：实际推理模式与模型能力仍需 P0 固定版本，不能以历史参数映射代替当前协议审计。

本轮未进行所有端点的完整字段逐项核对，未固定生产模型列表；这些是 P0 明确交付，而非已验收事项。

## 5. 第二版的实质修改

1. 用同生命周期、等价能力及可移植定义约束一致体验；保留普通调用的精确返回类型。
2. 逐格分离目标、实现和证据，原型前置到 P0，完整生命周期仍在乙计划范围内。
3. 分离 schema 编译、能力事实、授权和可执行限额，不靠 profile 提升权限或伪造验证。
4. 统一事件先由 Runner 路由，collector 保持专注；受控续接、业务结果及不可序列化资源分开。
5. 明确提交未知、对账、清理、恢复授权、批量逐项预留及实时撤权，复用甲计划机制而不另造调度器。
6. 提供默认接线和旧 Provider 局部桥接；保留最简对象、原型方法、继承入口及自定义 transport 的验证路径。
7. 可选端口在配置／绑定／子 Runner 中保真；单次协议动作与等待策略分开；明确 continuation 的封装、存储和资源所有权。

### 7.1 说服与投票规则

先记录原意见、现处置及理由，再由原提出方独立回应。主审被说服时直接采纳，不为证明原方案正确而强行驳回；原提出方接受主审理由时记录具体接受范围。有不能对齐的具体取舍，先固定 A／B 及各自理由，再交原提出方之外的其余六名评审投票，主审和原提出方不投；每票须有明确选择和理由，不把不响应或附条件意见记成赞成。3:3 交用户决定。投票期间不悄悄改变 A／B；实现困难或待 P0 固定的参数不自动等于架构争议。
