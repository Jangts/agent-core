# Agent Core 1.0.0 丁方案：概念正规化与稳定交付

日期：2026-11-25。修订：第三版及实施状态补记。状态：七方设计审议及原意见逐项回查、甲乙丙原设计者对齐已完成；D0 长期名称已定稿，命名迁移和跨项目消费已实施。实际候选、兼容例外、验证及剩余边界见[实施与验收记录](1.0.0-ding-implementation.md)，不以此标题宣称已发布 1.0.0。基线包含甲乙丙共享工作区的实际改动；各案设计、实现、专项证据及未实施增补分别核对，不以 package.json 的 0.9.0 判断完成状态。审议意见、取舍及原提出方回查见[丁方案审议记录](1.0.0-plan-ding-review.md)，各方实际确认范围以记录为准。

## 1. 目标与范围

1.0.0 表示核心抽象可以长期依赖、公开行为有兼容承诺、第三方可以独立接入，后续演进承担维护与迁移责任。丁方案负责概念正规化、公开合同收敛、接入与发布准备；不重复建设甲的可靠执行和组合能力、乙的模型协议与生命周期能力。

丙主案设计及实际交付分别见[多 Agent 分歧发现与处置](../multi-agent/1.0.0-plan-bing.md)和[实施记录](../multi-agent/1.0.0-bing-execution.md)；尚未实施的[多执行者协作增补](../multi-agent/1.0.0-bing-multimodal-supplement.md)单列依赖与范围决定，不算既有交付。丁按甲乙丙各自最新合同处理新增概念及相互依赖，不占用其设计或改变其完成状态；计划标题、勾选或旧测试统计不代替相应时点的实际合同与验收记录。

概念调整覆盖整个 Agent Core 库：Core、Support、Kits、公共类型及子路径、内部实现、诊断和序列化字段、开发工具、模板、示例、两种语言文档、随包 Skill。跨库同步覆盖 main 的小可乐与 Banker、pages 的 Agent Core 文档站，以及实际受影响的 MockGPT 契约。其他业务的独立术语不因同名被替换。

计划阶段交付为本文。用户后续已授权拆分实施，三域源码、公共合同和实际消费者调整见实施记录；按已定版本同步为 1.0.0；保留 0.9.0 未发布开发历史，不提交、不发布或部署。

## 2. 正规化原则

- 先写实际职责、输入输出、所有者、生命周期、副作用和权限，再定名称。采用能准确表达职责的通用词，不因流行而引入并不存在的 Agent、Memory、Session、Trace、Protocol 等承诺。
- 同一概念使用一个规范名称；不同概念保留必要限定词。统一不等于把所有上下文叫 Context、所有处理单元叫 Task 或所有执行记录叫 Trace。
- 术语覆盖英文符号、中文说明、配置键、提示词、诊断事件、文档标题和 import。修正名称时同步消费者，不能只改可见标签。
- 不统一具有不同错误、原子性、授权或执行顺序的实现。重命名默认保持行为；发现行为需改动时单列工作项和验收。
- 已发布的 @jangts/* 包身份不变。公共子路径、字段及序列化格式可提出破坏性迁移，但必须逐项列出影响和策略，不因“正规化”直接删除公开入口或旧数据。
- 历史验收和迁移记录保留当时名称；不伪造历史，也不把它们作为当前命名示例。
- 公开概念选名记录实际职责、现名、通用候选、保留方案及取舍依据；依据可以是现有标准／协议、成熟接口惯例或本库真实用例，不凭“听起来通用”定稿。涉及外部标准时核对一手定义及版本，不宣称本地组合名就是行业标准。私有局部变量不逐个开展行业调研。

### 2.1 首次正式定版的长期命名约束

1.0.0 是概念体系的第一次正式定版。对规范概念、模块名称及其公开符号，按将长期沿用、通常不再更名的前提选择；后续确需改变，通常应源于模块职责或概念模型的实质调整，而不是风格偏好、流行词变化或单纯更短。版本兼容和弃用机制用于处理必要变化，不能成为本次仓促定名的退路。

D0 每个规范概念除当前定义外，必须审阅：

- 职责稳定性：名称表达长期职责及实体，不绑定当前实现、单一厂商、临时阶段或偶然调用路径。
- 扩展适配性：以已有需求及甲乙丙的明确扩展方向检验含义是否仍准确；不为假想的全能能力起过宽名称，也不为当前局部实现起过窄名称。
- 整族一致性：概念、模块、类型、工厂、方法、字段、配置、中英文说明及实际 import 能组成可解释的一组；能区分邻近概念而无需反复补充例外。
- 选择依据：对比现名、准确的通用候选及保留方案，写明推荐与淘汰理由；已有名称准确时可以保留，不以改名数量作为成果。
- 定稿证据：通过完整真实用途示例和相关方案设计者的跨案审议，关闭具体歧义。尚有职责分歧或未决名称的条目不能标为定稿，也不能先以临时名进入 1.0.0 稳定公开面。

此约束针对长期概念与合同，不禁止内部实现优化，也不要求所有局部变量永久冻结。本文 N01—N20 仍是审议和定稿输入，七方原意见对齐不等于这些候选名称已获最终批准。

## 3. 源码排查结论

以下路径相对 packages/agent-core。结论来自源码和消费方静态阅读，不是运行验收；目标名是本方案建议，尚非已发布接口。

### 3.1 优先调整：同名异义与名称暗示失真

N01—N10 是需要审阅的语义域，不是必须逐项改名的指标。具体导出函数、工厂、文件及 JSON 键须在 D0 补齐一对一映射或保留依据，不能仅完成表内代表符号。N03、N05 的取舍须经整组用例比较后关闭；N02 保留两类公开扩展合同，不预设内部化。

N01 同族映射包括 ModelStageTransportRegistration → ModelStageInteractionRegistration，以及 PreparedModelCall 的继承、Runner 注册参数和精确返回类型；PreparedSessionTransport / SessionModelTransportRegistration 必须同时盘点，但撤回预先定为含 Session 的新名称。有限单次文本/多工具结果与真正实时会话的连接、轮次和关闭生命周期一起比较，不能只因存在多调用就永久称 Session。单选不是所有交互的基类语义，多调用结果保留文本、调用关联及非致命解析问题。

N04 同时盘点 CatalogGoal、CatalogTask.goalId、CatalogTool.goalIds、AgentCatalogPorts.goals/tools、supportsGoal 及其消费者。领域工具与执行／生命周期工具是两组实体，须分别命名其目录、ID 空间及关系方向；不得只把两端都改为 tools 后失去关系。N10 只迁移 Kit 的扩展合同，Core 的 ExecutableTool、ToolDefinition、RegisteredTool 保留基础用途，逐 import 路径核对聚合冲突。

N06 同时覆盖 diagnostics/native-sub-flow.ts 的原生埋点生产者：当前统一记录合同标为 origin: reported，但生产者既可以是 App，也可以是显式接入的 Core／Kit 边界。新说明必须如实区分生产者与证据强度；不能把所有记录描述为 App 手写，也不能由原生埋点推断完整执行或授权成功。真正的调用身份和结果仍由 invocation 合同关联。

### 3.2 应核实职责后收敛，避免机械改名

| 编号 | 当前概念 | 处理方向与判断条件 |
| --- | --- | --- |
| N11 | GoalTool.planIntent、scopePolicy / targetPolicy、preparedHandoff、delegates / auxiliaryActions | planIntent 注释实际为 planning action，建议 planningAction；scopePolicy / targetPolicy 若只是模式标签则改 scopeMode / targetMode。preparedHandoff 是 unknown 的 App 标记，先逐个读取消费者，不能硬改成布尔 isPrepared。delegates 需区分允许的处理器 ID 与真正的 Agent 委派；非 Agent 不称 agentIds。auxiliaryActions 若承载 UI 手动动作须保留所属用途 |
| N12 | ChatProvider、ModelRunnerProvider 和 BoundModelProvider 的共同合同已包含纯 operation/realtime 及生成能力组合 | 随乙最终合同评估 ModelProvider 共同入口及 ChatProvider 专用入口，不强迫纯 operation/realtime Provider 伪造 stream，不丢失组合可选性、receiver 与绑定状态；共同入口名称不能把所有 Provider 限定为 chat |
| N13 | ModelFunction、FunctionCallDelta、NativeFunctionCall、ToolProposal、ModelSelection、ToolInvocationRequest | 通用本地模型工具调用比较 ModelToolCall / ModelToolCallDelta，函数专用 wire 结构保留 Function。Proposal / Selection / Invocation 不合并；厂商托管执行事件与本地工具提案及真实执行分开，统一 Tool 字样不等于支持任意工具类型或同等授权/回执 |
| N14 | ContextTrust 的 instruction / server / user / tool | 保留现行 trust 安全分类：context/fragments.ts 依据它禁止 user/tool 提升为 system，context/audit.ts 保护 instruction 内容。本轮撤回 trust → source 候选；若确需新增来源字段，另列需求且不替代安全分类。任何分类调整必须证明所有分支安全等价 |
| N15 | Reflection / ReflectionTask | 阅读与分析运行证据、产出 observed / hypothesis / recommendation；仅有分析能力的公开用途称“运行分析”。只有确有反思评估过程才保留 Reflection，不能宣传为自动学习、自我改进或自动策略优化。是否改 RunAnalysis 由完整输入输出与执行路径确认 |
| N16 | Delivery / DeliveryStage | 当前是带完成结果的有序管线，能早结束且阶段可有副作用。若所有消费方都用于交付回复则保留 DeliveryPipeline；若公开承诺通用处理则命名 ResultPipeline。不得仅因存在 stages 就合入 Workflow 图或普通 Normalization 管线 |
| N17 | Support、Kit、structs、types、Definition / Options / Settings、define / create / register / bind | 保留职责模型；建立一致写法：Definition 描述能力，Options 描述调用或构造选项，Settings 只用于实际持久绑定配置。define 构造/校验声明、create 创建有生命周期实例、register 写入注册表、bind 绑定依赖。与真实实现逐项核对，不为形式统一制造包装层或全面移动目录 |
| N18 | Engine 的 AgentCheckpoint、restoreCheckpoint 与 DurableCheckpoint | 前者须按真实承诺区分 branch/data snapshot 与可恢复执行位置；优先比较 AgentSnapshot，但不直接改运行方法。DurableCheckpoint 有顺序任务恢复合同，不与前者合并。保留 checkpoint 时必须明确其保证，不能因通用名扩大恢复能力 |
| N19 | 乙新增 LifecycleContext、LifecycleRun、OperationAction / Status，与通用 OperationContext<App> 及工具 lifecycle 并存 | D0 比较 ModelLifecycleContext / Run、ModelOperationAction / Status 等模型限定名，模型生命周期与工具生命周期各有作用域；按乙最终合同增量核对，不现在改乙源码或强迫 Provider 实现全部端口 |
| N20 | 丙的 ResultReview、ReviewDecision、ReviewChoice，以及材料冲突、字段合并冲突、认知分歧、覆盖、答复与接纳 | 分别定义冲突种类、发现/确认、检查覆盖、处置建议、裁决答复和实际动作接纳；不统一为裸 Conflict/Status。Waiting resolved 只证明等待答复已记录，不证明争议解决、事实正确或动作已接纳 | confirmed finding 不是事实真理，完整覆盖不是正确性保证，裁决不替代当前授权及原子接纳；contentRevision/policyRevision/sourceVersions 与存储 CAS 代次分别定义 |

N11—N20 是按实际用途处理的语义域，D0 必须给出采纳或保留的依据及唯一目标名，未决不得散落实现。N14 已明确保留安全合同，不作为普通重命名候选。新名字不能掩盖现有类型过宽或职责混合，必要时拆出合同工作项。

N14 的安全等价验证覆盖角色提升限制与上下文处理前后结构审计两条路径，不能只比较枚举值。N17 的命名规律服从真实合同：defineRegistrationCatalog 构造时绑定回调，install 按序同步执行，predicate 能观察此前安装结果，后项失败不回滚此前安装；不得因称 Catalog 就提前求值、改时序或强行改为通用 Registry。相关定向检查保留 receiver、同步拒绝与局部失败行为。

长期命名审阅同时覆盖 N18 的 exportCheckpoint/restoreCheckpoint/fork 整族方法，不只换 AgentCheckpoint 类型名；N08 不得暗示完整 VCS 或运行调度，N07 保留重复 visit、部分记录及 coverage，不暗示完整追踪或恢复日志，N06 的 reported 表达证据性质而非限定 App 生产者。N17 中 defineDurableTask/defineWaitGate 已绑定端口并返回可调用实例，不为词法统一另造声明层。

### 3.3 明确保留，并统一解释

| 概念 | 规范解释与不得混用的对象 |
| --- | --- |
| AgentCoreEngine、ModelRunner | Engine 负责运行编排；Runner 拥有模型调用保证。不能统称 Agent，也不因命名统一合并两者 |
| Workflow、Node、Route、State | 工作流、执行节点、路由、运行状态；真实嵌套工作流才叫 subworkflow。App 自述步骤不是 Node |
| Tool、ModelTool、ExecutableTool、ToolRegistry | 共同 Tool 概念下不同能力接口：模型可选与授权执行。保持层级限定，不恢复 BaseTool 等无用途的新层 |
| ContextFragment、ContextPlan、BuiltContext | 上下文片段、待装配计划、装配结果。Plan 是合法输入计划，不因含 plan 一律更名为工作流 |
| Registry、Catalog | Registry 有注册及 seal 生命周期；Catalog 为只读目录视图。不可把实际可变对象统一命名 Catalog |
| Schema、parse、validate、normalize | Schema 描述结构，parse 可校验及转换，validate 作检查，normalize 作规整。不将带转换副作用的 parse 简称 validate |
| Policy、Authorization、Availability | 策略、授权、可用性；active/discovery 不是执行授权，profile/capability 不是权限事实 |
| InvocationResult、ModelResult、ToolResult | value 与 invocation 元数据组成结果。中文统一“调用结果／调用记录”；模型成功返回不等于业务操作成功，receipt 不自动表示外部系统已确认 |
| Event、Record、Trace、Log | 发生的事件、已保存的记录、关联执行轨迹、日志记录机制；不统一成一个万能类型，不伪造不存在的 trace 标准兼容 |
| cache、agentCache、State | Engine 内存缓存、宿主缓存端口、运行状态，作用域与同步性不同；agentCache 不因可持久化就叫 Memory。中文明确所有者，若需改字段单列兼容映射 |
| checkpoint、resume、replay、retry、reconcile、fork | 检查点、恢复、重放、重试、对账、分支创建；确认未知副作用与重跑不是同一动作，禁止混称 recovery |
| Skill、Task、Operation、Session | Skill 是文本方法，Task 是任务，Operation 是异步操作，Session 是有实际生命周期的会话；随包 taskSkills 与 TextSkillLoader 保留文本限定，不包装成可执行 handler |
| stage、step、round、turn、node visit | 阶段标签、处理步骤、循环轮、用户对话轮、节点的一次访问，分别说明计数及身份。stageId 不机械改 nodeId，模型可在非工作流阶段使用 |
| Evidence、Knowledge、Retrieval、Search、Projection、Artifact | 证据、知识资料、检索过程、搜索算法、内容投影、产物引用；按现有输入输出保留，相关度分数不是证据可信度 |
| Error、Issue、CheckResult、Status | 异常、结构化问题、检查结果、生命周期状态；不同状态机不强行共用同一枚举，unknown/unavailable 不转写为 failed |

## 4. 全库覆盖与可执行清单

1. src/execution、model、capabilities、context、diagnostics、support、kits、skills、utils 与 structs 的声明及实现；枚举、错误码、事件种类、回调、receiver、持久化载荷一并检查。

### 4.1 有限基线与增量审阅

D0 固定 main、pages 及实际受影响 mockgpt 的源码输入：各仓 HEAD、相关未提交文件内容指纹和路径集合。HEAD 不代表脏工作区实际源码。必须穷举公开 exports、声明、配置、回调、事件、错误分类、selector 和保存格式，以及 §4 列出的内部模块；局部变量只在所属概念域内核对一致性，不为每个 value/context 建词条。

冻结按概念域推进：D0 登记基线和依赖，能力所有者确认该域合同及长期命名后，D1 才迁移该域；乙丙仍变化的域保留未定状态，不冻结其临时实现。变化触发明确的增量重审，D4 再固定同一最终候选的完整合同、源码和包体输入。甲案可靠执行证据以其[复审记录](../execution/1.0.0-jia-reaudit.md)的时点及实际范围为准，后续源码变化不能直接沿用旧统计。

丙域沿用先确认职责/合同、证明公共接线收益、再决定是否新增公开 Kit 的顺序；协作增补的 M0 还未关闭时，不把其临时参与者组织或候选入口固定成长期模块。丁登记与增量审阅不等于扩充内核或批准新增公共 API。增补是否纳入候选的交付范围需明确列明，不默认为已完成，也不由丁静默删除或扩大。

丙增补回查新增三组条件性交叉合同，登记后由条件触发定向审阅，不构成当前已实现能力或本轮新增阻断：

| 条件 | 丙交付的实际合同 | 丁的收口责任 |
| --- | --- | --- |
| M0 选择补可复用接线或最小 Core 合同（B/C） | 实际入口、共享计量单位、唯一扣额方、受控调用与不透明 handler 的保证边界 | 核对整族名称、默认与公开承诺；若选 A 仅补说明/示例，不制造新公共实体 |

## 5. 迁移方式与兼容边界

### 5.1 按合同种类处理

| 类别 | 方案 |
| --- | --- |
| 私有符号及文件 | 在所属模块原子调整并同步 import，保持行为；不默认迁移目录 |
| 公开 TypeScript 名称 | 映射到单一规范导出；必要的旧别名仅作显式迁移入口，记录移除期限和理由，不保留两份实现 |
| 方法、配置键、字段 | 提供完整旧→新映射与示例，新数据只写规范键。保存载荷依 §5.3 对冲突双键拒绝；其他配置若允许优先级，须逐项明确声明，不由对象展开顺序或临时猜测决定 |
| 子路径与包出口 | 单列 npm 消费方迁移；保留包名和发布身份，是否保留旧子路径由兼容策略决定，不借改名擅自缩减公开能力 |
| enum / selector / 提示词键 | 视作程序与模型的共同协议，同步生成 schema、提示词、匹配、校验、分发和断言；字符串不靠全文替换 |
| 诊断、trace、checkpoint、等待及版本历史载荷 | 逐格式选择保持原格式、局部兼容 reader、独立迁移或明确拒绝；决定支持的旧格式才适用相应 decoder 规范。源码改名不要求改存储键，副作用与 CAS 身份不得因改名重建 |
| 中英文文档与文档 URL | 统一术语和实际符号；外部已有页面路径变动时使用站点支持的重定向或迁移入口，不留下失效示例和深链 |

1.0.0 之前可以集中承担一次必要的破坏性收敛，但仍需对 0.9.x 使用者说明迁移。不能把“尚未 1.0”作为清理存量数据和外部工程的授权。对 1.x 的兼容承诺须明确覆盖公开名称、默认值、异常、事件时序、取消、结果形状和保存格式，而不只覆盖 TypeScript 编译。

### 5.2 与并行迭代协调

- 乙和丙仍变化的公开概念先登记目标与负责人，按最终合同迁移，不在其工作区实施大规模重命名。
- 已定概念可先整理术语及迁移草案；D1 只迁移能力所有者已确认的概念域，不等待所有域同时成熟，也不提前冻结未定合同；D4 统一最终候选。
- 每批交付同时调整实现、消费者及来源文档；不允许新文档先承诺尚未存在的 API。
- 发现前三方案的语义缺口单独回报并修订责任方案；丁不通过换名掩盖缺口。

### 5.3 保存格式、身份和活跃写入

1. 分别登记诊断记录、workflow trace、Engine snapshot、Durable checkpoint、WaitRecord v1、分支版本记录及乙引入的 operation/continuation 等实际保存格式及存储寻址：当前 writer 版本、支持读的版本、转换位置、读历史／恢复执行能力及拒绝行为。逐格式选择保持原格式、局部 reader、独立迁移或明确拒绝，不默认给每模块增加多版本体系。甲当前 Durable 仅支持 v2，不由丁扩大为通用旧版本恢复。它们不共享一个总版本；schemaVersion、定义 revision、CAS revision、活动指针和执行身份不混用。
2. 区分源码名称、展示名称、协议 selector 与持久身份。Durable 的 operationId 由 definitionId/revision/taskId/step.id 形成，标识稳定操作；commitId 标识一次 persist 提交，用于保存确认丢失后的精确读回，每次新提交仍生成新 commitId。仅改名或转换须保留已有值与回执关联，不能把 operationId 重算成新操作，也不能永久复用旧 commitId。语义改变才单列身份迁移，并证明不会重复副作用。
3. 对决定兼容的保存格式，先按版本选择 decoder，纯转换为唯一规范结构，再校验；等价双键归一，冲突双键拒绝，缺失依合同报错，未知或未承诺版本明确拒绝而非猜测。保持原格式时不强造转换器。旧入口只转换参数，不执行工具、不补跑任务、不自动修复状态；字段冲突不能依对象展开顺序决定。
4. 优先读时投影，不写回。必须回写时使用原存储的排他／CAS 和原子提交合同，与活跃旧 writer 协调；不得调用 create/fork/promote/run 代替格式转换。不重置 TTL、保留期、额度、attemptCount、取消状态、活动指针或未决副作用；中断与冲突不留下半转换。
5. 每批建立旧 producer→新 reader、新 producer→旧 reader 的有限兼容矩阵，写明支持或明确拒绝、接入版本和切换顺序。先升级 reader 再切 writer；旧 reader 不能读新格式时阻止无条件回退，不把重装旧包称为可逆迁移。main/pages/mockgpt 各自管理 Git 记录和产物，用同一候选身份协调，不假设一个跨仓原子提交。
6. 实际触达格式的定向案例覆盖：旧诊断读取、旧快照重建、运行中 Durable 对账、版本 CAS 冲突、转换中断重试、存储提交后确认丢失及外部执行次数。unknown 保持未知，读历史不授予执行权；恢复重新绑定真实主体与授权，不恢复旧凭据或权限结论。

以上为后续实现与验证合同，不授权迁移真实存量库。未改变的格式不为了表格完整而新增版本或转换器。

WaitRecord v1 的独立兼容项包括 definitionId/revision、taskId/waitId/subject、submission.id、expiresAtMs 及 pending/resolved/cancelled 终态；寻址键包含定义 ID 与 taskId，仅改载荷而丢失原寻址不算兼容。迁移不得重新 open、生成新等待代次、延长有效期或改变已消费答复及终态；确需换键时明确旧键定位与原子转换，而非让旧等待不可寻址。

乙的 continuation 独立登记外层 protocol/model/scope 与版本，以及历史前缀锚点、逐轮原生块和相关 endpoint 约束。迁移不能机械替换厂商 wire 字段、重算锚点或重建 scope/operation/remote/item 身份，不能丢失签名、推理块和工具关联。历史工具名变化须逐协议明确兼容映射或拒绝，不通过字符串改名伪造一段可继续的旧会话；不支持时在新的模型调用或工具副作用前明确拒绝。

丙实际交付或后续正式采用的保存对象，分别登记争议/父任务关联、contentRevision、policyRevision、sourceVersions、waitIdentity、actionId、deadlineAtMs、submissionId、裁决提交与父级执行/接纳账本；不要因共用 dispute/revision 等词就合并身份。存储位置及状态转换按真实所有者，已有 ResultReview 的请求内报告不因登记而新增持久存储。等待答复、裁决结果和业务接纳的事实分别保持；增补尚未实现的格式不得虚构为当前可迁移记录。

### 5.4 1.x 维护与兼容政策草案

- D0 明确 stable / experimental / internal 清单。已公开且未明确标实验的入口默认进入稳定审阅，不可临时改标 internal 逃避兼容责任。实现细节与私有局部名不承诺永久冻结。
- 1.x 稳定合同覆盖公开入口及子路径、类型与结果、配置默认、异常分类、事件语义／顺序和取消／计账行为。删除/改名、收窄输入、改变默认策略、增加消费者必须处理的 union 分支、改变错误或副作用保证均需做破坏性评估；不能仅以“是新增”认定兼容。
- 弃用必须有替代路径、说明和移除版本。若 1.0.0 仍分发旧别名，则按稳定兼容入口维护到整个 1.x，移除进入 2.0.0；若决定在 1.0.0 移除某 0.9.x 入口，必须在 D0 清单明确记录，并完成旧使用者升级示例。禁止未定期限的“必要时兼容”。
- 实验项的变化范围需事先明确，不能降低既有安全保证；上游模型或协议变化按能力矩阵处理，不伪造永久等价。安全修复如确需破坏行为，说明触发条件、影响、版本和迁移，不静默改变默认行为。
- 保存格式支持范围逐格式列明，区分只读历史与可恢复执行；不承诺永久读所有旧版本。不支持时在新副作用前拒绝。维护响应 SLA、固定支持年限及生产容量没有依据时不作承诺。

S4 的渐进路径是一次调用→自定义 Provider→普通 Workflow→授权工具→取消/失败→可选持久恢复；可复用同一最小参考逐步增加配置，不要求另建六个 App 或新 SDK。分别验证普通对象、原型方法／私有状态实例、自定义 adapter、泛型结果与公共入口对象身份；可选 MockGPT peer 未安装时普通路径不得误加载它，不默认宣称整个 SDK 可在浏览器运行。

参考消费者还须使用宿主自定义存储、授权和观察端口，证明这些实现可按公开合同替换，无需复制 Core 账本、登记官方厂商或继承内部实现类；可复用甲已有样例与端口，丁仅补同候选仓外接入证据，不新建并行框架。

新接入与升级是两类证据：从固定旧包版本创建最小消费者，按迁移说明升级到同一候选 tarball，保留行为及必要旧记录；不能用全新项目安装成功替代升级。SDK scripts/api-reference.mjs、scripts/compile-skills.mjs、skills 的生成目录、应用模板及 pages 的 guide/recipes/locales 都纳入同候选核对，术语解释名与可 import 符号须明确区分。

丁发现的行为缺口按所有者回到甲乙丙或新增明确丁工作项，记录阻断保证、修复方和证据，不以“已转交”关闭验收。基线发生相关变化时重验最小受影响面；未验证环境与真实模型语义保持未验证，离线成功不能扩张结论。

甲提供的 S2/S5 故障不变量单列登记：耗尽后零模型只读对账；过执行期限仍可按合同查询完成成果；unknown 不自动重跑；not-executed 不退款；请求取消不等于持久取消；迟到输出隔离不等于撤销远端副作用；恢复重新授权且不恢复凭据。丁按迁移触达面最小重验，类型检查不能替代这些保证。

S4/S6 复用甲已有公开 handler 对照、原生共享账本、四进程保存响应丢失与实际 reconcile、真实 LangChain 契约测试及其适用范围；外部 Agent 内部模型使用独立资源域，未支持外部暂停自动恢复，四进程证据不等于 SIGKILL/断电证据。丁补同候选 tarball 的仓外安装、旧包升级和站点文档一致性，不新增通用 harness 或外部全兼容承诺。Engine 宿主数据/分支快照、Durable 顺序执行位置、Family 状态版本/CAS 活动指针分别验收。

乙提供模型协议、计账、取消、Provider 组合、续接身份及能力矩阵证据，丙提供协作行为、语义检测/覆盖质量、裁决接线及故障证据；丁负责最终名称、所选格式兼容、旧包升级及同候选整体一致性。可复用相同工件/相同保证的有效证据，相关命名、字段、类型或行为变化才定向重验；不同工件的专项数字不相加、不代替候选全局关闭。

乙的真实 DeepSeek、MockGPT 本地 wire、本机 WebSocket、注入双工及 fake WebRTC 分别标注证据范围；它们不能互证其他厂商云端、真实设备、音视频质量或厂商内部费用。当前 MockGPT 的较早 pack/仓外安装与最后实时续答修正后的本地 dist 联调分属不同工件；已发布可选 peer 的旧兼容用例也不证明新协议。S6 如交付依赖改后的 MockGPT，须核对它最终候选的包体及关联版本，而不是沿用旧包指纹。

乙曾报告较早全 SDK 快照有丙 result-review/review-decision 两项失败，后续乙专项通过不能关闭这两项；丙后续专项通过也须按对应输入核对。丁将历史失败映射到当前修复、对应源码和有效证据，才能关闭候选阻断；不据旧快照断言当前仍失败，也不据其他专项成功宣称全局已通过。

S1/S2 的每条保证须登记执行者、宿主前提、失败表现和证据，不能只有所属层名称。Core 拥有其预算／取消／调用保证，App 拥有真实主体、存储原子性和业务授权，Kit 拥有局部合同；node cache 分区不是用户隔离，schema/意图识别视图不是授权，Kit 可选不等于采用后可忽略检查。低层入口不因存在 Core 就被宣称自动具备完整业务授权。
