# Agent Core 1.0.0 丁方案：七方审议与重设计记录

日期：2026-11-25。范围：概念正规化、公开合同、独立接入与稳定交付提案的静态设计审议。修订后正文见[丁方案](1.0.0-plan-ding.md)。本文不是代码实施、运行测试或 1.0.0 完成声明。

## 1. 审议方式与输入

沿用甲乙的七方方式，分批只读评审，主审统一修改文档。用户本轮明确授权提交子代理审议；七方是不同任务与上下文的独立评审，不是七种模型投票。

独立规划方使用无会话继承的新上下文，仅收到用户目标、项目位置、分层原则及甲乙边界，首轮没有阅读丁正文。反方明确可推翻全部假设。其余评审根据职责读取正文及相关源码。首批六方审首版；分层方读取时部分条目已在整合修订，明确记录实际所读版本，不伪称七方同时审阅同一静态全文。

主审按项目 AGENTS.md、接口设计及代码检查标准选择 L0 范围、L1 命名与接入、L2 分层、L3 类型与协议、L4 保存与并发、L5 信任、L6 预算保持、L7 验证和发布证据视角。源码用于确认职责和风险，不把未实施目标写成已证运行缺陷。保留乙进行中的源码和已有暂存状态；评审不写文件，不构建测试或调用外部服务。

## 3. 关键分歧与主审改变的决定

| 问题 | 首版 A | 评审 B 及依据 | 第二版决定 |
| --- | --- | --- | --- |
| trust 能否改 source | 判断更像来源，条件允许则改 | context/fragments.ts 按 trust 限制 system，context/audit.ts 保护 instruction；当前“仅来源”前提不成立 | 主审接受反例，撤回候选；保留安全分类，来源另有需求才独立建模 |
| 所有 interaction 是否 Command | CommandProtocol 更统一 | query/presentation/input/receipt 是消息家族，不一定发出执行命令 | 撤回无条件改名，D0 比较 MessageProtocol 与限定清晰的原名；内部 Command 定义独立 |
| asIntent 是否 discovery | 直接换为 ToolDiscovery | 实际是预注册集合的意图识别投影，不发现新工具 | 撤回直接改名，优先保留并澄清，用普通选择/识别/include 完整例子决定是否再调整 |
| Prepared 中间类型是否内部化 | 作为候选退出公开面 | adapter.prepare 的公共签名依赖它，collector 及 resolve 与 Runner 最终结果不同 | 两类职责均保留公开，建议 PreparedModelSelection / PreparedModelInteraction<Result>；字段变化另列合同 |
| AgentFamily 是否 History | 服务统一为 BranchVersionHistory | create/fork/merge/promote、CAS 与授权是版本管理，不只是读取历史 | 服务推荐 BranchVersioning，History 留数据视图，不创建额外包装层 |
| 全量正规化如何关闭 | 每概念唯一、D0 全库补齐 | 乙丙持续变化、内部普通变量无穷；必须有限基线 | 固定各仓实际源码输入/脏文件指纹和公开面，按语义域穷举，后续相关增量重审 |
| 历史与新数据如何迁移 | 冲突报错或优先级，必要时离线迁移 | 顺序覆盖、身份改写、活跃覆盖会影响恢复和副作用 | 按版本 decoder→规范结构→校验，冲突拒绝，未知不猜测；保留持久身份，写回走原 CAS/排他 |

上述改变是主审接受有依据的反对，并非说服各方放弃它们。通用概念采用与否仍须按真实用途定稿，不能把本次设计意见当已完成全库命名迁移。

## 4. 主审源码复核与证据范围

路径相对 packages/agent-core：

- structs/model/interactions.ts、model/selection-transport.ts、structs/support/model/interactions.ts、support/model/session.ts：存在单选适配准备、最终结果 collector 和会话/stage 分支；不能强制一个 Prepared 类型承担全部语义。
- structs/kits/domains/registry.ts、domains/catalog.ts 及 capabilities/model.ts：GoalTool 是 ModelTool 的领域扩展，CatalogGoal 与 CatalogTool 又是两组关联对象；asIntent 控制已有工具投影，不产生独立意图实体。
- context/fragments.ts、context/audit.ts：trust 参与角色限制和不可变内容审计，是安全合同而非单纯来源标签。
- structs/debug.ts、diagnostics/native-sub-flow.ts：reported 合同的生产者也包括显式原生边界，不能全部描述为 App 手写；这些记录不自动证明完整业务执行。
- structs/kits/family.ts、kits/family.ts：版本条目、活动指针、CAS、授权及写操作均存在，版本管理比 History 更符合服务用途。
- context/journal.ts、structs/context/journal.ts：记录选定模型/工具事实，供上下文投影，不是完整审计或持久恢复日志。
- execution/engine.ts 与 kits/durable.ts：Engine snapshot/checkpoint 与顺序任务执行位置的保证不同；Durable 的 operationId、commitId、definition revision 不能作为普通词汇重写。
- support/registration.ts、structs/support/registration.ts：install 有顺序同步语义，不因 Catalog 命名而成为无时序元数据。
- package.json、scripts/api-reference.mjs、scripts/compile-skills.mjs、相邻 pages/apps/agent-core-docs/README.md：运行环境、双格式、可选 peer、生成来源与最终包体须共同核对。

这些是静态复核，不是故障复现或运行通过记录。未逐个核对外部行业标准，第二版将公开选名的一手定义/惯例/用例依据列为 D0 必交付，不能把建议词宣称为标准。

## 5. 原意见回查和分歧规则

修订后交回七名原提出方，逐项识别完整采纳、合理改写、部分采纳或遗漏；允许维持反对。原方确认只覆盖自己明确核对的意见，不扩张为修订全文通过。独立规划方首轮没有读丁，回查才阅读修订稿。

沿用甲乙机制：若主审与原方仍有无法对齐的具体取舍，先固定 A/B 及各自理由，交原提出方之外的其余六名评审投票；主审和原方不投，每票有选择及理由，3:3 交用户决定。不得把不响应或附条件意见算赞成，也不得在投票期间悄悄改 A/B。需要 D0 实际固定的字段不等于当前已有架构争议。
