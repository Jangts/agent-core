# Agent Core 1.0.0 甲计划：可靠执行与 Agent 组合

日期：2026-11-25。修订：第二版。状态：已实施，七方复审修复及新增交付已完成本地统一验收，见[复审记录](1.0.0-jia-reaudit.md)；不等于 1.0.0 整体完成。基线：当前工作区 0.9.0 源码及现行契约，不以版本号代替实际发布或验收状态。

甲计划负责“已有能力强化、可靠执行与 Agent 组合”，只是 1.0.0 的部分任务，不单独决定版本调整或发布。后续已按明确授权实施并验证；首轮实施见[实施与本地验收](1.0.0-jia-execution.md)，修复后的验收时点与范围以[七方复审记录](1.0.0-jia-reaudit.md)为准；后续相关改动须定向重验。未发布、部署或替代其他版本任务。

本版吸收七名独立 Agent 的评估、源码审计、独立规划和反方意见；意见、分歧与采纳依据见[多 Agent 评审与重设计记录](1.0.0-plan-jia-review.md)。A—E 为五个方向，P0—P4 为实施阶段。

具体工作包、负责人、文件所有权与首批进度见[实施安排与首批试运行](1.0.0-plan-jia-implementation.md)。实施分批推进，范围和验证结论以实际任务授权及验收记录为准。

## 1. 五个方向与完成目标

| 方向 | 实际收益 | 完成依据 |
| --- | --- | --- |
| A 强化既有长处 | 分层预算、工具授权、声明式编排、上下文、定向修复和诊断更可靠，接入负担减少 | 同一任务的普通接入与推荐接入对照，缺口修正及对应故障证据 |
| B 借鉴可靠执行 | 持久恢复、副作用重试、暂停继续、并行结果汇合在明确范围内可用 | 每类有支持合同、可运行组合和适用故障案例，不默认四类都新增 Core API |
| C 持续吸收与充实 | 从 LangGraph 及社区筛选设计，改良 Core 并充实 Support／Kit／Skills | 来源和采纳决定可追溯，落实到代码、组合、回归或指导，不能只收集链接 |
| D Agent 作为节点 | 完整有界的原生 Agent 进入大图；明确 LangChain 机制和互操作方式 | 原生组合样例及外部接入可行性结论，不预设运行时无损融合 |
| E harness 运行与组织 | App 从公开入口组合出承诺的任务形态，无需复制内核调度或猜测内部进度 | 具体宿主装配、可替换组织件、成果查询和资源清理证据 |

研究不能预先写死为新 API，也不能让必要补强止于审计。每方向均须形成可用能力或已满足合同的行为证据；发现真实缺口就修复。是否扩展内核，由执行不变量和现有组合不足决定。

## 2. 架构、责任与范围

采用 **Core 微内核、App 宏内核式整合、非全面化**。微内核不仅约束依赖方向，也要求核心语义克制；App 统一拥有 Agent 的装配和运行政策，不表示所有逻辑放入一个文件或类。

| 归属 | 应拥有 | 不应拥有 |
| --- | --- | --- |
| Core | 双向执行契约、调用／预算／取消／状态接纳的通用保证，普通 handler 无法安全替代的必要机制 | 具体任务角色、审批政策、业务完成标准、特定 Kit 状态 |
| Support | 可替换的端口接线、推荐策略和 Core handler 实现；绑定稳定依赖并继承运行元数据 | 第二套调度协议、另一份身份／预算清单、只在辅助内成立的核心保证 |
| Kit | 可独立使用的局部算法和模型，如定向检查、Durable 顺序任务、结果聚合 | 父流程全局运行权、所有 App 必选的统一任务状态 |
| Skills | 选择边界、接线、排障与验证的方法，指向真实接口和案例 | 靠提示词授予权限或保证计账与副作用安全 |
| App | 身份、授权、事实、存储及排他、审批、凭据重建、对账、成果与交付 | 复制 Core 已承诺的机制，猜测内部进度进行恢复 |

Durable 可组织局部步骤并调用 Core，不因此拥有父流程控制权。Core 不依赖 Support／Kit 的业务字段；共享基础和根入口聚合导出不按名字机械拆分。

### 新机制的必要性检查

每项新增公开机制说明：执行不变量、现有接口为何不足、唯一控制者、最小接口、不支持范围、新概念及维护成本。先定义场景目标与失败断言，再判断接口缺口，不为演示拟新增 API 而反向构造需求。已有接口足够就交付接线和案例。公共能力不要求多个消费者，但须有独立通用价值。P0 通过源码和纵向样例确定设计；日常实现取舍不另设用户审批，改变五方向或关键范围须明确报告。

### 明确不做与兼容边界

不建设通用 Pregel／分布式调度器、全量 LangGraph 兼容、全供应商目录、托管平台、默认数据库／沙箱／记忆服务、强制 Harness 类。不恢复 JS 调用栈，不强制所有字段用 reducer，不让普通调用承担持久任务配置。

历史兼容以简单、局部、不污染主路径为限；复杂迁移独立显式执行，不保留多代内核分支。不兼容状态在新副作用前拒绝，不静默从头运行。历史查询与恢复旧执行分开，不承诺所有旧格式永久可读。公开 API 按语义化版本演进；甲计划不承担全版本兼容与发布总责。

## 4. 纵向参考任务

维护一个独立最小参考 App，从公开入口逐步扩展。宿主装配、确定性 Provider、存储和工具端口明确，不能隐藏在测试中或依赖私有业务服务。示例采用现有公开示例目录，不另建 App SDK。

| 样例 | 场景与增量 | 必须观察的结果 |
| --- | --- | --- |
| R0 最小调用 | ModelRunner 一次输入输出，随后将同一调用放入普通节点 | 第一阶无需图或 checkpoint；后续复用 Provider 与业务逻辑 |
| R1 有界 Agent 组合 | 父流程准备输入 → 子 Agent 使用授权工具 → 成果检查 → 必要时只修复交付 | 状态映射明确；真实计账；拒绝无副作用；格式修复不重做已确认操作 |
| R2 持久与等待 | 在可恢复任务版本加入步骤／节点边界保存、人工确认、一次保存操作和成果查询 | 新进程重建端口及授权后继续；未知写入先对账；重复答复有结果；断连后只读获取同一成果 |
| R3 受控并行 | 读取两份资料的独立子任务，父节点显式接纳结果；至少一次对同一父级结果项给出不一致候选 | 交换完成顺序后得到同一约定结果或稳定拒绝；成功成果可保留，父接纳失败不推进；失败、取消和迟到有边界；不滥用版本 fork |

R2 不预设任意图恢复。先用 Durable 与普通 Workflow／Agent 组合；不能表达必要边界才补最小 Core 契约。R3 先用独立输入和结果集合、父节点显式提交，不先建共享状态引擎。

原生参考任务须可运行。必要能力由已有机制、接线或最小扩展提供；不能仅标“App 负责”就关闭。存储、审批和对账须有具体端口及实现，示例存储不冒充内置生产服务。

## 5. A：强化长处和接入体验

### A1 预算与执行范围

核对模型、工具内模型、子 Agent、多模型、重试和恢复的真实调用路径。请求共享、持久额度与外部黑盒资源域分开；保留父级预留、累计消费和调整事实。不因重启、换 Runner、压缩或创建子 Agent 重置已消费额度。

R1 证明子调用与修复受父级限制；R2 明确持久预留及未知尝试。执行额度耗尽不自动禁止无模型的只读确认，也不授予有成本的对账；后者须有预留或宿主授权。

### A2 工具、上下文与成果

列明各工具入口的解析、授权、执行、输出校验和记录顺序，检查请求隔离及授权变化。上下文投影／压缩保留关键约束、来源、最新纠正、回执与未完成项。程序保证外部内容不能授予权限；模型是否被注入影响另用样本评估，不承诺语义绝对免疫。

区分事实充分、格式有效、操作完成、保存和交付；附属失败不抹去主成果。只修缺失部分，不重放已完成副作用。缓存不是授权或业务事实来源，取消不是自动恢复故障。

### A3 可证明的接入收益

沿 R0—R3 比较相邻阶段的新增 import、必填字段、宿主决定和业务改动，不设武断行数上限。用同一任务对照普通 handler 与推荐接线，说明减少哪些重复安全规则、元数据传递与定位步骤；不因“已有”就认定有优势。

Support 说明省去和保留的决定；Kit／Skill 按“具体问题 → 首选入口 → 启用条件 → 可省略条件”组织。Agent 加入父图只补必要映射，不重声明全部内部配置。普通调用不引入持久任务状态。

参考 App 中重复出现、与业务政策无关的安全接线须进入现有或必要新增的可复用入口。等待／执行代次关联、运行元数据传递和迟到结果隔离，不能仅靠每个 App 手写约定保证；具体身份、授权政策、原子存储与真实事实仍由 App 提供。不因复用规则就把所有端口下沉 Core。

## 6. B：可靠执行共同合同与补强

### B0 唯一控制者

P0 登记运行／尝试／操作身份、状态与后继位置、等待记录、请求账本与持久预留、分支成果、最终结果、取消事实、资源的所有者及生效时机。按启用能力采用最小契约，不形成强制通用字段集。

明确谁决定下一步、提交父状态、仲裁恢复和执行授权。Core 管其公开保证，Durable 管局部顺序任务，App 提供真实端口；不能靠多套调度器互相包装掩盖重复控制。

### B1 持久恢复与提交

先核验 Durable 的预留、run／reconcile、状态与下一位置保存，同 Workflow 提交和选路顺序衔接。确定可恢复单位、handler 修改约束、失败后内存状态及持久后继位置，不将内存提交描述为存储事务。

受支持恢复记录在同一原子存储单位关联状态、后继位置和必要回执引用；原子性及排他由 App 端口保证。保存异常可能是未落盘或确认丢失，先读回确认事实。已确认成果不因响应丢失重做。仅序列化明确数据；连接、signal、函数、凭据和有效授权重新绑定。

### B2 副作用与对账

稳定操作身份在执行前建立，尝试身份每次区分。safe 仅用于可安全重放的操作；reconcile 要能表达“已完成、确认未发生、仍未知”，不能将所有返回当作成功推进。现有合同能表达则直接使用，不能表达则修正局部 Kit 及受影响消费者。

分别处理预算／期限耗尽、完成与取消竞争、无成本确认。未知操作仍占必要预留；查询不能暗启执行或退还未知额度。不承诺外部 exactly-once；幂等、对账和补偿由真实端口提供。

### B3 显式暂停继续

优先步骤／节点边界，不恢复调用栈。等待、错误、取消、完成分开。答复绑定具体等待和执行代次，检查任务／定义修订、主体、期限及当前权限；校验和消费由宿主原子实现，重复相同答复与冲突答复有明确结果。

暂停释放请求资源；继续重建资源范围并保留已消费事实。持久取消在恢复入口可见；停止等待不代表远端撤销。无法识别旧执行与未知副作用的组合明确拒绝自动继续，不从头重跑。

### B4 受控并行与结果汇合

分支独立输入，不共享可变父状态；按声明身份收集结果并显式接纳。默认冲突拒绝，或采用 App 明确选择的确定策略，不按返回时间覆盖。合并算法可在 Kit／普通 handler，Core 仅补不可替代保证。

分支成果和父接纳分开，部分成功的保留位置明确；父提交失败不冒充汇合成功。定义父取消、兄弟失败、迟到隔离、共享预算及提交边界。限定单 App 受控并发，不建设多 worker 协调。

### B 的故障验收

仅在声明支持的路径执行适用案例；未采纳项说明理由，不为勾选表格建功能。

| 注入点／条件 | 观察事实与预期结果 | 主要所有者 |
| --- | --- | --- |
| 外部成功，保存失败／确认丢失 | 读回提交事实；未确认则对账，不依据异常重发；状态与后继位置一致 | Core／Kit 边界，App 原子存储及事实 |
| 对账未发生／已完成／未知 | 按允许策略执行／接纳／保留未知，不将未知变成功 | Kit 局部合同、App 对账 |
| 最后额度预留后崩溃，两个恢复者竞争 | 未知额度不返还、无重复授权；确认和新执行分开 | Core 请求约束、Kit 预留、App 排他 |
| 暂停重启，重复／过期／跨主体答复 | 匹配本次等待、原子消费、重新鉴权；旧答复不消费新等待 | Core／Kit 边界，App 身份及存储 |
| 子任务成功，父保存失败 | 成果可回查；父未确认不推进；陈旧提交或恢复争用拒绝 | Core 提交入口、Kit 聚合、App 存储 |
| 不合作 handler 取消后迟到 | 新运行不接纳旧输出；可能成功的副作用保持未知，不盲重发 | Core 结果隔离、App 取消及对账 |
| 完成已保存但响应丢失，执行期限已过 | 按当前读取授权和保留期查询同一成果，不重执行 | Kit 查询语义、App 授权及成果 |
| 并行顺序交换、冲突、单支失败 | 同一约定结果或稳定拒绝，成功／失败／取消可定位 | Core 边界，Kit／App 显式合并 |

## 7. C：上游研究转成实际改良

围绕 B／D 查官方文档、源码、测试及 Issue／PR。固定适用 JS／TS 版本或 commit、访问日期和源码位置；Python 报告仅作线索。关闭、热度、测试数量不证明修复正确或当前稳定。

每项记录：本地问题 → 上游机制和限制 → 已有能力对照 → 静态依据或复现 → 采用／改写／不采纳 → 所属层 → 变更及证据。可交付实现、删除不可靠抽象、增强回归、组合或指导，不能仅摘录，也不要求每项新增功能。复制源码核对对应许可和声明。

## 8. D：原生 Agent 节点与外部接入

### D1 必交付：原生完整执行单元

R1 在早期验证普通节点包装子 Agent，不等恢复引擎完成后才集成。子 Agent 保留自身工具、上下文、循环与检查，父图只传明确输入并接纳验证后的输出。不同结构用普通映射；无收益不增加专用 Agent 节点类型。

请求内父子预算、取消、诊断、流式事件接线明确，子结果不能修改父权限或额度。R2 验证恢复后是否重跑子 Agent、如何识别已完成成果；创建新实例不等于继续旧执行。

### D2 必交付：机制与可行性结论；adapter 按证据决定

区分借鉴 LangChain Agent 进入大图的组织方式，以及接入真实 LangChain 运行时。前者在原生样例体现；后者先验证最小包装，不预设产品级兼容。

核对直接传入与普通节点调用 invoke／stream 的节点契约、状态、结果、事件、取消和暂停。已有 wrapper 足够则交付示例；真实包原型固定版本，采用确定性 Provider 与最小工具，不用形似对象冒充兼容。环境不可用时保留未验证项，不以静态推理宣布已运行。

外部运行时拥有内部循环，父节点只承诺可控制边界。内部调用未实际接入 Core 计账就采用独立有界资源域，不能把一次节点当一次模型调用。无法透传暂停或确认未知副作用时拒绝自动恢复；隔离迟到输出不等于撤销副作用。

外部原型不成为 Core 必需依赖。只有比普通 wrapper 明显减少接线、有通用价值且保证可解释时才提供可选 Support adapter；允许不产品化。无论选择如何，均交付直接方式是否成立、间接方式限制、机制借鉴及证据。

## 9. E：有限可验证的 harness 完整性

“完整”仅针对 R0—R3：输入可进入、调用受控、副作用可确认或明确未知、等待可继续、故障可定位并按允许范围恢复、成果可保留和再获取、资源有释放者，不是无限能力清单。

| 职责 | 具体交付 |
| --- | --- |
| 运行装配 | 清晰参考 App 入口，绑定定义、模型、工具、授权、存储、审批、成果及观察；稳定依赖与运行数据分开 |
| 资源与退出 | stream、订阅、存储句柄、子任务谁创建／借用／关闭；完成、错误、取消、暂停的释放顺序；借用资源不擅自销毁 |
| 结果与重连 | 运行身份关联成果，查询不执行任务；读取授权、保留期和执行期限分开；日志不自动公开 |
| 上下文与权限 | Core 边界与 Support 策略可替换，记忆／检索由 Kit 和 App 提供；快照不恢复凭据和有效授权 |
| 执行观察 | 区分 token 预览、进度、回执、状态接纳和最终结果；父子及尝试可关联；观察失败不改变业务结果 |
| 使用指导 | 启用条件、最小接入、可省略项、限制与故障定位明确，不强制统一 harness 框架 |

先交独立参考 App，再按公共契约变化选择仓库内一个实际受影响接入验证成本。不默认重写 Microcola／Banker，不为消费者数量硬加业务。包目录其他消费者按签名影响核对。

审查可标已有满足、需补证据、需修复、App 端口或不支持；参考任务的必要职责不能仅分类关闭，须有接线和行为证据。

## 11. 验证与交付纪律

- 每包写支持场景、观察事实、故障点、预期结果、责任者及不保证项。静态、离线、真实模型、外部服务和生产证据分开。
- 持久恢复承诺需要临时持久存储及新进程证据，内存 mock 不够；并发竞态验证不作压测。开发机不作容量结论。
- 按 main/AGENTS.md 运行频率，以具体疑问选最小检查，不因文档或清单例行构建。真实模型只证明语义／压缩／表达，程序授权隔离用确定性案例。
- 契约实现后再同步现行文档，计划留维护目录；双语手册、示例、Skills、实际源稿及相邻 pages 输入按影响同步，不只改生成副本。
- 不以测试／模块／社区／节点数量或未测性能验收。适用 ESM／CJS、类型、包体及消费者检查在实施记录按实际执行登记，不扩大为全版本发布清单。
- 保留未提交工作，不自动提交、推送、npm 发布、部署或修改 external。跨项目同步按真实契约影响，各仓库独立管理。
