## 1. 执行方式和文件所有权

- 使用当前 main 工作区，不新建 worktree，不重置、清理、暂存或提交已有修改。当前包有大量已有 staged／unstaged 修改，不能将其混算为本次交付。
- 三个子 Agent 与主 Agent 协作；每个可写文件只有一名当批负责人。相关源码可读，共享文件由主 Agent 顺序整合，不因并发方便把同一机制拆成重复实现。
- 首批未改运行时；后续实现已按单一文件负责人修改 Core、Kit、类型及公开入口。版本和工作区依赖保持不变，消费者按真实影响验证。
- 新增正式示例放现有 `development/examples/`；阶段设计和证据放包内 `docs/maintenance/`。一次性调试输出只放主仓库 `.tmp/`。不写组织目录或 `.external/`。
- 后续授权允许安排测试、MockGPT 和少量真实模型。使用临时官方 Node22、隔离 LangChain 依赖；只编译相关包，按改动和失败开展回归。真实模型限定同 key／异 key 六请求，不启动 UI、不提交、推送或发布。

## 3. 首批具体任务约束

### T1：真实组合而非形似演示

- 只从公开入口导入，确定性 Provider 无网络、密钥或后台服务。
- R0 使用一次 ModelRunner 调用；R1 父流程调用拥有自身有界循环与授权工具的子执行单元，结果通过显式映射接纳。
- 子调用和定向修复必须真正进入同一请求账本。不能用人工统计次数替代强制计账，也不能把一个节点当一次模型调用。
- 工具已有回执后，格式／交付失败只修对应结果，不重放工具。授权拒绝路径明确没有工具副作用。
- 不能从公开接口完成时，保留准确的探路结果和最小缺口，不导入 src 或手写平行引擎掩盖。

### T2：设计要能转为补丁

先列当前函数、执行顺序及已有消费者，再判断已有 State／异常能否表达对账结果。设计区分已完成、确认未发生、未知；无成本确认与新执行；执行期限与结果读取；请求取消与持久任务取消。

对每项列出建议改动符号、所有者、默认语义、兼容或显式破坏影响、失败注入及预期结果。暂停只研究有界步骤／节点，不设计通用图游标引擎。未经运行的风险标为静态待验证。

### T3：研究须影响实现选择

重点核对完整 Agent 进入父图、直接子图与函数包装、暂停重执行、副作用和确定性归并。给出比当前方案更小的替代，说明哪些只需普通节点，哪些值得 Support／Kit，哪些 Core 缺口不可绕过。

固定引用适用版本或 commit；只能确认文档查阅日期时标明尚未固定实现版本。真实 LangChain 包原型留后续独立接入任务，本批不安装依赖、不伪造兼容结果。

## 4. 收敛、争议与最小验证

首批回收顺序：检查越界与文件冲突 → 阅读实际代码／设计／来源 → 核对 T1 的共享预算与运行产物 → 汇总 T2／T3 决定 → 给出后续 T4／T5 可编码任务。

接口决定由主 Agent 与原提出方先对齐。无法对齐的具体分歧按既定规则交其余六名原评审投票，原提出者与主 Agent 不投该项；3:3 交用户裁决。不能用投票覆盖仓库约束、用户范围或已确认事实。

只针对实际疑问验证：T1 先核对公开产物是否包含所用入口；确需运行时只执行单个示例。T2／T3 静态设计不自动启动测试。后续持久承诺必须新进程＋临时持久存储验证，不能由本批示例通过代替。
