## 2. safe／reconcile 的失败窗口

1. **running 保存前失败**：尚未允许 handler 执行。save 的拒绝也可能是确认丢失；先读回，不得直接认为未提交。读回确认预留后可以进入该次执行；无法确认则停止。
2. **running 已保存，执行尚未开始就退出**：恢复看到 running，无法从该字段判断是否真的调用外部操作。safe 可按契约重放；reconcile 必须确认，不能凭本地无回执判断未发生。
3. **外部已成功，本地 state 未形成／验证失败**：旧输入仍在 checkpoint；reconcile 读取真实回执并构造完整下一 state。绝不为补格式再执行原写入。
4. **完成 save 失败或确认丢失**：可能已经持久推进。先读取同一提交身份，确认完成则接纳；未确认则留待恢复，不退回原输入自动重做。
5. **最后预留之后进程退出**：旧尝试资源不退还。恢复的只读确认应能进行；确认成功可以接纳成果，不能凭“仅对账”重新授予模型或外部执行资源。
6. **取消／超时之后 handler 迟到**：本地不接纳迟到结果，但远端仍可能完成。下次不可基于“当时查不到”证明永远未发生；not-executed 要求外部确认不存在仍可能提交的旧操作，或有稳定幂等／fencing 保证。

safe 也不等于免费：模型重复生成可能是业务上可重放但会重新消费额度，继续按新尝试计账。安全重放的真实条件仍由 App 与工具端口证明。

## 3. 设计决定：最小对账结果合同

保留 `run(state, context): Promise<State>`。将 step.reconcile 改为显式三态，不通过 state 的业务字段猜测，也不允许对账回调自己补发原操作：

```ts
type DurableReconciliation<State> =
  | { kind: 'completed'; state: State }
  | { kind: 'not-executed' }
  | { kind: 'unknown'; reason?: string };

// 当前显式对账合同。
reconcile?(state: Readonly<State>, context: DurableReconcileContext<App>)
  : Promise<DurableReconciliation<State>>;
```

| 结果 | 唯一允许的推进 |
| --- | --- |
| completed | 校验、复制 state；以原操作的确认结果保存下一位置，不增加执行尝试或模型预留；有后继时再独立检查执行期限及预算 |
| not-executed | 保留原输入，将 running 保存为 ready；不退还旧预留；当前 run 随后必须通过执行期限、次数、模型额度、取消及新授权检查，才能登记新尝试并调用 run |
| unknown | 不修改 state／位置／预留，不自动循环；抛出带稳定 `code = DURABLE_UNRESOLVED` 的局部错误，宿主可查询当前事实并明确告知未确认 |

malformed 结果视合同错误；reconcile 抛错保留原错误及原检查点，不推进。completed 的 state 缺真实证据属于宿主错误，库只能检查结构和调用边界。

`DurableReconcileContext` 继承 OperationContext，带 `taskId/stepId/operationId/attemptCount` 与固定 `maxModelCalls: 0`。`operationId` 是对同一 task、definition/revision、step 的稳定编码，不包含会变化的 attemptCount；taskId 禁止重用来表示另一个任务。新尝试的唯一身份由稳定操作身份加 attemptCount 表达。普通 run context 同样提供这些字段，避免业务手工生成互不相关幂等键。

reconcile 的回调合同仅允许只读外部确认和纯状态构造；不得调用模型、补写或补偿。上下文的 0 是显式约束，不是沙箱：任意 App 回调仍可能绕过约束访问自己的端口，文档不能声称 SDK 阻止所有出网和成本。只读查询有服务费用或严格配额时，由 App 提供单独限额；没有查询授权或限额就拒绝，不偷偷消耗已耗尽的执行预算。

## 4. 门槛顺序与期限分离

### run 的局部执行顺序

1. 采用调用方本次有效 signal，取得排他锁，load 并校验 checkpoint 与定义。状态读取／格式校验不依赖持久执行期限。
2. 通过当前 run/reconcile 操作授权。completed 立即返回分离 state，cancelled 禁止执行；这里不要求执行期限仍有效。
3. 若 running 且 replayPolicy=reconcile，先以本次调用 signal 进行只读对账；不创建过期的执行 signal，不增加尝试或模型预留。每次 run 最多一次对账，不隐含无限重试。
4. 若对账接纳后任务 completed，返回；若仍 unknown，停止；若需下一执行，才检查 `deadlineAtMs`、maxAttempts、剩余预留以及当前权限。
5. 新尝试先建立并保存身份、次数与完整预留，再以执行 deadline 与本次 signal 的组合调用 handler；结果通过取消、定义及状态检查，提交下一状态和位置。

`deadlineAtMs` 继续表示“不得启动／接纳新执行工作”的执行期限。只读确认在其后可确认旧成果；新步骤不能借确认获得新期限。completed 查询、未知事实确认、取消登记均使用本次调用 signal，宿主必须设置合理查询超时及保留期，不能复用过期的执行 signal。

读取保存后的结果不调用 step.run/reconcile、不续期、不修改额度；可以先使用现有 App read 路径，不为形式统一强制新增 `task.read`。复用 checkpoint 校验确有重复需求时，仅提取 Kit 内公共只读校验／读取辅助，另经最小性审查。它不成为执行入口。

authorize 两参数保留，当前 DurableAuthorizationContext 的操作身份为 `operation: 'execute' | 'reconcile' | 'read'`。cancel 由 App 实现，不属于该授权枚举。调用前明确操作模式，旧回调可忽略新增字段；App 须为新增只读路径提供当前读取／查询授权，不能自动复用过去写入许可。纯 App read 路径继续由 App 自身鉴权，不强制经 task.authorize。

## 5. 保存确认：v2 可选提交身份

实际实现保持 Checkpoint version=2，增加可选 `commitId?: string`。旧 v2 记录缺省时直接读取，存在时必须为非空字符串；每次新 persist 都生成唯一身份，保存分离快照。没有新增另一套旧执行路径，也没有实施原设计的 v3 格式提案，三处 safe 业务消费者不因此被迫迁移持久数据。

`defineDurableTask` 的局部 persist 在锁内保存快照；save 拒绝时 load 一次并检查读取记录，只有结构与定义校验通过且 commitId 精确等于本次预期身份，才确认原保存。读回失败、不同身份或不合法记录均保留原 save 错误，不盲重发。不以 JSON.stringify 比较业务 State，不以相似 status/index 确认提交。

这能兼容旧 v2 的缺省字段：只有新 persist 才需要确认本次提交，而它始终具有新 commitId；不会把没有身份的历史快照冒认为本次保存。`snapshotCheckpoint` 显式读取并保留该字段，防止序列化投影丢失确认依据。

commitId 只识别提交，不替代 store.exclusive 的真实排他性，不提供分布式 CAS／租约。存储仍须原子保存整个 checkpoint，提供可信读回；最终一致存储的一次空结果不证明旧提交未发生。若宿主序列化会丢弃新字段，保存确认丢失将安全失败而非猜测成功。

## 6. 持久取消与迟到边界

现有 cancelled 已足够表达禁止未来执行，不新增取消状态或默认 cancel API。复用宿主模式：先中止本机活动调用，再等其 finally 和已发出存储确认结束；通过同一 task 排他路径读取最新记录，若未 completed 则保存 cancelled，不覆盖已确认 completed。写成功之后才向用户确认取消已持久登记。

库不将 HTTP 断连、运行超时、服务关闭等任意 signal 自动持久化为 cancelled；这些通常仍可恢复。显式用户取消由 App 选择登记，进程重启后 run 必须从持久 cancelled 拒绝，换 signal 不得复活。

被取消但远端结果未知的操作，在 App 操作事实／回执记录保留 unknown；`status=cancelled` 不表示未发生，也不清除 reservedCalls。不允许 run 借对账恢复 cancelled 任务；需要确认远端状态时用独立只读查询，不重新调度步骤。

同一锁中完成提交早于取消登记时，完成事实保留；取消登记先于恢复入口时，后者拒绝。若宿主需要跨进程在活动执行中即时抢占，当前全 run 排他锁和本机 signal 不足，本设计明确不支持；不能悄悄用无锁覆盖 checkpoint 达到“即时取消”。主参考 App 限定单宿主受控运行。

handler 必须接收克隆输入；取消后 local state 与持久提交隔离，后续 continuation 不得提交。非合作远端仍可能执行：reconcile 的 not-executed 只接受稳定否定证据；临时查不到需返回 unknown。不得将 AbortSignal 或清除 Promise 当作 fencing。

## 7. 可恢复单位与唯一控制者

恢复位置是 Durable 的 `nextStepIndex` 和该 step 的输入 state；完整 Workflow／Agent 可以作为一步，但只有整步成果确认或安全重放。没有内部成果回执时，不承诺恢复到子图某个节点。Core 仍负责单次 Loop、取消、模型和工具调用保证；不新增通用图游标。

| 事实／决定 | 唯一控制者 |
| --- | --- |
| 步骤顺序、次数、预留、对账结果接纳、nextStepIndex 与状态 | Durable Kit |
| 每次调用的预算／取消和诊断执行保证 | 既有 Core／ModelRunner |
| 存储事务、真实排他、读取保留期、身份及权限、初始化与显式取消 | App 端口及服务 |
| 操作幂等、远端确认／否定／未知事实、对账费用与超时 | App 工具／外部服务 |
| 子 Workflow 内节点路由 | 该 Workflow 的 Core Engine；不得同时替 Durable 推进持久 step |

1. 已收敛三态、只读确认及 v2 可选 commitId；局部 Kit 合同不要求 Core 运行协议变化。

## 10. 待验证的最小回归矩阵

| 场景 | 必须断言 |
| --- | --- |
| safe running 重启 | 新尝试消费并保留旧预留，副作用安全性由测试端口幂等证明 |
| reconcile 三态 | completed 只推进一次；not-executed 不退额度、后续需新执行授权；unknown 不推进、不执行、不自动循环 |
| 尝试／模型额度耗尽 | 零模型只读确认仍可完成旧成果；无法确认或确认未发生时不新执行 |
| 执行期限已过 | saved completed 可查询；running 可只读确认；后继步骤不启动；查询 signal 过期仍中止 |
| 授权撤销／资源过期 | 对账、读取和执行分别按当前授权决定；过去执行权不自动成为读权 |
| running save 确认丢失 | 读回相同 commitId 后才执行；读回失败／不同提交不执行 |
| 完成 save 确认丢失 | 读回原提交即接纳；重启不重写远端；不确认则保留未知 |
| 两恢复者 | 宿主排他令同一步不双发，第二调用读取第一结果或拒绝；不能用 no-op exclusive 证明并发安全 |
| 显式取消／完成竞争 | completed 事实不被覆写；cancelled 重启不复活；断连不自动永久取消 |
| 非合作 handler 迟到 | 无持久状态越代提交；远端未知不被临时无记录误判为 not-executed |
| 格式与定义变化 | v2 缺省 commitId 可读；v1／v3、错误 revision、无效 commitId／三态返回在副作用前拒绝 |
| 方法接收者及保存取消 | class 私有成员可用；已发出 save settle 前不释放锁；取消异常不掩盖存储未知事实 |

先以确定性端口证明每个执行疑问，再用新进程验证持久恢复；测试和构建运行仍遵守仓库频率。T5 已用官方 Node22 执行 `artifacts-durable.test.mjs` 与 `artifacts-durable-types.test.mjs`，当时 32 项通过，包含双模块类型、既有取消与锁内保存、新三态及确认读回回归；这不是本矩阵全部或进程重启／生产存储的验收。T7 为文档和 Skills 静态同步，没有再次运行构建或测试。
