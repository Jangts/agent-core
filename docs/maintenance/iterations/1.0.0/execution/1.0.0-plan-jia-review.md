# Agent Core 1.0.0 甲计划：多 Agent 评审与重设计记录

日期：2026-11-25。范围：七名独立 Agent 的评估、源码审计、独立规划和反方审查，以及主 Agent 证据复核与第二版重设计。当前文档见[甲计划](1.0.0-plan-jia.md)。本文为维护记录，不是能力说明或实现验收。

## 1. 分工与上下文

七名 Agent 分批参与，均已返回完整意见；主 Agent 收集后统一改写，没有让子 Agent 并发修改计划或运行源码。

| Agent | 输入和任务 | 主要意见 |
| --- | --- | --- |
| plan_audit | 全量会话、原计划及仓库规则；审计范围、阶段与验收 | 研究被预设为新能力；真实外部互操作示例被列为必交付；Agent 组合验证太晚；开放完成标准和全故障清单不可判定 |
| fresh_plan | 不读原计划，只给五方向、架构原则和仓库入口；独立规划 | 保留实质改良，交付有界恢复、暂停、并发和 Agent 组合纵切面；Support 与 Skills 要有可用产物 |

这是不同任务与上下文下的独立意见，不是七种模型投票。反方被明确允许推翻原计划，未被要求先认同其价值。结论按依据采纳，不按人数通过。

## 2. 源码复核及证据范围

已静态复核以下事实，路径相对包根。未执行故障复现，不将风险当已证明运行缺陷。

- `src/execution/engine.ts` 的 executeWorkflow 将原 state 交给 handler，补丁先 commit 再选择 route；`Readonly<State>` 不提供运行时深隔离。节点调用、状态写入、路由和持久保存应分别定义。
- Engine 的 checkpoint／restoreCheckpoint／fork 保存宿主数据与分支身份，不包含任意图的执行游标恢复；fork 要重建依赖。
- `src/model/call-budget.ts` 的父子关系依赖请求内对象；`runner.ts` 的 createChild 共享请求 gate 和额度，不能直接推导跨进程上限。
- `src/kits/durable.ts` 先保存尝试和保守额度预留，中断后选 run 或 reconcile，成功后保存下一状态／位置，finally 等待已发出存储确认。必须先复核既有路径，不能再造类似顺序机制。
- 当前 reconcile 返回完整 State 并据此推进；执行和终态读取共享若干期限／额度边界。未知／未发生结果、耗尽后确认、完成查询等问题，需后续用确定性案例验证影响。
- `src/kits/family.ts` 的 merge 是版本成果合并，不是运行中并行字段归并。
- 类型化工具桥接与低层 ToolRegistry 责任不同，不能承诺所有公开路径都自动获得完整业务授权。

官方参照：[LangChain middleware](https://docs.langchain.com/oss/javascript/langchain/middleware/overview)说明完整 Agent 可进入 LangGraph 大图；[Subgraphs](https://docs.langchain.com/oss/javascript/langgraph/use-subgraphs)区分直接子图与函数包装映射。它们不证明跨运行时预算、取消与暂停自动贯通。

## 3. 分歧与处置

| 问题 | 不同意见 | 第二版决定与理由 |
| --- | --- | --- |
| 四类可靠执行是否必做 | 审计／反方允许不新增；独立规划要求实际交付 | 每类问题及支持范围必须有行为交付，不默认四类新 API。已有满足则组合证明，真缺口就修，不能全部降为调研 |
| 是否必须支持真实 LangChain | 原计划强制真实包装样例，并讨论可选 adapter；审计认为超过机制研究最低要求；可行性认为普通 wrapper 可表达 | 原生 Agent 节点必交付；真实包最小可行性原型给结论；有独立收益才产品化 adapter，不追求无损融合 |
| 是否新增图恢复引擎 | 原计划预设节点游标、暂停及 fork／join | 先复用 Durable 和普通节点，确定提交边界，无法安全表达才补 Core；并行改称受控任务与结果汇合，避免滥用版本 fork |
| 如何定义完整 harness | 原计划开放矩阵；反方认为不可证伪 | 用 R0—R3 有限任务关闭；App 给实际端口与实现，矩阵不能替代可运行链 |
| 优势如何证明 | 原计划只防退化；反方要求同任务、同等安全性下对照应用负担 | 采纳普通 handler 与推荐接线对照，核对安全规则、重复传递及定位步骤；反方没有要求另建通用引擎，也没有主张函数能写就否定框架价值 |
| 微内核如何约束 | 导入方向不足，新增语义可能膨胀 | 新机制给最小性依据及唯一控制者；不将全部状态下沉，也不以微内核为由把公共安全缺口留 App |
| 验收是否按数量和全清单 | 原计划固定案例数量及全故障要求 | 按宣称保证选证据，覆盖主题但不凑文件／模块；未采纳候选不必建设产品功能 |
| 组合验证何时做 | 原计划 D／E 靠后 | P0 原生薄切片探路，P1 完整组合，再补持久等待和并行，减少后期返工 |
| 能否删五个方向 | 反方允许推翻或延期等待／并发 | 不擅自删用户方向；保留可用组合，撤回未经证明的通用化方案。改变关键交付须明确报告 |

反方原建议新增公开 API 对应具体消费者需求；讨论后接受独立、可复现的通用场景也可构成需求证据，不要求业务先落地。保留已有接口不足与接入收益的必要性检查。参考场景应先定义目标行为和失败断言，不能为了演示拟新增 API 才反向构造需求。

采纳反方关于框架收益须经对照证明的建议：同任务、同等安全性下比较普通 handler 与推荐接线的重复规则、元数据传递和故障定位负担，不另建通用引擎。初版记录把该建议放大为“普通函数能写就没有框架价值”并记为驳回，归因不准确，现已纠正。

## 4. 第二版的实际改变

1. 保留五方向，区分问题交付与实现选择，新增机制必须解释必要性。
2. 加入 R0—R3 渐进参考 App，Agent 组合前置，不要求每次调用同时接入所有能力。
3. 明确提交确认、对账三态、跨重启预留、等待消费、持久取消、迟到副作用与终态查询。
4. 任意图恢复和通用并发不再是默认方案，先补强 Durable、普通节点和显式结果汇合。
5. 外部接入改为真实包可行性研究，adapter 按收益决定；黑盒内部资源独立有界。
6. Support／Kit／Skills 围绕可用接线和方法增强；App 有具体装配入口、清理及成果回查。
7. 阶段和关闭标准限定甲计划，不代替整个 1.0.0 发布判断。

修改甲计划、维护索引并保存本记录。七名 Agent 均只读评审；未修改运行源码、安装依赖、构建测试、调用真实模型、迁移应用或发布。主 Agent 仅核对本地链接、文档范围及相关源码；运行时发现仍是静态事实、风险或待复现问题。七份意见针对原计划，不能宣称修订后的全文又经过七名 Agent 独立验收。

本轮向三名原提出方交回第二版及取舍理由，由其独立回应；没有要求为形成一致而让步。
