# Agent Core 日志回查与模型复盘

2026-11-04 追加授权的 R2—R5、R7 当前实现与独立验收见[计划 D](../plans/plan-d.md)。本页较早的未实施判断保留为其时点记录，不能覆盖现行 API。

状态：长期 R2 设计提案，下文复盘端口、模型任务、结果查询与经验反馈均未实现或导出。统一路线及前置条件见[计划 C](../plans/plan-c.md#长期事项的前置条件)，已有执行事件与平铺代记见[日志规则](../../design/diagnostics-design.md)。

C4 单独补齐 `@jangts/diagnostics` 的有界文件读取和 inspect CLI，不把本文的 `DiagnosticHistorySource`、`results.query/get` 或复盘任务升级为现行 Core API。App 的读取权限、模型处理权限、结果披露、派生产物期限和消费反馈须先确定；本地能读取文件不代表可以发送给模型。本文描述的“Core 参与复盘”是后续任务能力的目标，不表示核心循环现在会自动回查，也不据此新增文件库依赖或第二套调度协议。

## Core 参与复盘的价值

App 保存日志，Core 理解自身的运行机制。一次复盘应把这两种知识结合起来：Core 带着对协议、模型调用、能力调度、预算、取消、检查与恢复的理解，研究实际发生了什么、哪些地方不合理、以后可以怎样做得更好；App 补充业务目标、领域事实、使用体验和最终消费需要。

因此，Core 不是等待 App 列完分析步骤才工作的报告工具。它有自己的理解视角、改进目标和产物规划；App 可以补充、细化或提出不同的问题。双方的需求构成模型的任务上下文，由模型结合证据形成具体调查和交付方案。

Core 自身的复盘目标与 App 的问题可以相互补充。同一段日志可能既回答 App 的故障问题，也使 Core 识别出反复出现的调度或恢复模式。同一份结论可供双方复用，不要求生成两套报告。

## 日志的归属

Core 日志只描述核心运行本身，例如模型调用、协议处理、工具调度边界、预算、取消与执行终态。Support 与 Kit 的内部处理不自动进入 Core 日志；调用方取得返回值、异常或按需配置该能力的 observer，自行决定如何收集和保存。

`breakWhile` 的观察器就是调用方显式收集的例子，不因为工具随包提供就归入 Core 事件。也不通过通用 extension 事件把所有 Support／Kit 日志重新汇入 Core。

Support／Kit 调用了 Core 时，Core 仍可记录自己真实发生的调用与执行行为；这不等于 Core 接管了调用方业务步骤和内部状态的日志。归属看实际记录的行为，而非仅看函数所在目录。

回查端口描述的默认范围是 Core 运行日志。App 如需联合 Support、Kit 或业务记录进行复盘，以独立来源补充并保留来源身份，不能伪装为 Core 自己的运行证据。没有这些补充记录，不因此把 Core 日志判为缺失；需要它们的具体判断另行说明资料不足。

## 1. 为什么开始回查

回查由实际需求触发，基本入口有两种：

- App 调用 Core 的复盘能力，可以是明确的问题、指定运行、业务反馈或维护任务；不要求先指定分析器和步骤。
- Core 在处理当前请求时，识别出需要历史证据的意图，例如解释以前的失败、比较处理效果、复盘重复问题，进而选择已登记且当前可用的回查能力。

第二种沿用现有意图、能力和工具注册，不增加独立的关键词分类器。Core 可以从当前任务推导出有必要回查，但仍受实际提供的数据访问能力约束。

运行结束、定时器或失败阈值并不天然构成复盘理由。App 若有这类需要，可以显式把它们接成任务来源；Core 不默认启动定时器、监视所有请求或在每次失败后调用分析模型。

没有对应任务或已注册触发需求时，Core 不无缘无故翻阅历史。有需求以后，Core 才主导自己的调查，而非被动执行 App 写死的子流程。

## 2. 组合任务：Core 自身视角加 App 补充

模型应获得相互区分、可共同使用的上下文：

| 来源 | 提供什么 |
| --- | --- |
| Core 自身知识 | 对执行、协议、模型和工具交互的说明，当前可用能力与相关运行语义 |
| Core 复盘目标 | 对当前问题的理解、需要研究的执行现象、初步的产物设想与待验证问题 |
| App 补充 | 本次业务问题、背景、领域判断依据、希望使用结果的方式，以及额外工具或 Skill |
| 实际证据 | 本轮状态、获准日志、真实检查和交付结果、相关历史产物及其局限 |
| 运行条件 | 可查范围、保留与过滤、可用处理方式、时间与调用预算 |

Core 自身知识优先取自实际的协议、注册清单、工作流说明及运行配置，不让 App 重新编写一份 Core 内部说明。App 注册的阶段和 handler 可以随原登记补充描述，不另建平行术语清单。

分析旧运行时要区分当时的版本和当前机制。缺少旧版本说明时注明不确定，不能凭当前规则断言历史实现一定有错。

Core 的复盘目标不是一张每次都必须跑完的检查表。它可以根据任务判断重点：有时需解释一次结束原因，有时要比较多次恢复，有时发现原问题之外的相关缺陷。产物规划也允许随证据调整，而不是调用开始就锁死所有结论栏目。

App 不必提供完整计划，也不只是报告展示端。它可以补充“用户实际看到的是什么”“哪些结果在业务上算成功”“希望拿这份理解做什么”。Core 会把这些需要与自身目标一起考虑。

目标冲突、证据不足或预算不够时，保留明确的未解决问题；不要为了交满一份预设格式而编造理解，也不要悄悄只回答其中一方。

## 3. 模型组织调查，工具提供能力

模型在任务中决定是否读取能力说明、先查哪个运行、是否缩小范围、补查哪段原始输出、调用何种计算、采用哪种 Skill，以及何时已有足够依据结束。Core 使用现有模型和工具循环承载这些决策。

这些行为没有一条固定必经路线。模型可以直接解释一份充分的运行快照，也可以先发现日志过滤导致资料不足，再改做可行的技术分析；不要求依次通过“选分析器、取数、统计、写报告”等固定阶段。

确定性能力适合完成计数、关联、去重、片段组合和预算计算；模型适合理解问题、提出与验证假设、结合语义和规划产物。两者由当前任务需要组合，不把推理过程压成预设分支。

内置 Skill 和分析工具提供默认经验与可用方法，不定义能力全集。App 可以：

- 补充可信的业务上下文、成功判据、问题和交付偏好。
- 登记领域资料、结果检查、外部分析服务或其他只读工具。
- 提供或替换分析 Skill、格式器和结构化产物 schema。
- 接收中间发现、补充必要上下文，或仅消费最终结果。

这些扩展复用已有 context fragment、capability、tool、Skill 和输出机制，不另建一套日志分析专用插件平台。工具与 Skill 供模型选择；是否适用、缺少什么证据由实际执行与检查说明。

复盘不重新执行原业务副作用。模型如提出需要业务操作，仍通过原有已登记能力处理，不能把读取日志当成重放命令的许可。

## 4. App 如何提供日志回查

以下是待评审的数据交互草案，而非现行类型或已决定的 Core 必需端口。写入沿用现有 `CoreLogOutput`；将来接入复盘时先复用 App 侧有界 reader，再按真实需求确定任务适配：

```ts
interface DiagnosticHistorySource {
  describe(call: HistoryCall): Promise<HistoryResponse<HistoryDescription>>;
  query(query: HistoryQuery, call: HistoryCall): Promise<HistoryResponse<HistoryPage>>;
}
interface HistoryCall { signal: AbortSignal; deadlineAt: number }
interface HistoryQuery {
  from: string; until: string;            // UTC，左闭右开
  runIds?: readonly string[];
  events?: readonly string[];
  maxEvents: number; maxBytes: number;
  cursor?: string;                       // 宿主生成的不透明游标
  expectedPolicyRevision?: string;
}
type HistoryResponse<T> =
  | { status: 'ok'; value: T }
  | { status: 'disabled' | 'unavailable' | 'restricted' | 'unsupported'
      | 'expired' | 'policy-changed' | 'invalid-query';
      code: string; retryAfterMs?: number };
```

方法由 App 绑定可信访问上下文，通过现有工具适配向复盘任务提供。目录、文件名、SQL 和客户端自报权限不进入查询参数。Core 不依赖宿主的文件库、数据库或环境变量。

### 能力与范围说明

`HistoryDescription` 表达存储／访问范围标识、观察时间、政策版本、实际可查窗口，以及保留、事件过滤、正文处理、采样、分页一致性和资源限制。当前是否代记、是否允许读取、是否允许交给模型分别表达。

当前配置和旧运行的采集状态不能混为一谈。当前允许保存正文不证明旧日志有正文，七天保留也不证明七天内每次执行都记录成功。旧政策不明时返回 unknown，Core 据此调整调查与结论。

只授权本地读取不自动授权发送给模型服务。任务使用 App 明确提供且获准处理本次数据的模型端口；过滤掉的内容不通过其他路径找回。

### 回查记录

每条记录保留稳定 recordId、存储来源和范围、Core事件type、version、run/span、producerSequence、occurredAtMs，以及可知的运行版本和到期时间。只接收当前事件合同，不提供旧格式转换。存储包装序号／写入时间与 Core 自身序号／发生时间分别表达。

payload 区分实际可用、经过脱敏、被省略、不可取得；可用时提供实际保留值。旧版或部分记录不冒充当前完整 `CoreEvent`。未知事件可作为未解释的证据返回，不因不能按当前类型解析而悄悄消失。

App 自有事件、调用方收集的 Support／Kit 记录和客户端报告可通过明确登记的上下文来源补充，保持来源标记。模型判断、用户反馈和真实执行回执不合并成同一事实。

### 实际覆盖与缺口

每个 `HistoryPage` 返回记录、继续游标，以及本次请求／实际范围、政策版本、读取时间、快照水位和缺口。分别说明：

- 读取是否完成：完成、还有下一页、预算中断或无法确认。
- 采集是否完整：已确认范围内完整、存在已知缺口或未知。

缺口可来自未采集、到期、政策过滤、采样、队列丢弃、写入失败、损坏、未落盘、版本不支持或访问限制；未知数量不填零。空结果不等于没有发生问题，完整分页不等于完整采集。

异步 output 已发出事件不代表已经持久化。active 运行默认仅能分析可验证的已读前缀；没有可信结束记录不能算作成功运行。

### 分页与资源

游标绑定筛选、范围、政策和读取水位。分页期间到期、撤权或政策收紧时返回实际缺口／失效，不借快照续期，不悄悄换范围。没有稳定快照支持时明确 best-effort，模型可决定是否仍能据此分析。

读取、扫描、页数、附件展开、解码深度、时间和模型调用分别有界。限制中断要保留原因，不把截断资料标为完整。宿主检查路径、附件、摘要和存储归属；Core 检查收到的数据与工具返回，模型据此判断证据是否足够。

## 5. 产物由任务中规划，双方都能消费

Core 的产物规划包括对自身行为的解释、可复用的经验和未解决问题。App 的附加需要可以是面向用户的说明、故障定位材料、业务侧评估、结构化建议或某种可供程序读取的数据。

这些是可组合的产物方向，不是每次强制填写的栏目。模型可以根据任务提出更合适的产物，并解释无法完成的部分；App 需要机器消费时，使用其登记的 schema 或输出契约校验相应部分。

共同的最小封套保留产物 ID／版本、任务来源、证据引用、实际覆盖、生成时间、适用版本和有效期。正文与扩展结构可以采用解释、记录、母板、组合项或 App 提供的其他形式。不要把所有理解都压成统一统计表，也不要为自由正文取消来源说明。

同一份结果能同时服务 Core 与 App：Core 保留可供后续任务使用的经验和待验证判断，App 按自身界面、业务流程和处理方式消费。经验不是模型权重训练，也不是自动修改全局配置；实际操作仍使用已登记的能力与现有授权。

### 返回、查询与消费

App 可以通过现有调用结果或流接收本次产物，也可以通过提议的 `results.query/get` 查询已保存产物。需要异步完成通知时，注册普通的 App 接收 handler；投递状态与分析状态分别表达，投递重试不重新跑整次分析。

消费需求应在复盘上下文中提供，而不是等报告生成后才让 App 适配。App 可补充产物类型、重点、语言、格式和期望处理方式；Core 据此参与规划，仍保留自身有价值的发现。没有自定义消费要求时，Core 也能完成自己的复盘并返回有依据的解释。

App 自己拥有分析能力时，可以把它作为任务工具交由模型使用，或独立处理同一份获准数据。其结果作为带来源的补充理解进入任务，Core 可比较与吸收；不要求所有分析先改写成内置 Skill。

需要保存时，App 可提供独立的结果存储端口，负责实际存储、范围、期限和条件写入；Core 负责自己产物的构造、关联与查询投影。保存失败仍可返回本次结果，明确未持久化。

### 经验如何继续使用

后续出现相关意图时，Core 可以查询获准且仍适用的旧理解，结合当前任务和新证据继续推理。它们是有版本、有局限的参考，不替代本轮原话、实际来源、权限或必需检查。

App 可以反馈结论已确认、已否定、已采用或尚未验证，并附真实变更与后续结果。Core 据此修正理解；采用建议、执行成功、问题确已改善分别表达，不把上次总结或模型自述当作新的验证证据。

## 6. 保存、失效与兜底

代记、回查和产物保存独立提供。没有 output 时维持不采集诊断副本的原约定；已有历史可读时仍可按需复盘。没有任何历史来源时，说明不可回查，不扫描磁盘或偷偷补建归档。

只有 metadata 时，可以理解技术执行；需要正文的判断注明资料不足。没有模型时可返回实际读取结果和可用技术计算，不把它称为完成了语义复盘。没有结果存储时直接返回本次产物，可选使用有容量与 TTL 的实例缓存，重启后不承诺仍能查到。

超时、取消、限流、预算不足和损坏数据都有实际状态；有效证据可以保留，未完成部分显式说明。分析失败不改变原业务结果，也不触发原业务重试。

带原文或可还原个人信息的产物默认不晚于最早证据到期。仅聚合经验另设期限须有 App 的明确政策和实际内容投影，不能给原文贴“经验”标签后长期保存。撤权和删除影响相关缓存与派生产物；源日志到期后，旧结论的可复核性变化也要说明。

## 7. 避免错误学习

日志正文是待分析数据，不是新系统指令。Core 的可信自我说明与 App 的可信需求通过明确上下文输入；用户内容、模型历史输出和异常文本不能借合法信封升级信任。

分析任务标记 purpose 与 lineage，避免把自身产生的分析调用反复算作业务样本。同一调用的 wire 帧、逻辑增量和解析值不算多次独立事件；原始请求与修正尝试分别计数。

事实观察、原因假说和改进建议保留区别。计数注明口径、分母和缺失；相关性不自动变成因果性，旧经验不能自己证明自己。Core 可以提出超出 App 最初问题的发现，但必须交代依据与不确定性。

并发任务的较旧结果不覆盖较新理解。结果内容仍按 App 政策过滤；允许读取不代表允许向任何消费者披露。实际消费与处理确认不伪装为模型已经执行了操作。

## 8. 实施重点

先明确 R2 的数据处理和消费政策；取得相应实施授权后，再把可用范围、回查和结果返回接进现有模型／工具机制，提供可信的执行说明及 App 补充入口。用真实任务检验模型能否自主选择证据、调整调查、同时满足双方需要，避免先搭一条固定分析流水线。C4 的文件读取证据不能代替这一阶段的授权或模型效果验收。

针对性验收关注两条入口能否进入同一能力、Core 在 App 只提问题时能否参与规划、App 补充能否真正影响调查和产物、非内置工具／Skill 是否可用，以及日志缺口、预算、取消、到期和结果消费是否真实。

本文是设计提案，未新增运行 API、定时任务或已通过的验收声明。
