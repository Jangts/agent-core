## 1. 设计结论

agent-core 的下一步是让应用声明的能力能够贯通装配、模型输入、真实调用、完成检查和诊断。保持一个 Core 执行内核，配套 App 侧 Support 与可选 Kit；不要求两端使用同一种意图模型、回复协议或业务工作流。

Core 拥有执行保证；Support 帮助应用把同源声明接入这些保证；Kit 组织可选算法与局部流程；App 拥有事实、权限、业务状态和持久化。先补真实接入缺口，再按收益抽取，不以增加 Kit 数量作为完成目标。

## 3. 目标能力与归属

| --- | --- | --- | --- |

| 工具调用 | 输入→授权→执行→输出检查；关联调用与结果 | Support 同源生成 schema 和注册；Tools Kit 组织领域生命周期 | 真实权限、资源归属、副作用与执行回执 |

| 诊断 | 核心事件和调用关联；观察失败隔离 | Support／Kit 各自提供可选观察 | 存储、脱敏、正文开关、保留期及回查授权 |

## 4. 六项优先演进

### A. 应用能力清单的装配支持（P1）

在现有 `Support.defineToolCatalog`、`defineRegistrationCatalog` 之上补组合能力。建议 API 名称仅为草案，实施时按实际缺口决定是否新增：`Support.defineCapabilityCatalog`。

- 输入以类型化、可独立阅读的清单为主；核心引用包含模块 ID、工具、模型阶段、fragment 等真实引用。业务扩展元数据由应用类型拥有，不加进所有应用必填字段。
- 编译后提供引用校验和工具／模型／上下文投影；应用模块仍通过既有 API 注册到 Core。Core 不识别“能力模块”新执行实体。
- 校验重复 ID、失效引用、Skill 必需／可选工具、阶段与协议关系。已有底层检查直接复用，编译层主要检查跨清单关系。
- 区分静态已登记、部署配置可用、当前请求允许。模型展示是投影，真实授权仍在执行时检查；启用条件和绑定顺序显式声明。
- 不统一两个应用的 `completeDecision`、`scope`、业务 resources 等字段。先从 Banker 的组合及引用校验提取机制，再以小可乐现有清单适配验证边界。
- status 与文档从同一编译结果投影；不输出私有数据、内部路径、凭据或规范全文。

收益：新增能力主要改所属模块与集中清单，不继续增加主循环分支；不再为状态说明维护平行工具表。

### B. 完成性与最终提交（P1）

目前 Engine 已有 `validateResult`，两端也已有各自的业务完成检查。先追踪所有正常、直接工具、恢复和降级出口，再决定是否需要给现有工作流增加可异步的接受端口；不预先另建终态框架。

- Core 检查已登记的接受合同，业务 handler 决定“需求是否完成”。模型说 answer 或 finish 不构成完成证据。
- 如确有异步缺口，扩展现有提交边界，支持接受、带结构化原因的继续执行、真实错误；继续执行必须走明确路由并消耗既有预算。
- 等待用户与受阻允许结束当前运行，不代表业务完成。Banker 的四种 outcome 保持应用协议，不作为所有应用的必需枚举。
- 完成检查失败不得先发布最终响应再补救；流式预览仍是暂态。输出检查通过后才能发最终提交事件。
- 外部副作用可能早于最终提交发生。提交失败或取消不自动回滚真实写入；保留回执并由应用决定恢复，不隐式重放工具。
- 恢复、母板直出、局部失败降级都经过同一接受边界，保留当前允许的部分交付规则。

首个样例：Banker 的配图尚未实际交付时不能用口头答复结束；第二个样例：小可乐批次回答不能遗漏独立问题，也不能通过恢复出口发布已知错误正文。

### C. 请求级预算与取消传递（P1）

已有 ModelRunner、Engine、AttemptBudget 与 signal。先核对调用链是否始终复用同一次请求额度；缺口通过共享预算端口补齐，不替换为新执行器。

- 明确区分轮数、模型调用数、修复次数、输入／输出限制和请求 deadline；不同计数不混成一个 steps。
- 同一请求内的正文、复核、修复及 Kit 内部模型调用复用对应额度；子调用只能收紧限制，不能重置额度或延长 deadline。
- Core 提供通用预算消费与取消保证；应用决定启用哪些额度及具体数值。Banker 图片日额度、小可乐访客周额度是应用政策。
- 额外推理绑定先声明是否使用当前 ModelRunner，外部调用则显式接入同一预算端口，不能因走 ModelCalls 就自动获得独立次数。
- 若涉及并发，预算预占与消费需防止超额；本轮不主动引入并发执行。已发起调用即使取消也不保证上游不计费。

### D. 调用、回执与产物引用（P2）

工具事件当前主要记录名称、耗时和成功／错误，Banker 业务回执另存名称与结果。可补最小通用关联信息：request/run ID、invocation ID、能力名、阶段及执行结果；具体字段须与已有 diagnostics 合同合并审查。

- 区分调用失败、契约合法返回但业务未满足、实际完成。Core 判断调用与合同状态，业务状态由输出 parser 和 App 解释，不做统一 success 推断。
- 文件、图片、资料快照和业务记录引用由应用返回；引用的存在性、版本、过期、权限由真实服务核实，模型不能构造有效凭证。
- 一个调用的关联 ID 不等于幂等保证。写入重试由 App 的幂等键和存储实现决定；不在 Core 承诺 exactly-once。
- 仅在两端确有重复时，扩展现有 Evidence／Delivery Kit 的引用关联；不强制给所有工具包一层新结果信封。

### E. 证据问答与局部修正（P2）

复用现有 Knowledge、Answering、Presentation，实现上优先补缺口和接入说明。

- 来源快照与选择条件绑定，任务、回答项和来源可追踪；事实以当前真实读取为准，旧助手回答和画像不能替代来源。
- 确定性检查、模型复核、局部修正、再检查和摘录降级保持分工，只重做失败项。
- 将 Profile 的通用覆盖／修正机制用于评估 Banker 产品问答接入；产品条款有效性、客户材料和业务判断仍归 Banker。
- 不默认给聊天、天气、每次工具操作增加事实复核；每种任务明确配置检查和预算。

### F. 跨轮续接与长任务（P3）

App 用历史、真实资源引用和请求输入恢复语义上下文；独立新请求有自己的预算及权限检查，同一持久任务的累计额度和 deadline 则不能通过新请求重置。用户历史同意仅在业务规则允许的范围内有效，不能由检索结果授予权限。

初始规划曾暂缓持久化长任务。后续用户明确要求全部处理后，已在 App 侧通过可选 Durable Kit 实现检查点和显式恢复，实际消费者为 Banker 产品批次；Core 不增加数据库、后台队列、自动恢复进程或长期记忆层。副作用恢复必须经过应用对账，具体合同见第11节。

这项交付不包括任意专业子任务跨请求恢复（R4）、Agent 家族持久接续／成果合并／上岗（R3）或多层并发（R5）。Banker 已有 planning 角色与 case work-plan，描述的是业务计划和建议保存；Engine 内存 fork 描述的是分支和克隆数据，均不能充当长期子任务进程或授权转移凭据。

## 5. 装配与执行路径

1. App 声明工具、模型阶段、上下文、工作流及业务检查，并提供真实服务端口。
2. Support 校验与投影清单，产出既有 Core 能消费的配置；不用 Support 的手写接入遵守同一合同。
3. Core 按应用工作流执行，维护预算、取消、模型边界与工具输入输出保证。
4. App handler 按需调用 Kit，把业务结果与真实引用交回现有协议。
5. 候选最终结果经过应用登记的完成／证据／交付检查；Core 只在接受后提交。
6. App 保存获准范围内的最终问答、业务记录和诊断，Core 不持有长期数据库。

声明贯通不等于把所有资料合成一个巨大 catalog。应用保留各自权威业务清单，组合入口持有引用和实现入口；模型 schema、运行检查和文档投影消费相同声明，业务正文仍按需加载。

## 6. 迁移顺序与完成依据

| 批次 | 范围 | 完成依据 |
| --- | --- | --- |
| 0：真实合同核对 | 追踪两端工具、模型、预算和全部最终出口；列出现有 API 能解决与确有缺口的部分 | 每项新增 API 对应真实调用点；不把已存在的功能重复建设 |
| 1：清单组合 | Banker 模块组合／引用校验 → Support；小可乐以适配方式接入实际需要的部分 | 同源投影、错误引用在装配时拒绝；业务字段和顺序保持 |
| 2：完成及预算 | 覆盖最终出口，按需扩展接受合同；统一子调用额度传递 | 未完成不能假结束，恢复不绕过检查，修复不重置额度，取消不提交迟到结果 |
| 3：回执关联 | 在已有调用与诊断合同上增加关联，接通真实产物引用 | 能区分同名多次调用、业务拒绝与实际交付；重试不自动重复写入 |
| 4：问答复用 | 优先用现有 Kit 适配 Banker 的确切产品问答需求 | 来源可追踪、失败项局部修复、已知事实错误不因复核不可用而放行 |
| 5：公开面整理 | 同步实际 API、子入口、ESM/CJS、应用源码地图与文档 | 一个机制一份实现；聚合入口转出同一实现，不保留平行循环或旧接口兼容层 |

每批允许同步修改两端和 agent-core。SDK 与 App 同步使用当前合同；迁移说明记录前后差异，不据此保留旧参数、旧持久格式或旧日志转换层。

实现时围绕具体疑问执行最小检查，遵守仓库运行频率限制。候选验证包括失效引用、手写接入与 Support 等效、异步接受拒绝、恢复出口、共享额度耗尽、取消后的迟到输出、重复副作用和多项覆盖。按对应批次选择，不在规划阶段运行全套检查；真实模型语义、真实外部服务和用户视觉验收各自单独说明证据。

规划阶段仅梳理源码并更新设计；后续已实施范围及验证见第7节。

## 7. 2026-11-02 首批实施与保留项

已实施：

- Support 增加 defineCapabilityCatalog，提供模块与工具集合快照、工具归属、重复与跨模块引用校验；Banker 模块清单和 Skill 引用检查已迁入，原绑定、完成、恢复及状态投影继续消费同一清单。
- Support 的 validateToolReferences 支持已有独立目录；小可乐工具注册封存前检查 Scope 工具引用，不强制改成 Banker 模块结构。
- Banker 将普通回复、工具直出统一交给模块级 completeReply；修正工具直出绕过交付检查的缺口，保留异步 completeDecision、业务回执和继续执行路径。
- Core 工具调用在发起时分配 invocationId，成功／失败元数据和诊断使用同一编号；Banker 摘要协议同步增加可选字段。编号与 App request ID 配合使用，不承诺幂等或真实产物有效性。

本轮核对后无需新增的机制：

- 工作流 handler 已可异步执行，最终路由已有 validateResult 与提交前取消检查；Banker 本次缺口可通过现有 dispatch 阶段收敛，不新增接受端口或终态枚举。
- Profile 正文、复核、修正复用请求内同一个 ModelRunner；Answering Kit 的 canInvoke 使用其 remainingCalls，压缩子调用也消耗相同计数。本轮不引入平行预算对象或改变应用额度。
- Knowledge／Answering／Presentation 已承担批次覆盖、来源快照、局部修正和正文绑定，继续复用；没有为了满足规划项而再造算法或给 Banker 自动增加产品问答流程。

保留项（首批时点，阶段传输的后续落实见第8节）：模型阶段跨目录装配、通用产物引用组合、Banker 具体产品问答 Kit 接入和持久化长任务，仍需对应真实消费者或明确业务需求；本次不将其列为已交付能力。现有 App 文件／图片有效性、业务写入幂等、记忆期限和权限规则保持应用所有权。

验证：Core ESM/CJS 定向构建及两个后端 TypeScript 无输出编译通过；Core 能力清单、工作流、预算和工具接入67项隔离回归通过，Banker 完成出口、Agent、图片45项隔离回归通过。未调用真实模型或外部生成服务，未运行应用预览或视觉验收。

## 9. 2026-11-02 工具取消与回执边界

核对发现：Core 的直接工具接入此前没有请求 signal 保证，Support 的执行后检查也不能覆盖输出校验中取消或无限等待外部工具；同步 invocation 此前仅在 handler 之前检查取消，可能将已取消调用记为 success；checkpoint 抛错时已有 journal 条目未关闭。

本批落实：

- ToolRegistryPorts 增加可选 signal，Core 在输入解析前后、输出校验前后及成功提交前检查取消。Support 现有 options.signal 自然传递给同一个 Core 注册器，不增加平行协议。
- invokeAsync 可在取消时停止等待忽略信号的外部执行，清理监听器并消费迟到拒绝；迟到结果不再转为成功事件。调用编号保持原来的 invocationId，不新增补偿或重试。
- 同步 executeInvocation 在 handler 和回执生成后检查取消，使用已经取得的 journal 记录 aborted；checkpoint 异常也在同一个错误边界内关闭记录并传播原错误。
- 维持已有事件状态和 App 错误映射。取消不承诺副作用回滚；App 仍负责真实服务的信号传递、写入幂等与副作用对账。

## 10. 2026-11-02 注册快照与 handler 接收者

继续核对发现：Core 的 ModelCapabilityRegistry、ToolRegistry 和 ModelRunner 以对象展开保存声明，原型方法可能丢失，调用时的接收者副本也不具备原实例私有字段；阶段传输对静态 schema 做了投影，但 resolver 方法仍从原源对象动态读取，存在已准备交互的解析方法被后续替换的问题。

本批落实：

- 模型能力显式保存 ID、描述及绑定原声明的 parse；模型 schema 继续复制冻结，select 不破坏原 handler 接收者。
- Core 工具显式保存 name、kind 及绑定原声明的 input／execute／output。同步、异步及取消合同保持，原声明方法替换不改写已注册 handler。
- ModelRunner 显式保存 ID 及绑定原实例的 prepare；准备结果提供 options 和响应收集器，typed transport 原始实例身份检查保留。
- 阶段传输在准备投影时绑定 capabilities.resolve；动态源仍在下一次交互准备时刷新，已准备交互不漂移。

这些改动不冻结 App 实例内部业务状态，不新增包装类、执行层或模型调用。现有函数与对象声明仍沿用同一注册 API。
