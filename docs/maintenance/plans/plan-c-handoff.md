## 工作模式与监督标准

- 先看真实声明、注册、消费者和分发文件，再判断遗漏。历史规划的愿望不等于当前必做接口；当前代码的存在也不等于消费者已经完成接入。
- 保持现有工具入口；优先复用共享配置快照、Knowledge 编译器和已安装资源。没有收益的套壳不算简化。
- 先完成一条可阅读的实际路径，再扩大同组整改。文档、代码和行为一致，验证只围绕具体疑问；不可用放松检查或补造事实通过。
- SDK 验证与第三方产物验证分清；不假设公共 registry 已发布私有包，不漏实际依赖，不用临时 stub 伪造独立安装成功。
- 状态观察、最终交付、候选资料、已发布事实、读取权限和模型处理权限分别表达。
- 进度应持续说明已学到的事实、下一步和真实证据，不以工具数量或代码行数代替收益。

用户特别明确：监督考核的是概念、需求及目标风格。普通代码错误、编译或测试问题正常修复，不计作理解失败。核心概念偏离时先解释和纠正两次；两轮后仍无法理解推进，才由原会话让任务停止并接回。不能遇到一次错误就放弃。

原会话观察理解核验和首批实际设计，不以测试数量作概念理解评分；确认方向后结束短期监督，C 自主继续。只以实际完成范围标记 C 交付，R1—R7 长期项仍保留明确前置条件。
