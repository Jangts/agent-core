# Agent Core 1.0.0 正式发行与分库维护评审

日期：2026-11-25。范围：用户要求多 Agent 评估正式版发行完整性，以及 Agent Core 与 Jangts 网站、Banker 分库维护的稳定性。这里的分库是源码与维护责任分离，不涉及跨语言转译。本轮只评估和记录，没有修复源码、移动目录、创建仓库、安装依赖、发布或部署。版本保持已经确定的 1.0.0，0.9.0 的未发布历史及升级关系继续有效。

## 结论

| 判断对象 | 当前结论 | 含义 |
| --- | --- | --- |
| SDK 产品与运行时独立性 | 具备基础 | 未发现运行时必须引入网站或 Banker 业务实现的确定依赖；Core、Support、Kit、App 的职责可分离，不需要为分库重写运行时 |
| 当前完整 1.0.0 发行验收 | 暂不通过 | F1 已复现：文档公布的 Mock API 与包所支持的实际 peer 不一致；应对齐后再签完整发行验收，不能悄悄排除已公开的可选入口来宣称全部通过 |
| 原样移出包目录后独立维护 | 不满足 | 构建源稿、API 生成、默认测试、锁及应用镜像链仍有确定的原 workspace 依赖 |
| 完成有限准备后分库 | 可行 | 先关闭 F2—F4 的维护与消费链依赖，再用干净源码 checkout 和真实消费者验收；分库不自动要求多进程锁、重写框架或迁移业务数据 |

这是评审判断，不是迁仓实施批准，也不以评审意见对齐代替问题修复。F1 的代码/资料修复尚未实施；F2—F4 是分库切换前条件，不是现有 workspace 下 npm 运行时的共同故障。

## 问题账本与主审处置

### F1：Mock 文档与实际支持版本不一致

**P1，完整发行验收阻断。提出：R6；关联 R3、R8；主进程复现。修复未实施。**

事实链：

- `packages/agent-core/package.json:324–335` 的可选 peer 和开发依赖均精确为 MockGPT 0.2.2。
- `src/mock.ts:8`、`src/mock/node.ts:8`、`src/mock/web.ts` 直接转发实际安装的 MockGPT，不补充另一版本 API。本轮实际解析的已装版本为 0.2.2。
- `pages/development/scripts/docs/sources.mjs:39–54` 把相邻 MockGPT 源码直接替换为 TypeScript paths；`pages/apps/agent-core-docs/scripts/extract-api.mjs:44–59` 用它抽取 Core API。该邻仓当前是 0.3.0，定位器没有校验它是否符合 Core 的 peer 合同。
- 现存本地 1.0.0 站点目录将下列符号标作 Core Mock 子路径的运行时导出；实际使用所声明的 0.2.2 peer，ESM 和 CJS 各检查一次，七个符号在两种格式都缺失。

| 缺失符号 | 站点声明的 Core 入口 |
| --- | --- |
| bindMockDataChannel | `@jangts/agent-core/mock` |
| createMockDuplex | `@jangts/agent-core/mock` |
| findProtocol | `@jangts/agent-core/mock` |
| lifecycleCatalog | `@jangts/agent-core/mock` |
| lifecycleFaultCatalog | `@jangts/agent-core/mock` |
| protocolCatalog | `@jangts/agent-core/mock` |
| createMockWebSocketServer | `@jangts/agent-core/mock/node` |

后果：遵守 peer 合同的使用者按站点导入会失败或得到 undefined；相邻 Mock 源码变化可在 Core 包未变时改变其文档。它不证明普通 Core 入口运行失败，也未证明线上已发生事故。

主审采纳。最小修正先明确 Core 1.0 支持的 Mock 版本：保留 0.2.2 则从匹配版本公开声明或固定源码生成；采用 0.3 则先验证 Core 对其接口/类型/实际行为的接入并同步合同。两种路径都必须固定来源并验证版本，不能只放宽 peer、只删七个页面，或以邻仓当前源码通过类型检查代替实际包验证；成员和参数也可能漂移。验收需同候选包配所支持 peer 的 ESM/CJS 导出、严格声明与站点目录比对，并保留无 peer 的普通路径检查。

### F2：源码、资料与生成输入尚未归拢

**P1，仅阻断原样移目录后的独立维护。提出：R1/R2/R3/R4/R7；关联 R8。**

`package.json:314–315` 构建必跑 `scripts/sync-articles.mjs:5–11`，读取包外 `main/shared/agent-core/articles`；复制已经生成的文章不能保留源稿维护能力。`scripts/api-reference.mjs:41–59` 固定枚举包上两级的 workspace/packages。品牌原件及同步属于 `development/scripts/site-sync/brand-assets.mjs:15–28`，Pages `generate.mjs:299` 与 dev watch 也推导原共享源稿位置。

主审采纳，合并重复发现。SDK 应拥有或取得固定、可复现的必需源稿、Skill、示例、API 生成及品牌输入，维持单一可编辑源。Pages 保有站点组合/语言路由/部署，不接管 SDK 手册所有权。SDK 文档生成只读本包及明确版本依赖或有限显式关联源，不扫描任意业务 workspace。可采用单包仓根清单；没有必须额外创建私有根容器或新 npm 身份的理由。实际移动和归属调整留给后续授权实施。

### F3：默认回归与重建尚非 SDK 自有闭包

**P1，分库切换前条件。提出：R2/R3/R4；关联 R7/R8。**

`package.json:316` 默认执行全部 `test/*.test.mjs`；`test/decorators-consumers.test.mjs:9–20` 硬读网站和 Banker 的 dist，`test/core.test.mjs:40–47` 读取外层 packages/catalog，部分测试在包外临时目录依赖现有 bare import 解析。当前独立锁并不存在，安装与编排由 main 根锁和 workspace 管理；这是现有组织规则，不能报成当前单仓缺陷。

主审采纳。将 SDK 默认测试闭合于其正式源与最小公开 fixture；真实业务集成保留在消费方或明确跨仓任务，不能删除保障后声称独立。建立自身锁、构建/类型/API/概念/回归入口及必要规范。外部真服务可 opt-in，但跨仓验收必须显式提供候选路径并检查 skip；MockGPT 的 `multi-protocol-agent-core.test.mjs:3–7` 没有候选路径会跳过。最终以无旧 dist、无父级 node_modules、无业务源码的干净 checkout 验证自足重建。

### F4：消费、镜像和版本交接仍绑定本地 workspace

**P1，分库切换前条件；不是现有 npm 发包阻断。提出：R4/R7/R8，关联 R2/R3。**

网站、Banker 及 Cafe 已精确声明 Core 1.0.0，但当前锁与安装仍以本地 workspace 为输入。`deploy/docker-banker/Dockerfile:8–23,29–36,65` 安装指定 Core workspace、构建并复制本地 manifest/dist；网站 `deploy/docker/Dockerfile:24–25,55–58,94–97` 也保留对应假设。发布 npm 不会自动切换这些链路。

主审采纳。分库时同步 workspace/catalog/锁、构建上下文、生产安装与产物复制，正式消费明确 registry 版本或受控候选；源码联调作为显式覆盖，不能有旧目录兜底。SDK 发布和应用升级是不同责任，应用分别升级锁、验证真实 handler 和保存合同，再决定交付。SDK 维护入口应从 main 的 `development/maintenance/public-package-release/publish.mjs:19–20,54–73` 明确交接；已有该工具，不能误说没有发布机制。未查到仓内 .github/workflows 不证明没有外部 CI，实际 CI/发布系统保持待登记。

### F5：双模块或多副本工作流实例的组合边界

**P2，已验证互操作限制；不单独否定单模块格式的发行。提出：R5，主进程验证。**

`src/execution/workflow.ts:128–134`、`src/execution/engine.ts:543–545` 以 instanceof 识别工作流实例。主进程通过公开 import/require 对当前被验工件执行无模型探针：

| 组合 | add 结果 |
| --- | --- |
| ESM 实例 + ESM 实例 | 成功 |
| CJS 实例 + CJS 实例 | 成功 |
| ESM 实例 + CJS 实例 | TypeError: Invalid or duplicate workflow node |
| CJS 实例 + ESM 实例 | 同上 |
| ESM + CJS 的公开 definitions 扩展补丁 | 成功 |
| CJS + ESM 的公开 definitions 扩展补丁 | 成功 |

异格式实例不满足本地 instanceof，其运行时 nodes Map 被误作补丁节点序列，继而校验失败；不是已验证的 undefined nodes 异常。带 routes 的 fork 有相同构造器检查，但本轮未执行该分支，不冒称实跑。任意不同 SDK 版本之间的实例互操作没有据此获证。

主审采纳为应明确的边界：跨插件/跨格式交接优先传公开定义或显式适配，由宿主保持执行实例归属；不能为消除 instanceof 就随意信任任意对象。给不受支持的实例组合准确错误及文档，或另以具体需求设计兼容合同；不强制本次支持所有跨版本对象。两种格式分别可加载不等于实例可以混用。

### F6：首次稳定公开面与长期维护成本

**P2，维护承诺确认项，不是已发现的运行缺陷。提出：R4/R8。**

`src/index.ts:54` 公开 utils 整桶，`src/utils/index.ts:9–12` 包含规则遍历、文本比较、模型协议错误与 retrievalQueryKey；这些已进入公开快照。内部算法、查询身份及别名随公开面承担行为兼容成本，不能以后事后改标 internal 逃避责任。

主审采纳为明确成本，不要求删除已有公开/兼容入口或更改已定长期名。用有限公开合同清单确认哪些符号有意稳定；后续内部 helper 默认不要自动进入公共 barrel。既有 1.x 别名与正式政策继续承担，不因分库转嫁给消费者。

### F7：乙维护入口的实施状态残留

**P2，资料状态冲突。提出：R1。**

`docs/maintenance/iterations/1.0.0/model-protocols/1.0.0-plan-yi.md:3` 仍写尚未实施或运行验收，但实施记录与丁收口已有交付证据。主审采纳为维护资料收口建议：维护责任方更新入口指向准确时点证据，不改写历史真服务/专项记录，也不据此否认实际实现。此问题不是运行时失败；本轮未代改乙文件。

## 故障与升级必须保留的宿主条件

R5 静态核对 Durable 的 commitId、耗尽/过期只读对账、unknown 不重放、not-executed 不退款、先授权与登记尝试后执行等与实际测试断言吻合；历史 15 项条件跳过及四进程合成保存响应丢失的边界记载准确。不以未测所有云厂商、设备或断电自动否决有限合同发行。

分库本身不增加 writer。当前两端 work 的排他依赖 service 实例内锁，Durable exclusive 直接运行，保存再由宿主处理 revision：网站 `work/service.ts:40,56–62,318–328`，Banker `work/service.ts:81,114–119,449,471–482`。不能在未改合同的情况下把它扩大为多个实例共同恢复同一数据域；CAS 不替代覆盖执行过程的互斥。只有实际改变部署并发模型时才需要相应跨进程保证。

SDK 包版本不等于任务 definition revision。两端固定 revision='1' 的定义若以后改变步骤/状态/副作用语义，应由能力所有者决定新修订及旧记录策略；包版本锁不能代替此项。恢复重新授权，不恢复凭据；取消等待不等于远端撤销；回滚分别考虑代码、配置、数据和已发生副作用，不能只说回退 npm 版本就完成回滚。

## 影响摘要与最小顺序

| 变化与传播 | 受影响者 | 缓解与剩余边界 |
| --- | --- | --- |
| 邻仓当前源码代替受支持 peer → 文档超前 → 用户导入失败 | SDK、Mock、Pages、外部用户 | F1 先固定支持版本与候选来源；仅静态链接通过仍不能发现运行时导出错配 |
| SDK 目录移出 → 源稿/测试/生成工具缺输入 → 下个维护者不能重建 | SDK 与 Pages 维护者 | F2/F3 先转交唯一来源及本仓入口，再隔离验证；不复制业务私密资料 |
| 本地 workspace 改 registry → 修复不再自动进入应用 → 锁或镜像继续用旧/缺源码 | 网站、Banker 及部署维护者 | F4 明确包发布与各应用升级的不同责任；无旧目录兜底验收 |
| 分库后插件或依赖带另一份实例 → 工作流组合被拒绝 | SDK 扩展与宿主 | F5 使用公开定义交接/显式适配；不承诺任意版本实例互通 |
| 版本范围/混跑/代码回退 → 依赖或保存语义不同 | 所有消费者与真实外部动作 | 依赖解析和实际格式分别核验；unknown 不重放、身份/期限不重生，数据与副作用不随代码自动回滚 |

建议最小顺序：先对齐 F1，形成同一支持依赖与资料的 1.0.0 候选；再收拢 F2/F3 的源稿、锁、工具和测试；随后切换 F4 的消费、镜像与 Pages 来源；最后在无兄弟业务源码的独立 checkout 重建 SDK，网站/Banker 分别安装同候选验证真实合同。物理迁仓仅在后续明确授权后执行，不把发包与部署绑成一个不可回退操作。

发布前补核具体支持环境及 registry 依赖实际解析：Node 22.20/24.9 的历史实测不能写成精确 Node 22.12 实测；streaming 声明 ^0.1.2 而历史仓外固定 0.1.3，不代表已证实最低 0.1.2 不兼容，也不替代支持范围验证。公共 registry 发行后 README/keywords/版本/完整性复核属于发布阶段，不把尚未发布的 1.0.0 视为不存在。
