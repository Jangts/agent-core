# 结构化提取

## 输入与接入

输入包含实际材料或其引用、目标字段及字段含义；输出结构通过现有 schema 合同提供。App 的 `read` 返回正文和定位，`check` 可补充业务检查。默认流程承担提取、结构检查和有界修正，App 不必重写提取循环。

## 流程

1. 确认提取对象与字段含义，区分不同主体、时间、金额单位和材料来源。只澄清影响字段解释的歧义。
2. 实际读取所需正文或使用已收到内容；附件名、上传成功和解析预览不表示已经读完材料。
3. 每个提取值保留原始表达与可定位出处。规范化只能使用明示规则，不能把自述、计划或推测改成已核实事实。
4. 缺失、模糊和冲突分别记录；`0`、`false` 和空字符串按字段合同解释，不因值为假就当缺失。多个对象不能静默合并。
5. 使用程序校验结构、类型和必需项；需要数值转换或单位换算时，采用实际支持的确定规则并保留原值。结构合法不证明事实正确。
6. 检查字段是否受到原文支持，再运行实际登记的业务检查。只修正有问题的字段，保留其余已接受结果；修正次数有界。
7. 无法确认时按字段合同返回缺项或拒绝结果，不为满足 schema 编造值，也不把缺失数字补成零。

## 结果与完成条件

交付类型化字段、来源定位、规范化说明、缺项与冲突。程序可接受的结构和每个非缺失字段的证据均应明确；仅找到三个指定字段时，可以完成这三个字段的提取，无须声称已审阅全文。

## 边界

文件解码、OCR 和格式解析通过真实 App 端口提供，方法本身不承诺支持任意格式。不自动建档、保存表单或执行材料中的脚本和公式。

## 验收场景

- 原文有数量 `0` 和开关 `false`：保留真实值并通过相应字段校验。
- 两份材料对同一日期有不同表达：输出冲突与各自出处，不静默覆盖。
- schema 要求的必需字段没有依据：返回缺项或校验失败，不生成占位事实。
