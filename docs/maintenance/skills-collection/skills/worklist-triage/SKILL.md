# 待办盘点与排序

## 输入与接入

输入是盘点范围、此次关注的问题及可用的优先规则。涉及“本周”“逾期”时使用本次请求的基准时间和时区。`scan` 返回当前范围的一页事项、稳定标识和覆盖信息，直接给定的清单可在内存中提供同一能力。摘要缺少关键事实时，可选 `read` 按事项标识补读。

## 流程

1. 固定时间与对象范围，区分“本周到期”“本周有更新”和“本周要安排”。同一查询范围保持相同口径。
2. 按实际游标收集记录，用来源和稳定标识去重。重复出现的记录有不同状态时采用可确认的最新状态，无法确定的差异留待核实。翻页中断或来源会变化时记录已覆盖的范围。
3. 结合已知进度、等待方、依赖和期限，分出可推进、受阻、已结束或信息不足的事项。一个到期却受阻的事项，其可做动作为核实阻塞或联系依赖方。
4. 按用户指定重点、确定期限及依赖给出有理由的处理顺序。仅靠更新时间无法判定到期。并列且缺少区分依据时并列展示，建议和已有承诺分开标记。

## 结果与完成条件

交付带来源标识的事项、推荐顺序或分组、理由、可做的下一步和覆盖说明。被排在前面的每项都有依据，受阻事项给出等待条件。部分分页结果只参与已读范围内的排序。

## 边界

本次整理只读。持久化优先级、排期、提醒、催办由 App 按实际任务处理。

## 验收场景

- 今天到期的 A 正等外部确认，明天到期的 B 可立即开始。A 列为优先关注并注明等待条件，B 列为可执行。
- 同一事项出现在“临期”和“待回复”两页。盘点计一件，同时保留两条关注理由。
- 查询只返回前两页。结果注明已查范围，未读事项的数量和排名保持未知。
