# 交付复核

## 输入与接入

最低输入为待检查内容与检查目标；需要事实复核时还须有相关依据。App 的 `read` 提供成稿和来源正文，可用 `query` 重算数字、`check` 运行特定检查。没有来源也能检查表达和内部一致性，但不能声称事实已核实。

## 流程

1. 确认待检查对象、当前修订和范围。纯错字或指定段落检查按该范围工作，不擅自扩大到完整报告审计。
2. 实际读取需要的正文与附件内容，记录读过和未读过的部分；文件生成回执、标题和摘要不能代替读取。
3. 按目标核对主体、日期、单位、数字、正文与表格、引用和结论强度。建议不是事实，意向不是承诺，准备不是完成。
4. 每项确定问题关联成稿位置和实际依据。数字疑问用已支持的程序查询核对，条件不清时保留疑问，不猜一个替代值。
5. 区分确定错误、需核实的问题和表达建议，按影响排序。业务规则仅使用实际登记的检查，不强加不存在的必填清单。
6. 给出局部可替换文字或明确修改方向；修改后对受影响部分复核。修正有界，无法确认的结论保持未确认。
7. 交付复核范围、问题、建议和剩余缺口，不把“未发现问题”升级成对原件真实性或所有业务要求的保证。

## 结果与完成条件

每项问题包含位置、原内容、依据、影响与建议。指定范围已完成相关检查，或未完成部分已明确列出；没有检查内容的空问题列表不能代表通过。

## 边界

本方法不自动重写全文、覆盖原件、发布或发送。文件内容检查不等于排版或视觉验收；这些能力未实际执行时保持相应边界。

## 验收场景

- 成稿将“计划提交”写成“已提交”：指出位置与来源差异，提供准确替换。
- 没有证据附件：可以指出内部矛盾，不能判定外部事实真实。
- 仅检查一个章节：结论限定该章节，不报告整份文件通过。
