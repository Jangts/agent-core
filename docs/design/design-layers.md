# Core、Support 与 Kit

命名约定：`Support` 表示围绕 Core 契约的一套接入支持能力，作为不可数名词不使用 `Supports`；内部可以包含多个模块、类和函数。`Kit` 表示一组可独立选用的业务能力，多个 Kit 的汇总入口为 `/kits`。helpers、utils 可描述局部实现，但不替代这两个按服务对象划定的公共职责。

本页说明库的职责与依赖关系。接口调用见 [API 手册](../../packages/agent-core/development/docs/api/README.md)，内部模块定位见 [模块职责](modules.md)。路由、生成器及执行接口的具体设计约定见[接口设计约定](interface-design-conventions.md)。

## 与调用方共同演进

SDK 与调用方按各自项目维护。应用功能需要时，可同步调整 Core API、协议和运行机制，以及 Support、Kit 和相应调用方。Core 维护通用执行保证，应用提供平台事实、权限与具体业务规则。修改公开契约时同步维护受影响的实现、文档和消费者。

## Core 自身的最简路径

Core 的普通调用只要求 Provider 和输入。ModelRunner 自带可覆盖的运行设置、普通文本交互及原始 prompt 接入；AgentCoreEngine 提供默认有界步数和耗尽错误。省略配置可以运行小型示例，完整配置仍控制同一执行路径，不形成另一套调度机制。Core 的缺省行为由 Core 提供，最小调用可直接使用普通对象和标量。应用接入时，优先从 Support 提供的参考实现开始。复杂上下文策略、压缩 handler、工具授权和业务编排在显式启用后继续遵守原合同。

## Core 缺省与 Support 补全

Core 的可选字段来自执行契约。字段省略时，Core 或者可以照常运行，或者采用缺参时合理且可预测的值。这个值用于保证基础运行，例如 Engine 的默认步数上限。

Support 的可省略字段来自具体实践。Support 可以按场景选定推荐值，也可以补齐 Core 合同里的必填字段。推荐值既可以是标量或对象，也可以是解析、选择或处理函数。应用拿到的是可以直接交给 Core 的接口实现。

判断缺省值先看 Core 合同如何解释缺参。数字的 `0` 和字符串的空值可以表达中性含义，实际取值仍由字段合同决定。例如 ModelRunner 默认最多调用 8 次，提供有限的运行预算；`0` 则明确表示禁止调用。判断最佳补全先看使用场景。例如采用 JSON 对象交互的模型调用可以选用相应的解析 handler，字符串占位文案则应由具体场景说明需要填写的内容。场景不足以推导时，由调用者给出业务选择。

同一个 Core 合同可以配有多套 Support 推荐策略。每套策略应说明适用场景、默认值、生成规则及可覆写项。场景可以通过不同构造器或 Define、Create、Build 函数表达，也可以通过单一入口中有明确类型的策略参数表达。沿用现有场景标识即可，是否拆入口以调用者能否理解和渐进配置为依据。多套策略最终均实现 Core 接受的合同，应用也可以在该合同上自行组合或替换。

Support 可以用有场景意义的快慢、质量、大小或预算档位表达偏好，生成 Core 所需的数值、处理器及关联配置。档位名称和参数映射由 Support 拥有，并公开适用条件、覆盖优先级及成本取舍。调用者可直接填写精确参数覆盖生成值。只有实际掌握模型、场景或能力依据时，才把选择描述为质量或性能承诺。

补全还包括从现有输入推导字段，以及从清单生成可枚举配置。例如路由生成器可以从目标推导路由 ID，能力目录可以从一份定义生成模型可见清单。可机械推导的枚举、字典和数组由生成函数统一构造；用户负责给出业务决策及无法推导的数据。授权等需要调用者明确决定的事项继续遵守 Core 合同。

## 一个内核，配套 Support，可选 Kit

| 设计取向 | 负责内容 | App 的接入方式 |
| --- | --- | --- |
| API 与协议 | App 调用 Core、Core 回调 App 的双向合同及运行保证 | 调用实际 API，并实现需要的 handler／端口 |
| Support 与约定 | Core 契约的推荐实现与使用范式 | 直接传入 Support 实现，按需替换为实现同一契约的对象或类实例 |
| Kit 与规范 | 可选业务库及自己的 API、局部合同与流程 | App 单向使用；需要时把结果转换后交回 Core |

它们不是三个并列的运行层，也不要求每个函数唯一归类。组织用于澄清责任、减少真实耦合，不为概念完整增加目录、接口或自动门禁。同一基础实现可跨用途复用。

## 双向合同与单向使用

```text
App 调用 Core API ───────────────→ Core
App 实现 Core handler ←────────── Core 按合同回调

App → Support → 合规配置／handler → App 注册到 Core
App 的业务 handler → Kit → 业务结果 → App 返回 Core
```

Support 提供可直接交给 Core 的接口实现。应用可以沿用其配置和策略，也可以独立实现同一接口。Core 按接口调用并保留接收者，支持原型方法和私有状态。确实需要实例身份时，由 Core 提供构造器，Support 和应用可以继承。Kit 拥有自己的局部模型，Core 不按 Kit 名称分支、读取其状态或要求其启动。Kit 内部可以调用 Core API，调用期间仍服从 Core 的预算、取消与错误语义。

## 运行边界

- Core 的已注册能力与阶段选择、输入→执行→输出、取消、预算、完整响应及提交合同不能被辅助库放宽。
- 用户身份、资源归属、事实校验和实际副作用来自 App 真实端口；模型可见 schema 不证明授权或业务真实。
- App 不采用 Support，也须满足已经接入的 Core 合同；App 不采用某个 Kit，无需模仿其内部阶段或工作模型。
- handler 的错误、求值与执行顺序、同步／异步边界按各接口保证；诊断和 observe 的失败隔离不能吞掉业务错误。
- 采用 Kit 后，其局部 API 仍有严格的参数与结果合同；可选意味着可以不选，不意味着选用后可以忽略检查。

## 组织与公开面

Core 运行主体直接使用自身合同和共同基础，避免反向依赖 Support 封装或 Kit 业务。声明按责任集中；内部实现不从包根重新导入自己。

Core 和 Support 从根 index 提供。Support 先集中到一个总空间，再按实际需要编组。Kit 默认独立路径，也有显式全量入口。静态模块可提供对象；有主构造器时由主构造器承载相关静态辅助和从属构造器；多个平级构造器由对象组织。保持原对象身份，避免为命名空间复制 wrapper class。

聚合路径转出同一实现，不代表执行层之间的依赖。App 的推荐调用与 [API 手册](../../packages/agent-core/development/docs/api/README.md) 一致，内部的目录与导出排查记录另放维护文档。

## 日志

Core 仅产出自身运行事件，App 管理存储、过滤与保留期。Support 的 ProviderObserver 与 Kit 的 observe 向 App 提供局部观察，不写入 Core 事件目录。未提供输出端口时不记录；观察错误与业务执行隔离。Kit 内调用 Core Engine 或 ModelRunner，仍由这些 Core 服务记录自身事件。

## 资源与可靠交付

Core持有请求消费账本、授权调整上限、父子约束和取消保证。Support提供剩余工作评估及不重放主操作的恢复边界；Completion Kit提供明确修复目标的检查结果。它们不构成第二个调度框架，不要求应用采用统一全局任务状态。任务价值、是否值得追加资源、证据充分性、主任务与附属功能的认定、持久状态和对用户的说明由应用负责。输入负担优先通过投影、复用或安全压缩处理；初始分配不足不自动推导为部分交付。


## 拓扑与产品角色

Core 不按业务节点或技术节点判断应用质量。完整用例可以作为节点，探索循环可以由新证据驱动并设置无进展出口；阶段拆分按独立路由、成果复用和恢复收益，与状态交接、失效及额外调用成本比较。仅需观察的内部细节使用 subflow 或调用记录。Support 的推荐拓扑是可替换的接入范式，App 的实习助理角色、业务完成标准与表达规则不是所有应用的公共合同。

静态 inspection 的可达性、引用和声明检查不证明上述设计合理，也不证明动态授权或任务完成。离线运行验证指定响应下的路径与副作用；真实模型样本验证语义质量；生产结果需要宿主实际证据。详见[节点决策依据](../../packages/agent-core/development/articles/nodes-and-tools.md)。
