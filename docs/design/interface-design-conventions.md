# Agent Core 接口设计约定

本页说明 Agent Core 的路由生成、执行边界与 Core／Support／Kit 分层约定。通用接口原则见[接口设计规范](../standards/interface-design-standard.md)，实际 API 见[使用手册](../../packages/agent-core/development/docs/api/README.md)，职责关系见[Core、Support 与 Kit](design-layers.md)。

## 同一入口逐步扩展

最小用法是完整配置的子集。增加配置、工具、模型或策略时，已有构造、执行和结果读取方式继续成立；只补充新需求的内容。不要先用一套极简 DSL，遇到真实业务再要求使用者重新学习另一套编排方式。

- 构造负责固定依赖及常用设置；运行负责本次变化的数据。
- 配置可在构造时提供，也可在省略后通过实例方法绑定；不强制必须分成构造和后续登记两步。
- 同一调用允许便利输入时，输出保持同一结果合同，不因传字符串或对象而切换返回范式。
- 自定义 handler、配置对象和内置实现应能在同一条执行路径组合，不另建平行调度机制。
- 实际预算、取消、授权、输入输出检查及错误顺序不能被便利入口绕开。

## 实例拥有固定关系

实例应持有它所代表的配置与依赖，不能创建实例后仍让每次调用重复传入同一套东西。

Provider、Workflow、工具清单、观察出口和默认策略若属于实例的固定关系，应提前绑定。请求只携带状态、输入、当前身份及确实随本次运行变化的选择。不能为减少参数而将用户身份、请求取消信号、余额或可变状态固化进共享定义。

一对一关系通常使用 bind；集合登记通常使用 register。名称表达关系基数和生命周期，不要求所有对象都使用同一动词。已经绑定的默认实体允许按 ID 选择时，优先使用一个明确的选择字段，不另设作用相同且可同时传入的 ID 字段。

配置的所有者与可变性必须可见：绑定是否允许重复、选择是否仅影响本次请求、派生是否共享预算、组合是否覆盖冲突，均应写入合同。Workflow 扩展等不可变操作保持旧定义不变；派生 Agent 的继承、组合、检查点与日志身份按对应 API 明确表达，不能靠“复制”一词隐藏执行状态共享。

## 一致性先于局部省写

同一概念统一名称、字段结构和语义；同组方法保持相同参数顺序、可选项位置和输入输出关系。

- `route.to*` 的首参为目标节点；比较值与比较路径分别使用 toIfEqual 和 toIfEqualWith。
- 字段路径按同一规则解释，包括 `aaa.0.bbb` 这样的数组下标路径；不要在不同入口切换路径语法。
- 真值判断、已定义、非空、相等、错误存在和可交付分别表达，不以一个模糊的“有值”覆盖所有语义。
- 执行身份、定义身份、实体引用、序号、数量、绝对时间及持续时间不能混用；单位和作用域明确标注。
- 同步接口明确拒绝异步结果；异步接口等待真实结果。抛错、返回错误和返回布尔值的作用按合同区分。
- 检查参数名称表达触发语义，例如 breakWhile 的 occur；不为单复数制造另一套概念或重复入口。

名称、默认值与参数顺序应结合整组接口评审，不能逐个优化后产生不同习惯。类型与运行时校验共同保证合同，不依赖调用者“应该知道”。

## 原始合同与生成方式

原始配置本身可以是规范、完整的用法。便捷函数的价值是固化常用选择逻辑、提供语义化配置方式，并减少复杂配置；它生成同一种原始合同，不创造另一种运行格式。

以下片段展示同组生成方法的参数方向；具体导入和可用入口见 SDK API 手册。

```ts
route.to('repair');
route.toIfError('failure');
route.toIfNotEmpty('candidate', 'candidates');
route.toIfEqual('service', 'intent', 'status');
route.toIfEqualWith('matched', 'selected.id', 'expected.id');
```

这些方法封装的是确定的条件和配置生成。任意业务判断仍可直接写 when；不必把每个函数都包装成 picker。已经生成 route 的数组不需要再套一个没有额外职责的 routes 函数。业务专属字段或流程不能只因两个 App 使用就升级为所有使用者必须理解的 Core 概念。

同组专用生成器可以有不同的合理规则。介绍现有 `route.to*` 的标识习惯时使用“一般”“习惯”，不能将多数方法的习惯写成全局约束。`route.to` 一般按目标生成 ID，第二参可显式覆盖；比较型生成器可以依据路径、值及目标构造标识。

可推导标识由生成器负责。要求稳定关联时不使用随机 ID；重复标识的加缀和显式冲突按所属合同处理。使用者只需在确有外部关联或可读性需要时提供自定义标识。

## 公共规则与专用规则分开

Workflow 面对的是配置对象，不应猜测对象来自哪个 helper。公共处理能力对所有实现同样有效，不通过额外 flag 或 namespace 字段识别“便捷函数生成的对象”。

例如原始路由配置可以使用 `conditionId: '{nid}.{rid}'`，由 Workflow 用所在节点和路由的实际身份求值。手写对象与生成器产物共同使用这一合同；不要求调用者再配置可从节点取得的命名空间。

相反，某个生成器的 ID 命名习惯不应被移入 Workflow 自动补齐。生成器负责自己承诺的配置，Workflow 负责公共引用、占位符和冲突检查。公私边界以谁掌握规则及上下文确定，不能为了省一个字段给整个系统增加新标准。

## Core、Support 与 Kit

三者按责任区分，不是三套并列执行框架。

| 部分 | 定位 | 设计边界 |
| --- | --- | --- |
| Core API 与协议 | 最基础且广泛的双向契约及运行保证 | 接口驱动，不依赖 Support 或 Kit 的业务模型 |
| Support 与约定 | Core 的推荐使用范式及可替换实现 | 提供有场景依据的补全与策略，不只是参数套壳 |
| Kit 与规范 | App 按需选用的能力库 | 拥有局部协议；Core 不识别其业务名称与状态 |

Core 接收满足 Interface／type 的实现，可以是普通对象、带原型方法的实例或自定义类。Support 产物直接交给 Core，不需要转成 plain object；保留方法接收者、私有状态和合同允许的属性访问。确有实例身份要求时，基础构造器由 Core 提供，Support 和独立开发者通过规定扩展点实现。

Core 最小启动仍可由普通对象和标量组织。推荐先学习 Support，不等于 Core 运行依赖 Support。Core 不把某套压缩算法、资料结构或 Kit 阶段固化为所有应用的必需项；选择、压缩等策略可通过普通节点接入，由 Core 提供调度和运行保证。

## Core 缺省与 Support 最佳补全

Core 可选参数源于“缺少此参数是否仍能执行”和合同规定的基础缺省；Support 补全源于“此场景怎样配置更合适”。数值为0、字符串为空并不天然正确，实际含义始终服从语义。

Support 的最佳实践可以体现为：

- 合理的标量、对象及 handler 默认实现。
- 根据参数关系推导 ID、引用和关联配置，避免冗余。
- 从枚举、字典和数组生成完整配置，减少逐项重复和漏配。
- 按快慢、大小、质量或预算档位生成明确数值和处理策略，同时保留精确覆盖。
- 多套场景实现或有类型的策略选择，而非为所有使用情形规定唯一答案。

策略必须说明适用条件、默认映射、覆盖优先级、成本及限制。没有模型或业务依据时，不作质量、速度或容量承诺。Support 保留 Core 合同的自由度，不为方便而封死自定义 handler、精确数值或合法的其他实现。

## 观察、日志和真实副作用

Loop 统一拥有节点执行身份、开始结束、错误、取消及实际模型／工具调用事实。节点通过 payload、子步骤等规定出口报告自己掌握的事实，不重复承担整个诊断系统，也不在每层手工转传可以由当前执行端口绑定的上下文。

模型事件、工具回执、请求内 Journal 与持久化日志按同源调用关联，不能把一种投影虚构成另一条调用。App 负责存储、保留期及披露，App 的问答记录关联 Core 调用链，Core 不感知 App 的消息表。App 注册监听取得中间状态及最终输出；预览不是完整验证结果，也不是隐藏思维或授权证明。

取消等待、超时、停止本地界面与实际副作用终止是不同保证。接口必须保留已经发出的提交及真实回执，不假装回滚；重试是否安全由幂等或对账合同决定。元数据和观察失败不能掩盖业务错误；执行所需校验也不能被降为尽力记录。

## 公开面、示例与评审

每个公开入口都有明确职责，聚合和独立路径使用同一实现。避免同义别名、无职责的本地转发层、重复配置字段和仅为分类新增的目录；有独立使用价值的完整工具可以独立成包，不以消费者数量机械判断。

Kit 既然通过 SDK 提供，其公开 API、字段和场景就纳入 SDK 文档。包括 MockGPT 在内，示例使用 SDK 的公开转发入口；读者不必跳到另一个包补学缺失合同。

示例按同一业务由简入繁，标明输入、返回和实际行为。比较两种写法时展示等价的配置与结果，不能把不同业务结果包装成纯写法差异。策略实现也应可查；使用文档只描述当前合同，讨论、变更和待办遵守[文档规范](../standards/documentation-standard.md)独立维护。

评审主要接口时，逐项回答：

1. 固定的东西是否仍在反复传递？可以绑定或代指的决定是否重复配置？
2. 从最小调用加一个需求，是否只需补配置而无需换写法？
3. 同组入口的名称、参数方向、字段、单位和返回是否一致？
4. 封装是否实际固化了逻辑、推荐策略或生成关系，而非套壳？
5. 专用默认规则是否错误地进入公共执行层？是否增加了可推导的新字段？
6. 普通对象与实例是否都按同一合同工作？是否隐藏了身份依赖或接收者丢失？
7. 自定义实现是否仍保留预算、取消、授权、完整响应和副作用边界？
8. 文档、策略、示例与实际消费者是否使用同一套公开合同？
